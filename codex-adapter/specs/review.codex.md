# Codex Spec：review

> 本短流程卡用于 Codex 执行独立审查。
> 它强调“只读权威原文”，避免被执行者叙事锚定。

## 输入

Codex 必须从 `codex-adapter/handoff/review-handoff.md` 格式的交接包开始。

必读：

1. review handoff。
2. task package 全文。
3. diff 或 PR 改动。
4. PRD/TRD 精确引用。
5. standards 精确章节。
6. 测试文件与测试结果。

不得把执行者总结作为审查依据。

## 审查顺序

### Step 1：确认审查范围

确认：

- 审查对象是 diff、PR，还是 working tree。
- task-id 和 source 明确。
- 任务包和 diff 都存在。

缺一不可。缺失则停止。

### Step 2：建立 AC 对照表

从任务包抽取 AC，建立：

| AC | 来源 | 应该在 diff 中看到什么 | 测试证据 |
|----|------|------------------------|----------|

审查过程中逐条填。

### Step 3：读 diff

只围绕当前任务检查：

- 修改是否覆盖 AC。
- 是否出现任务外修改。
- 是否删掉或绕过已有约束。
- 是否引入安全敏感类别。

### Step 4：核 standards

按 handoff 指定章节检查，不泛泛套用所有标准。

若发现明显相关但 handoff 未列的 standards，可补读并报告“handoff standards 不完整”。

### Step 5：核测试

检查：

- 测试是否真的断言行为，而不是只调用。
- 不可视区 AC 是否有测试。
- 错误路径、边界、权限、数据隔离是否覆盖。
- 测试结果是否来自本次改动后。

### Step 6：分类 findings

分类规则：

- `[阻断]`：不修会导致 AC 不满足、越界、安全风险、测试虚假、standards 明确违规。
- `[建议]`：可合并但建议后续改进，或风格、可维护性、轻微重复。

每个 finding 必须有证据。

## 输出格式

```markdown
## Codex review 结果

### 结论

通过 / 需修订

### 阻断

- `[阻断] {标题}`
  - 证据：
  - 影响：
  - 建议：

### 建议

- `[建议] {标题}`
  - 证据：
  - 建议：

### AC 对照

| AC | 结果 | 证据 |
|----|------|------|

### 已检查

- task package：
- diff：
- standards：
- tests：

### 未能检查

- `{项目}`：`{原因}`
```

## 审查红线

- 不根据“看起来应该可以”给通过。
- 不因测试绿就跳过 AC 忠实性检查。
- 不把执行者总结当证据。
- 不直接修改代码，除非用户把任务改成修复任务。
- 不替代 Gate 签字。

## 通过条件

只有同时满足以下条件，才输出“通过”：

- 无阻断 finding。
- 每条 AC 至少有实现证据或明确不适用说明。
- 相关 standards 无明确违规。
- 测试结果没有虚假或缺口未说明。
- 未发现安全敏感未裁决风险。

有建议项时仍可通过，但必须列入建议。
