# Codex Spec：method-change

> 本短流程卡用于 Codex 修改 hact-method 方法论仓的局部文件。
> 它强调范围控制、先扫后改、改后回扫。

## 输入

Codex 必须从 `codex-adapter/handoff/method-change-handoff.md` 格式的交接包开始。

没有明确修改目标和允许范围，不进入编辑。

## 执行步骤

### Step 1：核对边界

确认：

- 修改目标明确。
- 允许修改范围明确。
- 禁止修改范围明确。
- 只读参考文件明确。
- 验证方式明确。

缺少任一关键项，停止并要求补 handoff。

### Step 2：读取参考

只读取 handoff 指定的只读参考和允许修改文件。

若发现必须读取额外文件才能判断：

1. 说明原因。
2. 读取最小范围。
3. 在结果中记录扩读。

### Step 3：现状扫描

按任务性质先扫：

- 术语替换：`rg "{旧术语}"`
- 路径调整：`rg "{旧路径}"`
- task type 变化：扫描 `skeleton/04`、`specs-*`、`templates/status.yml`
- 脚本变化：查看脚本和调用点
- 若本次修改目标是 `specs-execution/*.md` 或 `codex-adapter/specs/*.codex.md`：额外检查对方是否需要同步（两者是长卡/短卡关系，独立维护、无自动同步，参见 `specs/consistency-check.codex.md` 第 7 类检查）

不做盲目全文替换。

### Step 4：编辑

编辑原则：

- 小步修改。
- 保持原文件风格。
- 不做无关重写。
- 不改历史事实，除非 handoff 明确要求。
- 不把实验层内容写入正式方法论，除非 handoff 明确要求。

### Step 5：验证

按 handoff 跑验证。

常用验证：

- `rg "{旧术语}"`
- `rg "{新术语}"`
- `git diff --check`
- `node --check {script}`
- 对照清单人工核对

无法运行的验证必须说明原因。

### Step 6：完成输出

输出格式：

```markdown
## Codex method-change 结果

### 修改文件
- `{file}` — `{改动原因}`

### 验证
- `{command/check}` — 通过 / 失败 / 未运行（原因）

### 范围说明
- 是否只改允许范围：是 / 否
- 是否发现额外问题：

### 建议下一步
- 
```

## 退回条件

出现以下情况，停止并退回 CC：

- 修改目标与现有方法论冲突。
- 需要用户重新拍板方向。
- 发现允许范围不足以完成任务。
- 验证显示会影响未授权目录。
- 需要改历史记录但 handoff 没说明。

## 成功标准

- 修改范围可解释。
- 验证结果可复现。
- 无未说明的主体方法论漂移。
- 下游 CC 能直接审阅 diff。
