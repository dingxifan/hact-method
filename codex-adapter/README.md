# Codex Adapter for hact-method

> 本目录是 hact-method 的 Codex 适配层实验区。
> 它不修改现有 Claude Code 方法主体，只定义 CC 与 Codex 混合运行时的分工、交接包和短上下文协议。

## 目标

让 hact-method 可以在两类执行端之间协同：

- Claude Code 继续承担长上下文、长对话、语义收敛和 Gate 编排。
- Codex 承担边界清晰、可文件化、可验证的执行任务。

本适配层的目标不是替换 Claude Code，而是把部分工作从「长上下文连续会话」改造成「短上下文、强文件输入、可重复验证」的执行单元，**以降低这部分工作的单次执行成本**。

## 为什么引入 Codex

引入动机是**成本**，不是"Codex 上下文比 CC 小"。上下文窗口大小会随模型版本变化，不适合当长期立论依据；即便两者窗口相近，可验证执行类任务本来就不需要长上下文才能做对，用短上下文、强文件输入的方式执行，是把钱花在真正需要长上下文的语义收敛类工作上。

决策#26 已经在 CC 内部把纯审查/一致性核对类 subagent 降级为 `haiku` 模型来控成本。`codex-adapter/specs/review.codex.md` 和 `consistency-check.codex.md` 描述的场景与此高度重叠。**在扩大 Pilot B/C 之前，应先对比"同等任务用 Codex 的成本"与"同等任务用 CC + haiku subagent 的成本"**，确认净收益确实来自 Codex（例如 develop 场景 Codex 生成代码质量更好、或计费单价更低），而不是想象中的"上下文更小"。若对比后差距不明显，本适配层的收益应重新定位为"供应商分散"或具体场景的能力差异，而不是成本本身。

## 不做什么

第一阶段不改动以下目录：

- `skeleton/`
- `specs-structural/`
- `specs-execution/`
- `templates/`
- `guide/`

这些仍然是当前 Claude Code 版方法论的权威来源。Codex 适配层只在本目录内试验，待试点验证后再决定是否回填正式方法论。

## 初始文件

| 文件 | 用途 |
|------|------|
| `task-routing-matrix.md` | 定义每类 task 推荐由 CC、Codex 或二者混合执行 |
| `context-strategy.md` | 定义 Codex 短上下文运行策略 |
| `handoff/develop-handoff.md` | 定义 CC 将 develop 任务交给 Codex 时必须提供的交接包 |

## 设计原则

1. **不靠聊天记忆交接**：交接必须落成文件或明确路径。
2. **不让 Codex 猜上游语义**：Codex 只执行已收敛、边界清楚的任务。
3. **权威来源优先**：任务包、PRD/TRD 行号、standards 章节、diff、测试结果优先于执行者口头总结。
4. **短上下文优先**：Codex 不默认加载整份长规范，而是按任务包精确读取必要片段。
5. **可验证优先**：能用脚本、测试、`rg` 检查的，不交给模型记忆。

## 人工交接怎么操作

第一阶段"先人工切换，不做自动编排"（见 `pilots/pilot-plan.md`）指的是以下具体步骤，不是"把内容念给 Codex 听"：

1. CC（或人）按对应模板，把交接包**写成实际文件**落盘到仓库内，推荐路径 `_meta/sessions/{task-id}-{develop|review|method-change}-handoff.md`。交接包必须是仓库里的真实文件，不是只存在于 CC 对话里的文本。
2. 人在目标仓库根目录新开一个 Codex CLI 会话（`cd` 到 repo 根，而不是子目录，保证相对路径可解析）。
3. 会话的第一条指令固定为："读取 `{交接包路径}`，按其中的格式和 `codex-adapter/specs/{对应}.codex.md` 执行。" —— **不额外补充口头背景**，背景该写的都应该已经在交接包里。
4. Codex 完成后按各短卡"完成输出要求"给出结果。人把这段输出连同 diff 一起带回 CC 会话，作为 CC 后续判断（复核 / 写回状态 / 决定下一步）的输入。

也就是：交接包是**磁盘上的文件**，开场指令只做"指路"，不重复解释任务——这样才能验证 Codex 是否真的只靠文件化输入完成任务，而不是靠人在开场时口头补的上下文。

## 推荐试点顺序

1. 方法论仓结构化修改：验证 Codex 对 hact-method 文件体系的局部编辑能力。
2. 独立审查：验证 Codex 是否能只凭权威原文发现问题。
3. 单个 develop 任务：验证 Codex 是否能按任务包完成代码实现、测试和状态回写。
