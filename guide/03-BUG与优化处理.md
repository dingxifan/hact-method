# 情境：B 类任务——BUG 与功能优化

> 适用于：发现 BUG 或提出优化需求时的处理流程。  
> B 类任务无 Gate，随时可以开始，与当前迭代版本的进展无关。

---

## 什么是 B 类任务

项目上线后，会持续收到两类反馈：

- **BUG**：某个功能不对，需要修复
- **优化**：某个地方可以做得更好

只要不涉及"新用户场景、接口结构变更、跨模块重构"，就走 B 类流程。B 类不需要 PRD、不需要 TRD、不签 Gate——接到问题，派任务，修好，合并，等待下次统一部署。

如果一个"优化"越做越大，涉及了上述情况，就升级为 A 类，走一期完整流程。

---

## 流程图

```
收到 bug / 优化需求
      ↓
dispatch-new（判定 B/A + 写任务包入 b-queue）
      ↓
develop（source=bug / optimization；含独立审查 + 自合并到 master）
      ↓
deploy（合并部署 / hotfix 快速通道）
```

`urgency=hotfix` 时，PR 合并后立即单独部署，不等积累。

---

## § 1 派发任务（dispatch-new）

在项目根目录用 Claude Code 或 Codex 开新会话，说明收到 bug 报告或优化需求。当前运行时会先做 B/A 类判断。

### 先判断：B 类还是 A 类？

满足任意一条就升级 A 类，终止 dispatch-new，走 `draft-prd-vN` 流程：

| 情况 | 说明 |
|------|------|
| 需要新增或修改接口路径 / 参数 | 涉及 TRD 接口 schema 变更 |
| 需要修改数据库表结构或字段 | 涉及数据结构变更 |
| 影响两个以上模块的核心逻辑 | 跨模块重构 |
| 需要产品决策（新用户场景 / 新功能边界） | 超出已有 PRD 范围 |

**有疑问时倾向升级 A 类**——宁可多走流程，不遗漏产品决策。

---

### BUG 场景的信息收集

当前运行时会收集：

1. **现象描述**：看到了什么 / 期望是什么
2. **复现步骤**：最小复现路径
3. **已尝试的解决方案**（如有）
4. **最可能的修复方向**（如有判断）

复现步骤不明确时，当前运行时会先追问，不跳过。无法复现的 bug 在任务包 `known-risks` 中标注，不写"复现不明"的任务包。

---

### 优化场景的信息收集

当前运行时会收集：

1. **改进目标**：想达到什么效果
2. **当前状态**：基线指标（如"页面加载 3 秒"）
3. **验收标准**：怎么算做成了，需要可观测（如"响应时间 < 200ms"）

无量化验收标准时，当前运行时会先确认可观测的成功指标，再写任务包。

---

### 确定紧急程度

| 条件 | urgency |
|------|---------|
| 影响核心功能且用户无法绕过 | `hotfix` |
| 其余 | `normal` |

`hotfix` 任务包写完后，当前运行时立即提示通知相关开发者优先认领，不等积累。

---

### 任务包写入 queue

当前运行时写完整任务包，放入 `b-queue/{task-id}.md`，同时在 `b-tasks.md` 追加一行。`risk` 缺省按 `standard`；触及安全敏感四类时填 `sensitive`。

task-id 命名格式：`{项目缩写}-b-{三位序号}`，如 `hact-b-001`。

---

## § 2 开发（develop, source=bug / optimization）

认领任务后，在项目根目录开新会话，告诉当前运行时 task-id。流程与 A 类 develop 一致：

**AI 做 / 你做**

| AI（当前运行时）做 | 你做 |
|---|---|
| 写代码前做 freshness preflight，确认任务包、当前代码与 oracle 仍一致 | 提供复现环境（bug 场景） |
| 修复 / 优化代码，通过自检 | 确认修复结果符合验收标准 |
| 创建功能分支，推送 Gitee | — |
| 创建 PR，写 PR 描述 | — |

代码审查内化进 develop，同 A 类：首轮按契约、实际改动与适用规范做 full review；真实缺陷整改后只对稳定 finding id、反例和受影响回归做 targeted review。只有改动使先前结论广泛失效且无法局部验证时才升级 full。每轮固定 Git tree/diff 并落报告，问题及处置只在报告维护；`status.yml` 保存结论、报告索引、轮次与时间。通过通用 review 审计后由 develop 自合并到 master。

---

## § 3 部署

### 常规合并部署

`urgency=normal` 的 B 类任务合并后，积累到一定程度由有 dispatch 权限的成员发起合并部署——A 类迭代 + 所有待部署 B 类任务一起上线，一次性部署。

### hotfix 快速通道

`urgency=hotfix` 时，PR 合并后立即部署，不等其他任务积累：

1. 当前运行时通过已预检可用的远端命令通道连接服务器
2. 拉取最新代码，执行构建
3. 重启服务（pm2 / nginx）
4. curl 健康检查端点，确认服务正常
5. 写入部署日志

---

## B 类积累管理

`b-tasks.md` 是 B 类任务的统一账本，每行一个任务：

```
| {task-id} | {类型} | {urgency} | {标题} | {状态} | {日期} |
```

状态流转：`[可取]` → `[taken-by 姓名]` → `[merged]`

同一 bug 被多次报告时，当前运行时先查 `b-tasks.md` 是否已有对应条目——有则在已有任务包 `known-risks` 追加频次备注，不新建任务包。

---

## 升级 A 类的时机

如果开始修复后发现比预想复杂：

1. develop 执行人将任务包回退到 `[可取]`，写明升级原因
2. 由 dispatch 判断是否升级 A 类（走 `draft-prd-vN` 流程）

不要在 B 类任务里悄悄扩大改动范围——发现复杂就上报，走对流程。
