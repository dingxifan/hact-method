# 情境：A 类主线——一期完整流程

> 适用于：一个迭代版本（v1、v2……）从需求到上线的完整过程。  
> 前置：项目已初始化（见 `01-启动新项目.md`）。

---

## 全局流程图

```
§1 编排阶段
  draft-prd-vN ──→ [G1]
  draft-tech-design ──→ [G2]
  plan-sprint ──→ [G3] ──→ queue/ 任务就绪
        ↓
§2 开发循环（可多人并行）
  develop（写码 → per-task 独立审查 → 全量绿 → 自合并到 master）
        ↓
§3 联调与验收
  integration-verify（系统语义独审 + runtime 联调）→ 失败修复 → 全部闭合
  manual-test ──→ [G4]
        ↓
§4 收尾部署（可并行）
  deploy
  wrap-up-iteration ──→ [G5]
```

每个阶段结束时都有一个 Gate 作为确认点，签署状态记在 `status.yml iterations.vN.gates`。

---

## § 1 编排阶段

> **目标**：把"我们要做什么"变成"每个人知道自己要做什么"。

### 1.1 写 PRD（draft-prd-vN → G1）

**做什么**：把本期要做的功能写成结构化的产品需求文档，包含用户故事、验收标准、业务约束。

**AI 做 / 你做**

| AI（Codex）做 | 你做 |
|---|---|
| 从背景描述中起草 PRD 框架 | 提供需求背景和目标 |
| 补全用户故事和验收标准（AC） | 审核 AC 是否准确反映预期 |
| 指出需求模糊或遗漏的地方 | 澄清歧义，拍板边界 |
| 在文档末尾询问是否签 G1 | 确认签字，授权进入技术设计 |

**开始方式**：在项目根目录用 Codex 开新会话，告诉Codex你要写这期的 PRD，描述背景和目标。它会按共同启动协议读取状态并加载 PRD 规范。

**产物**：`iterations/v1/prd.md` 完整版，G1 写入 `status.yml iterations.v1.gates.G1`。

---

### 1.2 写技术方案（draft-tech-design → G2）

有新页面或核心交互时先做 draft-ux：先说清用户要办成什么、从哪里开始、怎样知道已完成，再设计跨功能动线与页面。Codex 先实际验证主路径、失败/取消/恢复，再让你按真实任务评价体验。页面可承接多个功能；AC 映射负责查漏，不要求每功能单独一页。TRD、开发包与集成验收继续引用同一 U/S 动线。

**做什么**：设计本期的技术实现方案，产出 TRD（接口定义 + 数据结构）及其验证入口。

**AI 做 / 你做**

| AI（Codex）做 | 你做 |
|---|---|
| 从 PRD 推导 API 接口和数据库表结构 | 审核技术方案是否可行 |
| 核对项目技术选择、不变量与验证入口 | 补充架构决策和特殊约束 |
| 识别技术风险和依赖关系 | 拍板关键技术选型 |
| 在文档末尾询问是否签 G2 | 确认签字，授权拆 sprint |

**开始方式**：开新会话，说明 PRD 已签、要开始技术方案。Codex会读取 PRD，引导你完成 TRD 和项目约束。

**产物**：`iterations/v1/trd.md`（迭代内）+ project.md 的技术选择与验证入口，G2 签字。

> **存量项目迁移**：升级到本版前，逐仓确认并用独立 worktree 核对三个旧 Standards。通用教程和有完整机械承接的重复散文直接退役；独有的安全/数据不变量归 Foundation，项目选择归 project.md，本期契约归 PRD/TRD/design，任务禁区归 do-not，命令归脚本与项目说明。按现有修订/确认流程处理真实语义冲突；不把三份全文搬到另一个文件。
> 一次性处置依据写现有 decisions 或升级 PR，列必要承接锚及主动放弃的软性约束。更新活跃任务的 reference/do-not、方法论入口与检查器后再删除旧文件；历史报告、已完成任务与既有测试/类型/lint 保留。不批量重写历史审查字段；新报告不再生成 relevant-standards/standards_checked，也不增加替代字段。验证失败或独有约束尚无归属时，项目保持原方法论版本，保留在制品。

---

### 1.3 拆 Sprint（plan-sprint → G3）

**做什么**：将 TRD 和项目约束 拆解为开发者可直接执行的任务包，放入 queue。

**AI 做 / 你做**

| AI（Codex）做 | 你做 |
|---|---|
| 从 TRD 拆出前端/后端任务包 | 确认拆分粒度合理 |
| 为每个任务写完成判据和依赖关系 | 确认任务边界无遗漏 |
| 生成 sprint.md 概览 | 检查是否有并行冲突 |
| 将任务包写入 `queue/` | 确认成员与任务类型的对应关系 |
| 询问是否签 G3 | 确认签字，开发可以开始 |

**开始方式**：开新会话，说明技术方案已确认、现在拆 sprint。Codex会读取 TRD 和项目约束，开始拆任务包。

**产物**：`iterations/v1/queue/` 下若干任务包文件 + `sprint.md`，G3 签字。

---

## § 2 开发循环

> **目标**：把任务包变成合并进主分支的代码。可多人并行，互不阻塞。

### 2.1 开发者认领任务

**开始前**：看 `iterations/vN/sprint.md`（或 `status.yml` 的 `tasks[]`），确认哪些任务 `status` 为「可取」（无人认领 = 可以拿）。

在项目根目录开新会话，告诉Codex你要认领哪个任务（说任务名或 task-id）。它会自行读取任务包，确认边界和完成判据后开始工作。此时该任务在 `status.yml` 的状态变为 `taken-by`，记录认领人。

---

### 2.2 写代码（develop）

**AI 做 / 你做**

| AI（Codex）做 | 你做 |
|---|---|
| 读取 TRD 和项目约束，按规范写代码 | 回答实现过程中的业务判断 |
| 自检：调用 simplify skill 检查冗余 | 确认实现符合预期 |
| 创建功能分支，推送到 Gitee | — |
| 创建 PR，写 PR 描述 | — |

**产物**：Gitee 上一个带完整描述的 PR。

---

### 2.3 内置独立审查 + 自合并（无独立 pr-review）

> 代码审查**内化进 develop**：写码前先做 freshness preflight；每个任务首次派**全新隔离上下文的隔离审查单元**，standard 做 lightweight Error Containment，sensitive 或实际 diff 升档的包做 full-local。真实代码/机制阻断修复后只做 targeted review；规格、示例、证据与 scope 问题按类型改文档、补证据或另开 owner。只记录发现、必要证据和未完成验证。整批通过 + 末端全量绿后，develop **自己把 PR 合并到 master**；最终 System Assurance 由 `integration-verify` 承接。

**AI 做 / 你做**

| AI（Codex）做 | 你做 |
|---|---|
| freshness preflight + policy-selected package review / 整改 targeted 独立审查 | 一般无需介入——全自动跑；问题与处置在逐轮报告留痕，同一根因不按语法变体重复开 blocker |
| 末端全量绿 + 自合并到 master + 写逐轮报告与证据索引 | **唯一例外**：安全敏感改动（权限/认证/数据隔离）由用户或其明确指定审批人裁决后再合并 |

> **为什么 PR 还在、CR 却自动了？** PR 仍是有据可查的记录（改了什么、为什么、独审结论）——出问题可追溯、新人可了解历史。区别是：质量把关从"另一个人开会话复审"变成"develop 内置隔离审查单元即时审 + 自合并"。**治理代价**：master 写入少了第二个人工门（仅安全敏感改动保留），这是明确接受的取舍——团队引入期若需要可恢复独立 merge 门。

---

### 2.4 重复直到 sprint 完成

所有任务包从 `queue/` 流入 `queue/done/`，sprint 完成。

---

## § 3 System Verification 与验收

> **目标**：先对 final system candidate 完成整体语义独审与真实 runtime 验证，闭合全部 system finding；再由用户完成产品体验验收。

### 3.1 System Verification（integration-verify）

在项目根目录按Codex入口开新 AI 会话：

```
integration-verify
```

**AI 做 / 你做**

| AI 做 | 你做 |
|---|---|
| 固定 final system candidate，执行 Fresh Isolated System Full Independent Review | 仅在出现产品/技术 Contract 取舍或其他 Human Authority 边界时裁决 |
| 按用户任务和本期契约执行真实 runtime 路径、失败/重试/恢复与适用外部边界 | 对付费、真实凭据、外部写入等动作决定是否授权 |
| 把 blocking finding 路由为 `local-close` 或 `system-rereview` | — |
| `local-close` 走局部修复、Fresh Isolated Local Review 与声明 revalidation；越界即 escalation | — |
| `system-rereview` 根据 invalidation scope 做 targeted 或 full System Reviewer event | — |
| 持久化 immutable review/finding 与 additive closure evidence，全部 obligation 闭合后完成 | — |

---

### 3.2 人工验收（manual-test → G4）

System Verification 两条 lane 全部满足、blocking findings 全部合法关闭后，进行人工验收：

```
manual-test
```

**AI 做 / 你做**

| AI（Codex）做 | 你做 |
|---|---|
| 从 PRD 生成验收场景清单 | 逐条在浏览器/App 里操作验证 |
| 记录每条验收结果 | 发现问题时描述复现步骤 |
| 将未通过项生成 develop(source=manual-test) 任务包 | 修复完成后重新验收 |
| 全部通过后询问是否签 G4 | 确认签字，授权部署 |

**G4 签字**：意味着产品质量已确认，代码准备上线。

---

## § 4 收尾部署

> **目标**：把通过验收的代码上线，完成本期迭代的文档收尾。  
> 部署和迭代收尾可以**并行**进行，互不阻塞。

### 4.1 部署（deploy）

```
deploy，target: prod
```

**AI 做 / 你做**

| AI（Codex）做 | 你做 |
|---|---|
| 通过已预检可用的远端命令通道连接服务器 | 确认部署窗口和时机 |
| 拉取最新代码，执行构建 | — |
| 重启服务（pm2 / nginx） | 验证线上功能正常 |
| 执行健康检查（curl health 等），记录部署日志 | 确认上线结果 |

---

### 4.2 迭代收尾（wrap-up-iteration → G5）

```
wrap-up-iteration，version: v1
```

Codex 核对实际偏离、欠账与项目事实，最后由用户确认 G5：

**第一步：偏离对账**  
对比最终代码与 PRD/TRD 的差异，将偏离记录写入 `backlog.md`，必要时反向更新文档。

**第二步：必要缺口与经验分开**

本期承诺缺口必须闭合或由用户明确调整范围；其他遗留给去向与理由。经验可留 feedback 或 PR，不要求清空、誊入私人 notes 或收割。

**第三步：更新 project.md**  
将本期完成的功能、技术决策和已知风险合并进 `project.md`，作为下一期的基础。

完成后，Codex询问是否签 G5，签字后本期迭代正式关闭。

---

## 一期完成后

下一期从 `draft-prd-v2` 开始，流程相同。上一期沉淀的 `project.md`、`decisions.md`、`reusables.md` 自动成为下一期的上下文——积累不会消失，每期都在前一期的基础上往前走。
