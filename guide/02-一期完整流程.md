# 情境：A 类主线——一期完整流程

> 适用于：一个迭代版本（v1、v2……）从需求到上线的完整过程。  
> 前置：项目已初始化（见 `01-启动新项目.md`）。

---

## 全局流程图

```
§1 编排阶段
  draft-prd-vN ──→ [G1]
  draft-tech-design ──→ [G2]
  plan-sprint ──→ [G3] ──→ queue/ 任务就绪
        ↓
§2 开发循环（可多人并行）
  develop（写码 → per-task 独立审查 → 全量绿 → 自合并到 master）
        ↓
§3 联调与验收
  integration-verify（系统语义独审 + runtime 联调）→ 失败修复 → 全部闭合
  manual-test ──→ [G4]
        ↓
§4 收尾部署（可并行）
  deploy
  wrap-up-iteration ──→ [G5]
```

每个阶段结束时都有一个 Gate 作为确认点，签署状态记在 `status.yml iterations.vN.gates`。

跨 ChatGPT、用户人工搬运与 Codex 的 repository 边界统一使用：`BASE_SHA → Execution Packet / 文件 → Codex execution → RESULT_SHA → ChatGPT re-read`。大正文和多文件内容走文件，Packet 只保留 repository、SHA、范围、执行与验证控制信息。Gate 和真实体验接受均绑定明确 Accepted snapshot。

---

## § 1 编排阶段

> **目标**：把"我们要做什么"变成"每个人知道自己要做什么"。

### 1.1 写 PRD（draft-prd-vN → G1）

**做什么**：把本期要做的功能写成结构化的产品需求文档，包含用户故事、验收标准、业务约束。

**AI 做 / 你做**

| AI（ChatGPT / Codex，按职责）做 | 你做 |
|---|---|
| 从背景描述中起草 PRD 框架 | 提供需求背景和目标 |
| 补全用户故事和验收标准（AC） | 审核 AC 是否准确反映预期 |
| 指出需求模糊或遗漏的地方 | 澄清歧义，拍板边界 |
| Codex 落盘、检查后，ChatGPT 复读 final snapshot 并准备 G1 | 对明确 Accepted snapshot 确认 G1，授权进入技术设计 |

**开始方式**：ChatGPT 基于明确 `BASE_SHA` 形成 PRD 内容；PRD 文件与短 Packet 交给 Codex 落盘、检查、独审和机械闭环。Codex 返回 `RESULT_SHA` 后，ChatGPT 复读 final PRD，再由用户对明确 Accepted snapshot 作 G1。

**产物**：`iterations/v1/prd.md` 完整版，G1 写入 `status.yml iterations.v1.gates.G1`。

---

### 1.2 写技术方案（draft-tech-design → G2）

有新页面或核心交互时先做 draft-ux：先说清用户要办成什么、从哪里开始、怎样知道已完成，再设计跨功能动线与页面。ChatGPT 可形成设计内容；Codex 负责实际验证主路径、失败/取消/恢复，再让你按真实任务评价体验。页面可承接多个功能；AC 映射负责查漏，不要求每功能单独一页。TRD、开发包与集成验收继续引用同一 U/S 动线。

**做什么**：设计本期的技术实现方案，产出 TRD（接口定义 + 数据/非表承载结构）及其验证入口；固定候选后完成独立审查和 task-specific completion check。

**AI 做 / 你做**

| AI（ChatGPT / Codex，按职责）做 | 你做 |
|---|---|
| 从 PRD 推导 API 接口和数据库表结构 | 审核技术方案是否可行 |
| 核对项目技术选择、不变量与验证入口 | 补充架构决策和特殊约束 |
| 识别技术风险和依赖关系 | 拍板关键技术选型 |
| 固定候选、完成 Fresh Independent Review，并运行 `check-task-completion` | 针对明确 Accepted snapshot 确认是否签 G2，授权拆 sprint |

**开始方式**：ChatGPT 基于 `BASE_SHA` 形成 TRD 与项目约束内容；TRD 文件和短 Packet 交给 Codex 验证、落盘、独审和机械闭环。ChatGPT 重新读取 `RESULT_SHA` 后，用户才对明确 Accepted snapshot 作 G2。

**产物**：`iterations/v1/trd.md`、`iterations/v1/document-reviews/{task-id}/round-NN.md`（迭代内）+ project.md 的技术选择与验证入口。`draft-tech-design merged` 与 G2 人签分开记录。

> 项目必须完整安装当前 Method；不在运行时解释旧 Standards 或旧 schema。
> 一次性处置依据写现有 decisions 或升级 PR，列必要承接锚及主动放弃的软性约束。更新活跃任务的 reference/do-not、方法论入口与检查器后再删除旧文件；历史报告、已完成任务与既有测试/类型/lint 保留。不批量重写历史审查字段；新报告不再生成 relevant-standards/standards_checked，也不增加替代字段。验证失败或独有约束尚无归属时，项目保持原方法论版本，保留在制品。

---

### 1.3 拆 Sprint（plan-sprint → G3）

**做什么**：将 TRD 和项目约束 拆解为开发者可直接执行的任务包，放入 queue。

**AI 做 / 你做**

| AI（ChatGPT / Codex，按职责）做 | 你做 |
|---|---|
| ChatGPT 可形成拆分语义、任务边界、ownership 与依赖；Codex 以真实仓库事实对账、落盘、运行 `check-sprint`、独审和机械整改 | 确认拆分粒度、边界和并行取舍 |
| Codex 将已确定的任务包写入 `queue/` 并交付 Git 结果 | 对明确 Accepted planning snapshot 确认 G3，开发可以开始 |

**开始方式**：ChatGPT 可先在明确 `BASE_SHA` 上完成 planning 内容；多个 Task Package 走文件 / bundle，Packet 只描述控制信息。Codex 对照真实 repository facts 落盘与验证；若事实使既定边界或 ownership 失效，返回 semantic issue，不擅自重做规划。

**产物**：`iterations/v1/queue/` 下若干任务包文件 + `sprint.md`，G3 签字。

---

## § 2 开发循环

> **目标**：把任务包变成合并进主分支的代码。可多人并行，互不阻塞。

### 2.1 开发者认领任务

**开始前**：看 `iterations/vN/sprint.md`（或 `status.yml` 的 `tasks[]`），确认哪些任务 `status` 为「可取」（无人认领 = 可以拿）。

在项目根目录进入 Codex，说明要认领哪个任务（任务名或 task-id）。Codex 自行读取任务包，确认边界、完成判据和 freshness 后开始工作；不需要把每个机械开发步骤送回 ChatGPT。此时该任务在 `status.yml` 的状态变为 `taken-by`，记录认领人。

---

### 2.2 写代码（develop）

对于一个已签 Sprint，Sprint 保留完整 Develop scope；ChatGPT 每次基于明确 `BASE_SHA`、已完成 / 剩余包、依赖、工作量、复杂度与验证边界，只决定下一个 bounded execution window。它输出两段内容：第一段是可直接输入 Codex 的 `/goal ...`，第二段才是 Develop Execution Packet；Goal 不是大 Task，也不替代每个 Task Package，更不要求一个 Codex interaction 完成整个 Sprint。

**用户操作**：

1. ChatGPT 先生成 `/goal ...`；
2. 用户先把这条 `/goal` 单独输入 Codex；
3. 确认 Goal 已建立；
4. 再粘贴 Develop Execution Packet；
5. 此后 Codex 只在该 Goal 下完成当前窗口明确列出的包；窗口结果返回 ChatGPT 后，由 ChatGPT 重新读取 Git Truth 决定下一窗口。

**AI 做 / 你做**

| AI（Codex）做 | 你做 |
|---|---|
| 读取 TRD 和项目约束，按规范写代码 | 回答实现过程中的业务判断 |
| 自检：调用 simplify skill 检查冗余 | 确认实现符合预期 |
| 按项目 Git policy 创建分支、提交、推送或合并 | — |

**产物**：Gitee 上一个带完整描述的 PR。

Codex 连续完成当前 execution window：每个 in-scope Task 自己完成 freshness、开发、测试、独审、修复和合并；普通工程问题自行闭环。Codex 在窗口内按依赖、工作量、耦合和验证边界组织一个或多个轻量 Wave；Wave 与 window 都不是 Task、Gate、状态或持久化对象。到达 complex Task 时只问一次 `analyze first | continue directly`；无回复只等待用户下一条明确选择，不轮询、不重复提问，也不自行宣布暂停或 blocker。需要 Human Authority 时，Codex 直接在当前交互中询问用户，决定后继续原 Goal。一个局部 blocker 只暂停该包及其窗口内依赖；窗口完成或提前停止后，Codex 返回 `RESULT_SHA`，ChatGPT 重新读取 Git truth 并决定下一窗口。

---

### 2.3 内置独立审查 + 自合并（无独立 pr-review）

> 代码审查**内化进 develop**：写码前先做 freshness preflight；每个任务首次派**全新隔离上下文的隔离审查单元**，standard 做 lightweight Error Containment，sensitive 或实际 diff 升档的包做 full-local。真实代码/机制阻断修复后只做 targeted review；规格、示例、证据与 scope 问题按类型改文档、补证据或另开 owner。只记录发现、必要证据和未完成验证。整批通过 + 末端全量绿后，develop **自己把 PR 合并到 master**；最终 System Assurance 由 `integration-verify` 承接。

**AI 做 / 你做**

| AI（Codex）做 | 你做 |
|---|---|
| freshness preflight + policy-selected package review / 整改 targeted 独立审查 | 一般无需介入——全自动跑；问题与处置在逐轮报告留痕，同一根因不按语法变体重复开 blocker |
| 末端全量绿 + 自合并到 master + 写逐轮报告与证据索引 | **唯一例外**：安全敏感改动（权限/认证/数据隔离）由用户或其明确指定审批人裁决后再合并 |

> **为什么 PR 还在、CR 却自动了？** PR 仍是有据可查的记录（改了什么、为什么、独审结论）——出问题可追溯、新人可了解历史。区别是：质量把关从"另一个人开会话复审"变成"develop 内置隔离审查单元即时审 + 自合并"。**治理代价**：master 写入少了第二个人工门（仅安全敏感改动保留），这是明确接受的取舍——团队引入期若需要可恢复独立 merge 门。

---

### 2.4 重复直到 sprint 完成

所有任务包从 `queue/` 流入 `queue/done/`，sprint 完成。

---

## § 3 System Verification 与验收

> **目标**：先对 final system candidate 完成整体语义独审与真实 runtime 验证，闭合全部 system finding；再由用户完成产品体验验收。

### 3.1 System Verification（integration-verify）

在项目根目录进入 Codex，以明确 final system candidate SHA 执行：

```
integration-verify
```

**AI 做 / 你做**

| AI 做 | 你做 |
|---|---|
| 固定 final system candidate，执行 Fresh Isolated System Full Independent Review；如 ChatGPT 参与 system-level semantic judgement，也只读取 fixed candidate / reports | 仅在出现产品/技术 Contract 取舍或其他 Human Authority 边界时裁决 |
| 按用户任务和本期契约执行真实 runtime 路径、失败/重试/恢复与适用外部边界 | 对付费、真实凭据、外部写入等动作决定是否授权 |
| 为 blocking finding 形成新 fixed candidate，并用 targeted/full Fresh Review report 关闭 | — |
| 持久化 immutable review report chain，latest report 无 open finding 后完成 | — |

---

### 3.2 人工验收（manual-test → G4）

System Verification 两条 lane 全部满足、blocking findings 全部合法关闭后，进行人工验收：

```
manual-test
```

**AI 做 / 你做**

| AI（ChatGPT / Codex，按职责）做 | 你做 |
|---|---|
| ChatGPT 可帮助组织验收场景、解释 PRD evidence 与分类反馈；Codex 负责真实 repository / environment mechanics、持久化与修复链 | 逐条在浏览器/App 里操作验证；发现问题时描述复现步骤 |
| Codex 将未通过项生成 develop(source=manual-test) 任务包 | 修复后只复测受影响范围 |
| Codex 持久化 acceptance 结果 | 对明确 implementation snapshot 确认 G4，授权部署 |

**G4 签字**：意味着产品质量已确认，代码准备上线。

---

## § 4 收尾部署

> **目标**：把通过验收的代码上线，完成本期迭代的文档收尾。  
> 部署和迭代收尾可以**并行**进行，互不阻塞。

### 4.1 部署（deploy）

```
deploy，target: prod
```

**AI 做 / 你做**

| AI（Codex）做 | 你做 |
|---|---|
| 通过已预检可用的远端命令通道连接服务器 | 确认部署窗口和时机 |
| 对已授权的 exact deploy snapshot 执行构建与部署 | — |
| 重启服务（pm2 / nginx） | 验证线上功能正常 |
| 执行健康检查（curl health 等），记录部署日志 | 确认上线结果 |

---

### 4.2 迭代收尾（wrap-up-iteration → G5）

```
wrap-up-iteration，version: v1
```

Codex 核对实际偏离、欠账与项目事实，最后由用户确认 G5：

**第一步：偏离对账**  
对比最终代码与 PRD/TRD 的差异，将偏离记录写入 `backlog.md`，必要时反向更新文档。

**第二步：必要缺口与经验分开**

本期承诺缺口必须闭合或由用户明确调整范围；其他遗留给去向与理由。经验可留 feedback 或 PR，不要求清空、誊入私人 notes 或收割。

**第三步：更新 project.md**  
将本期完成的功能、技术决策和已知风险合并进 `project.md`，作为下一期的基础。

ChatGPT 可辅助分析偏离、debt / defer 与 G5 decision preparation；Codex 从明确 `BASE_SHA` 重新读取 durable facts、持久化 closeout 并完成检查。用户对明确 Accepted closeout snapshot 确认 G5，签字后本期迭代正式关闭。

---

## 一期完成后

下一期从 `draft-prd-v2` 开始，流程相同。上一期沉淀的 `project.md`、`decisions.md`、`reusables.md` 自动成为下一期的上下文——积累不会消失，每期都在前一期的基础上往前走。
