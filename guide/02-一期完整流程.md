# 情境：A 类主线——一期完整流程

> 适用于：一个迭代版本（v1、v2……）从需求到上线的完整过程。  
> 前置：项目已初始化（见 `01-启动新项目.md`）。

---

## 全局流程图

```
§1 编排阶段
  draft-prd-vN ──→ [G1]
  draft-tech-design ──→ [G2]
  plan-sprint ──→ [G3] ──→ queue/ 任务就绪
        ↓
§2 开发循环（可多人并行）
  develop（写码 → per-task 独立审查 → 全量绿 → PR 合并到 Accepted branch）
        ↓
§3 联调与验收
  integration-verify（系统语义独审 + runtime 联调）→ 失败修复 → 全部闭合
  manual-test ──→ [G4]
        ↓
§4 收尾部署（可并行）
  deploy
  wrap-up-iteration ──→ [G5]
```

每个阶段结束时都有一个 Gate 作为确认点，签署状态记在 `status.yml iterations.vN.gates`。

项目工作默认在 Codex 中连续完成，ChatGPT Work 按需使用；Codex 直接任务不额外制作往返材料。真实跨入口统一使用：`BASE_SHA → Execution Packet / 文件 → Codex execution → RESULT_SHA → ChatGPT re-read`。大正文和多文件内容走文件，Packet 只保留 repository、SHA、范围、执行与验证控制信息。Gate 和真实体验接受均绑定明确 Accepted snapshot。

---

## § 1 编排阶段

> **目标**：把"我们要做什么"变成"每个人知道自己要做什么"。

### 1.1 写 PRD（draft-prd-vN → G1）

**做什么**：把本期要做的功能写成结构化的产品需求文档，包含用户故事、验收标准、业务约束。

**AI 做 / 你做**

| AI（ChatGPT / Codex，按职责）做 | 你做 |
|---|---|
| 从背景描述中起草 PRD 框架 | 提供需求背景和目标 |
| 补全用户故事和验收标准（AC） | 审核 AC 是否准确反映预期 |
| 指出需求模糊或遗漏的地方 | 澄清歧义，拍板边界 |
| 固定 final candidate、完成检查与独审；用户批准后继续完成 PR / merge、Task state 与 G1 record 持久化 | 对明确 final PRD snapshot 确认一次 G1，授权进入技术设计 |

**开始方式**：Codex 可直接基于当前 Git truth 澄清需求并形成 PRD；按需从 Work 交接时绑定明确 `BASE_SHA` 与完整文件 / Brief。PRD candidate 固定并通过检查 / 独审后，用户对该明确 snapshot 作一次 G1。只要后续 delivery 不改变 PRD 语义，Codex 连续完成 PR / merge、Task `merged` 与 G1 record；如果 Task 已先行 merged 而 G1 尚未批准，再对 Accepted snapshot 取得一次 G1 即可。

**产物**：`iterations/v1/prd.md` 完整版，G1 写入 `status.yml iterations.v1.gates.G1`。

---

### 1.2 写技术方案（draft-tech-design → G2）

有新页面或核心交互时先做 draft-ux：先说清用户要办成什么、从哪里开始、怎样知道已完成，再设计跨功能动线与页面。Codex 可连续完成 UX 设计、原型和主路径、失败/取消/恢复的真实验证，再让你按真实任务评价体验；Work 按需参与设计。页面可承接多个功能；AC 映射负责查漏，不要求每功能单独一页。TRD、开发包与集成验收继续引用同一 U/S 动线。

**做什么**：设计本期的技术实现方案，产出 TRD（接口定义 + 数据/非表承载结构）及其验证入口；固定候选后完成独立审查和 task-specific completion check。

**AI 做 / 你做**

| AI（ChatGPT / Codex，按职责）做 | 你做 |
|---|---|
| 从 PRD 推导 API 接口和数据库表结构 | 审核技术方案是否可行 |
| 核对项目技术选择、不变量与验证入口 | 补充架构决策和特殊约束 |
| 识别技术风险和依赖关系 | 拍板关键技术选型 |
| 固定候选、完成 Fresh Independent Review，并运行 `check-task-completion`；用户批准后继续完成 PR / merge 与 Gate 持久化 | 针对明确 final TRD snapshot 确认一次 G2，授权拆 sprint |

**开始方式**：Codex 可直接比较技术方案并形成 TRD 与项目约束内容，必要取舍由用户决定；按需从 Work 交接时绑定 `BASE_SHA` 与完整文件 / Brief。fixed candidate 完成验证和独审后，用户对该明确 snapshot 作一次 G2。只要后续 delivery 不改变 TRD / related project truth 的语义，Codex 连续完成 PR / merge、Task `merged` 与 G2 record；若 Task 已先行 merged 而 G2 尚未批准，再对 Accepted snapshot 取得一次 G2 即可。

**产物**：`iterations/v1/trd.md`、`iterations/v1/document-reviews/{task-id}/round-NN.md`（迭代内）+ project.md 的技术选择与验证入口。Task lifecycle 与 G2 authority 分开记录，但同一 snapshot 不要求两次用户确认。

> 项目必须完整安装当前 Method；不在运行时解释旧 Standards 或旧 schema。
> 一次性处置依据写现有 decisions 或升级 PR，列必要承接锚及主动放弃的软性约束。更新活跃任务的 reference/do-not、方法论入口与检查器后再删除旧文件；历史报告、已完成任务与既有测试/类型/lint 保留。不批量重写历史审查字段；新报告不再生成 relevant-standards/standards_checked，也不增加替代字段。验证失败或独有约束尚无归属时，项目保持原方法论版本，保留在制品。

---

### 1.3 拆 Sprint（plan-sprint → G3）

**做什么**：将 TRD 和项目约束 拆解为开发者可直接执行的任务包，放入 queue。

**AI 做 / 你做**

| AI（ChatGPT / Codex，按职责）做 | 你做 |
|---|---|
| Codex 可连续完成拆分语义、任务边界、ownership 与依赖，再以真实仓库事实对账、落盘、运行 `check-sprint`、独审和整改；Work 按需参与 | 确认拆分粒度、边界和并行取舍 |
| Codex 将已确定的任务包写入 `queue/`、固定 planning candidate；用户批准后继续完成 PR / merge 与 G3 record | 对明确 planning snapshot 确认一次 G3，开发可以开始 |

**开始方式**：Codex 可直接完成整体规划、工程拆包及收口；仅真实从 Work 交接时基于明确 `BASE_SHA` 交付完整规划意图文件 / bundle 与简短 Brief，Packet 只描述控制信息。Codex 对照真实 repository facts 落盘、运行 `check-sprint` 并完成独审；用户对 final planning snapshot 批准 G3 后，只要内容语义不变，PR / merge、plan-sprint `merged` 与 Gate record 连续完成。若事实使既定边界或 ownership 失效，返回 semantic issue，不擅自重做规划。

**产物**：`iterations/v1/queue/` 下若干任务包文件 + `sprint.md`，G3 签字。

---

## § 2 开发循环

### 2.1 认领与开始

在项目根向 Codex 指明 task-id。登记为“可取”只表示尚未认领；Codex 还须核 G3、依赖、授权、能力及 freshness，再按 `tasks/develop.md` 认领。不能只看文件所在目录判断当前状态。

### 2.2 当前窗口

当前入口依据最新 Git truth 与已有授权确定下一有界窗口。Codex 直接任务在当前环境建立并实际激活 Goal，再自主完成窗口内工作；仅真实从 Work 交接时按 `runtime/chatgpt.md` §3 先激活 Goal 再交 Develop Execution Packet。执行 / 返回边界见 `runtime/codex.md` §5，窗口和 Wave 约束见 `tasks/develop.md` §5.9。

用户只处理必要的产品/技术取舍与 Human Authority，不负责逐包排序、维护 Wave 或搬运中间 reasoning。普通失败由 Codex 在原范围修复，完成后说明 RESULT_SHA；当前入口核 Git truth 与授权后判断下一有界窗口。仅真实跨入口才返回来源会话并由接收方回读。

### 2.3 独审与交付

每包有固定候选与 Fresh Independent Review，Package Review 不代替最终 System Assurance。正常已授权交付走 source branch → PR → merge → 核 Accepted SHA，不绕过 PR；敏感边界与其他必要授权依当前 Contract/Authority。

PR 保留变更与独审证据，develop 可按仓库策略自合并，不另设 pr-review Task。详细完成条件及复审范围读 `tasks/develop.md` 与 `protocols/review.md`，不在导读复制另一套审查流程。

### 2.4 Sprint 完成

按 Accepted status 和每包完成条件判断，不从 queue/done 文件移动或聊天总结推导。全部计划内 develop 完成后进入 System Verification。

---

## § 3 System Verification 与验收

> **目标**：先对 final system candidate 完成整体语义独审与真实 runtime 验证，闭合全部 system finding；再由用户完成产品体验验收。

### 3.1 System Verification（integration-verify）

在项目根目录进入 Codex，以明确 final system candidate SHA 执行：

```
integration-verify
```

**AI 做 / 你做**

| AI 做 | 你做 |
|---|---|
| 固定 final system candidate，执行 Fresh Isolated System Full Independent Review；如 ChatGPT 参与 system-level semantic judgement，也只读取 fixed candidate / reports | 仅在出现产品/技术 Contract 取舍或其他 Human Authority 边界时裁决 |
| 按用户任务和本期契约执行真实 runtime 路径、失败/重试/恢复与适用外部边界 | 对付费、真实凭据、外部写入等动作决定是否授权 |
| 为 blocking finding 形成新 fixed candidate，并用 targeted/full Fresh Review report 关闭 | — |
| 持久化 immutable review report chain，latest report 无 open finding 后完成 | — |

---

### 3.2 人工验收（manual-test → G4）

System Verification 两条 lane 全部满足、blocking findings 全部合法关闭后，进行人工验收：

```
manual-test
```

**AI 做 / 你做**

| AI（ChatGPT / Codex，按职责）做 | 你做 |
|---|---|
| ChatGPT 可帮助组织验收场景、解释 PRD evidence 与分类反馈；Codex 负责真实 repository / environment mechanics、持久化与修复链 | 逐条在浏览器/App 里操作验证；发现问题时描述复现步骤 |
| Codex 将未通过项生成 develop(source=manual-test) 任务包 | 修复后只复测受影响范围 |
| Codex 持久化 acceptance 结果 | 对明确 implementation snapshot 确认 G4，授权部署 |

**G4 签字**：意味着产品质量已确认，代码准备上线。

---

## § 4 收尾部署

> **目标**：把通过验收的代码上线，完成本期迭代的文档收尾。  
> 部署和迭代收尾可以**并行**进行，互不阻塞。

### 4.1 部署（deploy）

```
deploy，target: prod
```

**AI 做 / 你做**

| AI（Codex）做 | 你做 |
|---|---|
| 通过已预检可用的远端命令通道连接服务器 | 确认部署窗口和时机 |
| 对已授权的 exact deploy snapshot 执行构建与部署 | — |
| 重启服务（pm2 / nginx） | 验证线上功能正常 |
| 执行健康检查（curl health 等），记录部署日志 | 确认上线结果 |

---

### 4.2 迭代收尾（wrap-up-iteration → G5）

```
wrap-up-iteration，version: v1
```

Codex 核对实际偏离、欠账与项目事实，最后由用户确认 G5：

**第一步：偏离对账**  
对比最终代码与 PRD/TRD 的差异，将偏离记录写入 `backlog.md`，必要时反向更新文档。

**第二步：必要缺口与经验分开**

本期承诺缺口必须闭合或由用户明确调整范围；其他遗留给去向与理由。经验可留 feedback 或 PR，不要求清空、誊入私人 notes 或收割。

**第三步：更新 project.md**  
将本期完成的功能、技术决策和已知风险合并进 `project.md`，作为下一期的基础。

ChatGPT 可辅助分析偏离、debt / defer 与 G5 decision preparation；Codex 从明确 `BASE_SHA` 重新读取 durable facts、形成并检查 fixed closeout snapshot。用户对该明确 snapshot 确认一次 G5；只要后续持久化不改变 closeout 语义，wrap-up `merged`、G5 record 与 iteration closed 连续完成，不再重复确认。

---

## 一期完成后

下一期仍从 `tasks/draft-prd.md` 开始。读取当前 Task 的 Required/Conditional Inputs，按需使用有效 project/decisions/reusables 等事实；不自动继承完整历史，未变化事实无需重复整理。
