# 情境：A 类主线——一期完整流程

> 适用于：一个迭代版本（v1、v2……）从需求到上线的完整过程。  
> 前置：项目已初始化（见 `01-启动新项目.md`）。

---

## 全局流程图

```
§1 编排阶段
  draft-prd-vN ──→ [G1]
  draft-tech-design ──→ [G2]
  plan-sprint ──→ [G3] ──→ queue/ 任务就绪
        ↓
§2 开发循环（可多人并行）
  develop → pr-review → merge
        ↓
§3 联调与验收
  generate-integration-tests → 失败修复 → 全部通过
  manual-test ──→ [G4]
        ↓
§4 收尾部署（可并行）
  deploy
  wrap-up-iteration ──→ [G5]
```

每个阶段结束时都有一个 Gate 作为确认点，在 hact-app 里实时可见。

---

## § 1 编排阶段

> **目标**：把"我们要做什么"变成"每个人知道自己要做什么"。

### 1.1 写 PRD（draft-prd-vN → G1）

**做什么**：把本期要做的功能写成结构化的产品需求文档，包含用户故事、验收标准、业务约束。

**AI 做 / 你做**

| AI（CC）做 | 你做 |
|---|---|
| 从背景描述中起草 PRD 框架 | 提供需求背景和目标 |
| 补全用户故事和验收标准（AC） | 审核 AC 是否准确反映预期 |
| 指出需求模糊或遗漏的地方 | 澄清歧义，拍板边界 |
| 在文档末尾询问是否签 G1 | 确认签字，授权进入技术设计 |

**开始方式**：在项目根目录开新 CC 会话，告诉 CC 你要写这期的 PRD，描述一下背景和目标。CC 会自动读取现有的占位文件，开始和你一起起草。

**产物**：`iterations/v1/prd.md` 完整版，G1 写入 `iterations/v1/gates.md`。

**hact-app 里**：G1 变为已签（绿色），项目总览进度更新。

---

### 1.2 写技术方案（draft-tech-design → G2）

**做什么**：设计本期的技术实现方案，产出 TRD（接口定义 + 数据结构）和三份开发规范。

**AI 做 / 你做**

| AI（CC）做 | 你做 |
|---|---|
| 从 PRD 推导 API 接口和数据库表结构 | 审核技术方案是否可行 |
| 生成前端、后端、共享三份 standards | 补充架构决策和特殊约束 |
| 识别技术风险和依赖关系 | 拍板关键技术选型 |
| 在文档末尾询问是否签 G2 | 确认签字，授权拆 sprint |

**开始方式**：开新 CC 会话，告诉 CC PRD 已经签了，现在要开始做技术方案。CC 会读取 PRD，引导你一步步出 TRD 和 standards。

**产物**：`iterations/v1/trd.md`（迭代内）+ 项目根 `standards-shared.md` / `standards-frontend.md` / `standards-backend.md`（跨迭代活文档，v1 在此播种），G2 签字。

**hact-app 里**：G2 变为已签，迭代详情页可查看 TRD 只读视图。

---

### 1.3 拆 Sprint（plan-sprint → G3）

**做什么**：将 TRD 和 standards 拆解为开发者可直接执行的任务包，放入 queue。

**AI 做 / 你做**

| AI（CC）做 | 你做 |
|---|---|
| 从 TRD 拆出前端/后端任务包 | 确认拆分粒度合理 |
| 为每个任务写完成判据和依赖关系 | 确认任务边界无遗漏 |
| 生成 sprint.md 概览 | 检查是否有并行冲突 |
| 将任务包写入 `queue/` | 在 hact-app 为成员分配任务类型 |
| 询问是否签 G3 | 确认签字，开发可以开始 |

**开始方式**：开新 CC 会话，告诉 CC 技术方案已经确认，现在要拆 sprint。CC 会读取 TRD 和 standards，开始拆任务包。

**产物**：`iterations/v1/queue/` 下若干任务包文件 + `sprint.md`，G3 签字。

**hact-app 里**：开发者看板出现所有任务，状态全部为「待认领」。这是团队开始并行开发的起点。

---

## § 2 开发循环

> **目标**：把任务包变成合并进主分支的代码。可多人并行，互不阻塞。

### 2.1 开发者认领任务

**开始前**：打开 hact-app 开发者看板，确认哪些任务待认领（无人认领 = 可以拿）。

在项目根目录开新 CC 会话，告诉 CC 你要认领哪个任务（说任务名或者把任务文件内容贴给它）。CC 读取任务包，确认边界和完成判据，开始工作。此时 hact-app 开发者看板该任务状态变为「进行中」，显示认领人。

---

### 2.2 写代码（develop）

**AI 做 / 你做**

| AI（CC）做 | 你做 |
|---|---|
| 读取 TRD 和 standards，按规范写代码 | 回答实现过程中的业务判断 |
| 自检：调用 simplify skill 检查冗余 | 确认实现符合预期 |
| 创建功能分支，推送到 Gitee | — |
| 创建 PR，写 PR 描述 | — |

**产物**：Gitee 上一个带完整描述的 PR。

---

### 2.3 代码审查（pr-review）

PR 创建后，有代码审查权限的成员来做 CR。开新 CC 会话，把 PR 链接告诉 CC，说要做代码审查就行。

**AI 做 / 你做**

| AI（CC）做 | 你做 |
|---|---|
| 对照 standards 检查代码质量、命名、结构 | 关注业务逻辑是否正确 |
| 识别潜在 bug 和安全隐患 | 做最终通过/打回判断 |
| 生成结构化 CR 反馈 | 写入 PR 评论 |

**两种结果**：
- **通过**：PR 合并，任务包移入 `queue/done/`，hact-app 任务状态变「已合并」
- **打回**：开发者按反馈修改后重新提交，再次 CR

> **为什么要走 PR/CR？**  
> 不只是"检查代码"——每一次 PR 都是一条有据可查的记录：改动了什么、为什么改、谁审过。出问题时，这是追溯的依据；新人来了，这是了解系统历史的窗口。AI 做了大部分检查工作，CR 的额外成本已经很低。

---

### 2.4 重复直到 sprint 完成

所有任务包从 `queue/` 流入 `queue/done/`，sprint 完成。

**hact-app 里**：开发者看板所有任务变「已合并」，sprint 完成率 100%，可以进入联调。

---

## § 3 联调与验收

> **目标**：验证各模块集成后的整体行为，确认系统达到 PRD 验收标准。

### 3.1 联调测试（generate-integration-tests）

在项目根目录开新 CC 会话：

```
generate-integration-tests
```

**AI 做 / 你做**

| AI（CC）做 | 你做 |
|---|---|
| 从 PRD 和 TRD 设计测试场景（前端 pinchtab ≤15 条，后端 API 不设上限） | 确认场景覆盖了关键业务路径 |
| 编写 curl 脚本（接口测试）和 pinchtab 脚本（前端交互） | — |
| 执行全部测试，生成结果报告 | — |
| 失败的场景自动生成 develop(source=integration) 任务包 | — |
| 修复合并后重新跑，直到全部通过 | 确认所有修复符合预期 |

**hact-app 里**：集成测试清单实时刷新（5 秒轮询），可以看到每条测试的通过/失败状态，无需盯着终端。

---

### 3.2 人工验收（manual-test → G4）

联调全部通过后，进行人工验收：

```
manual-test
```

**AI 做 / 你做**

| AI（CC）做 | 你做 |
|---|---|
| 从 PRD 生成验收场景清单 | 逐条在浏览器/App 里操作验证 |
| 记录每条验收结果 | 发现问题时描述复现步骤 |
| 将未通过项生成 develop(source=manual-test) 任务包 | 修复完成后重新验收 |
| 全部通过后询问是否签 G4 | 确认签字，授权部署 |

**G4 签字**：意味着产品质量已确认，代码准备上线。

**hact-app 里**：G4 变为已签，项目总览显示本期可部署。

---

## § 4 收尾部署

> **目标**：把通过验收的代码上线，完成本期迭代的文档收尾。  
> 部署和迭代收尾可以**并行**进行，互不阻塞。

### 4.1 部署（deploy）

```
deploy，target: prod
```

**AI 做 / 你做**

| AI（CC）做 | 你做 |
|---|---|
| 通过 SSH MCP 连接服务器 | 确认部署窗口和时机 |
| 拉取最新代码，执行构建 | — |
| 重启服务（pm2 / nginx） | 验证线上功能正常 |
| 执行健康检查（curl health 等），记录部署日志 | 确认上线结果 |

**hact-app 里**：部署日志写入后，可在项目页面查看本次部署记录。

---

### 4.2 迭代收尾（wrap-up-iteration → G5）

```
wrap-up-iteration，version: v1
```

这是一个**机械化的三步操作**，CC 完成大部分工作：

**第一步：偏离对账**  
对比最终代码与 PRD/TRD 的差异，将偏离记录写入 `backlog.md`，必要时反向更新文档。

**第二步：feedback 审阅**  
读取本期积累的 `feedback.md`，分流：
- 编码规范、禁止事项 → 誊入执行人个人 notes（`[规范]`）
- 自检容易漏的验证项 → 誊入个人 notes（`[checklist]`）
- 方法论 / 流程问题 → 誊入个人 notes（`[方法论]`）（**不在收尾阶段直接改方法论文件**）
- 业务积累 → 更新 `decisions.md` / `reusables.md`（项目仓，不变）

> 誊入个人 notes 的条目，之后由管理者用 `harvest-notes` 收割、去重择优后上提到公共层（templates/standards、templates/checklists、方法论待议）。开发者全程不碰 hact-method。

**第三步：更新 project.md**  
将本期完成的功能、技术决策和已知风险合并进 `project.md`，作为下一期的基础。

完成后，CC 询问是否签 G5，签字后本期迭代正式关闭。

**hact-app 里**：G5 变为已签，五个 Gate 全绿，迭代自动归入「已完成」列表，可随时查看历史记录。

---

## 一期完成后

下一期从 `draft-prd-v2` 开始，流程相同。上一期沉淀的 `project.md`、`decisions.md`、`reusables.md` 自动成为下一期的上下文——积累不会消失，每期都在前一期的基础上往前走。
