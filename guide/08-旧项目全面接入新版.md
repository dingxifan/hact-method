# 旧项目全面接入新版 Method

本指南用于把已经运行过旧版 HACT 的项目一次性接入 current-only Core。目标是 reconcile，不是 restart：保留 PRD、UX、TRD、Sprint、历史 Task、Gate、review 与业务事实，只归一化新版无法安全读取的安装、所有权和活跃状态边界。

## 1. 完成定义

旧项目只有同时满足以下条件，才可声明全面采用新版：

- `_meta/method-sync.json` 为 `hact-method-install/v2`，绑定固定 Method SHA；
- runtime check 与项目 checker/hook 验证通过；
- Method-owned、merged、project-owned 文件边界明确，项目专属规则没有丢失；
- 历史材料保留但不进入 current lifecycle；
- 活跃 `tasks[]` 身份唯一，当前 Task 能由新版入口唯一路由；
- 文档 Task 与 develop Task 使用各自 completion profile；
- Independent Review 绑定 fixed candidate 并保留 stable finding lineage；
- 至少一个真实、低副作用 Task 完成端到端冒烟；
- 没有未经授权的 push、deploy、生产迁移或外部副作用。

## 2. Phase 0：固定真实基线

在任何写入前记录：

- repository、remote、branch、HEAD、tree、upstream、ahead/behind；
- working tree、index、stash；
- 旧 Method identity 与 metadata schema；
- `status.yml`、历史状态文件和 Gate 事实；
- hook、checker、项目启动入口；
- 项目专属规则所在文件。

工作树有来源不明改动、目标 Method SHA 未固定、repository identity 不明确或存在同文件活跃写入时停止。不要先 stash/reset/覆盖。

## 3. Phase 1：生成 normalization plan

计划文件写到项目外的临时目录，避免为了生成计划先把项目变脏：

```text
node ../hact-method-lab/legacy-migration/normalize-legacy-project.cjs \
  --root . \
  --ref <固定 Method SHA> \
  --out <外部临时目录>/legacy-adoption-plan.json
```

plan 固定：

- project baseline commit/tree；
- legacy Method source；
- target Method source；
- 每个安装目标的 ownership、current/previous/target digest 与动作；
- retired paths；
- 重复 Task ID；
- 全部 blockers。

退出码非零表示存在 blocker，不能应用。

## 4. Phase 2：关闭 blockers

### `WORKTREE_NOT_CLEAN`

先识别改动 owner 和用途。只在获得正确权限后完成、提交或隔离；不能由迁移器自行 stash、restore 或删除。

### `METHOD_OWNED_DRIFT`

说明一个目标文件既被视为 Method-owned，又含无法由旧 source 证明的内容。逐项判断：

- 项目规则应迁入 `project.md`、`foundation.md`、项目自有配置或其他 project-owned 路径；
- 入口文件确需合并时，应在 Method ownership policy 中被明确归为 `merged`，而不是临时豁免；
- 无法判断时停止并由项目负责人裁决。

### `DUPLICATE_ACTIVE_TASK_ID`

新版活跃 `status.yml` 要求 Task ID 唯一。处理时：

- 不删除 Git 历史；
- 已完成旧记录可迁入只读历史投影，或在有证据时使用明确的新 identity；
- 依赖、review 与状态引用必须同步；
- 无法无歧义判断时停止，不允许 Map 静默保留最后一项。

### `LEGACY_SOURCE_UNPROVABLE`

先取得旧 Method commit/object，使旧 ownership 可以验证。不能根据当前文件内容反推旧 source，更不能伪造旧 manifest。

关闭后重新生成 plan；不要手工删除 `blockers` 字段。

## 5. Phase 3：核对文件所有权

逐项检查 plan：

| ownership | 允许动作 | 禁止动作 |
|---|---|---|
| `method-owned` | `install-source` / `adopt-source` / `update-source` | 保留不明漂移 |
| `merged` | 缺失时安装；有旧 source 时执行可复现三方合并 `merge-three-way` | 静默覆盖项目规则或忽略新版入口 |
| `project-owned` | 已有内容保持不动 | 因模板存在而宣称 Method 拥有 |
| retired | `preserve-retired`，后续单独裁决 | normalization 中顺手删除历史/项目文件 |

`AGENTS.md` 与 `gitee-ops.md` 默认为 merged。normalizer 以“项目当前文件 / 旧 Method source / 目标 Method source”做三方合并；冲突即 `MERGED_PATH_CONFLICT`，不得自动选一边。合并结果的 digest 会进入 plan 和 v2 manifest；后续未登记漂移仍会被 runtime check 拦截。

## 6. Phase 4：隔离应用

在独立 branch/worktree、原 baseline 未移动且项目工作树干净时：

```text
node ../hact-method-lab/legacy-migration/normalize-legacy-project.cjs \
  --root . \
  --ref <固定 Method SHA> \
  --apply <外部临时目录>/legacy-adoption-plan.json
```

应用器会重新生成计划并逐字节比较；HEAD、工作树、source、文件或状态有变化即认定计划过期并停止。

成功后写：

- `_meta/method-sync.json`：current v2 ownership manifest；
- `_meta/hact-vnext-normalization.json`：一次性接入证据。

后续 current v2 升级若需要 merged 三方合并，追加 `_meta/method-upgrades/{target-method-sha}.json`，不覆盖初次 normalization evidence。若项目 `.gitignore` 忽略 `_meta/`，必须按候选写集显式纳入这些证据文件；不能让本地存在冒充 Git Truth。

它不会 commit、push、改 Gate、重开 Task 或修改业务代码。

## 7. Phase 5：机械验证

至少运行：

```text
node ../hact-method-lab/scripts/sync-method.cjs --verify --root . --ref <Method SHA>
node ../hact-method-lab/scripts/sync-method.cjs --runtime-check --root .
node scripts/check-hook-state.js
git diff --check
```

并运行项目实际使用的 checker tests、语法检查和 changed-file allowlist 核对。机械验证只证明结构与 identity，不证明迁移语义正确。

## 8. Phase 6：Fresh Isolated Migration Review

固定 migration candidate commit/tree 后，Reviewer 只读取：

- project baseline；
- migration candidate；
- target Method SHA；
- normalization evidence；
- ownership/diff 清单；
- mechanical evidence。

必须回答：

1. 项目专属规则是否丢失；
2. 历史 Task、Gate、PRD/UX/TRD/Sprint 是否被改变或重开；
3. 历史材料是否被错误带入 current lifecycle；
4. 是否出现未授权业务、部署或外部变化；
5. manifest 是否准确描述实际安装状态；
6. 启动入口是否只引用同一 adopted Method SHA。

Blocking finding 修复后形成新 candidate，并以相同 finding ID targeted re-review。Review PASS 不批准 Gate，也不等于允许 push。

## 9. Phase 7：集成与首个 Task 冒烟

只有原 branch/HEAD 未漂移、写集准确、机械验证和独审均通过时才能本地集成。集成后再次运行 runtime check，并确认历史 Task/Gate 未变化。

随后选择一个低副作用、边界清晰的真实 Task：

```text
Task routing
→ fixed candidate
→ deterministic verification
→ Fresh Independent Review
→ targeted fix/re-review（如需）
→ task-specific completion check
→ Accepted Project Truth
→ 独立 Human Authority / Gate（如适用）
```

安装成功不能替代这次冒烟。冒烟只验证新版 lifecycle，不重验整个旧项目。

## 10. 回滚与停止条件

失败时保留原项目 branch/HEAD，不把部分安装结果搬回原工作树。保留候选、plan、review 和失败证据在隔离引用；修复形成新 candidate，不改写旧报告。

遇到以下任一情况必须停止：

- 需要改变产品、业务或 Gate 历史；
- 文件所有权无法无歧义判断；
- normalizer 必须猜测历史状态；
- 写集超出迁移 allowlist；
- baseline 漂移或存在未知活跃写入；
- 需要 push、deploy、生产迁移或其他新 Authority。
