# 情境：开启下一版本（v2+）

> 适用于：v1 完成或接近完成时，开始新一期迭代。  
> 流程与一期完整流程完全相同，本文聚焦"新旧期的衔接"和"并行规则"。

---

## 什么时候可以开始 v2

**标准时机**：v1 签了 G5（迭代收尾完成），正式进入 v2。

**提前启动（并行）**：A 类约束允许 v2 在 v1 G3 之后启动：

| v1 当前阶段 | 能否启动 v2 |
|------------|------------|
| G3 之前（PRD/TRD/sprint 还没完） | 不建议；上一期边界未定，新期需求容易混乱 |
| G3 之后（开发进行中） | 可以；v2 可以开始写 PRD 和 TRD |
| G4 之后（验收通过） | 完全没问题 |

B 类任务不受此限制，随时可以开始，不依赖任何迭代状态。

---

## 上一期留下什么

v1 结束后，这些文件会成为 v2 的基础背景——CC 自动读取，不需要你重新讲一遍：

| 文件 | 内容 | v2 时如何用 |
|------|------|------------|
| `project.md` | 最新产品状态快照 | CC 读取了解已有功能，不重复描述 |
| `decisions.md` | 架构决策记录 | 延续技术选型，避免重复踩坑 |
| `reusables.md` | 可复用组件 / 工具 | 任务包标注复用来源，减少重复开发 |
| `design.md` | 视觉规格 | 保持 UI 风格一致 |
| `backlog.md` | 积压与排除项 | v2 PRD 时决定哪些进本期 |

---

## 开启 v2 的起点

在项目根目录开新 CC 会话，告诉 CC 要开始 v2：

> "v1 已经完成，我们要开始 v2，这期想做……"

CC 会自动：

1. **创建 v2 目录结构**：`iterations/v2/queue/done/`（v1 的 `init-project` 不创建这个，由 `draft-prd-v2` 创建）
2. 读取 `project.md` / `decisions.md` / `reusables.md` 了解已有现状
3. 进入 `draft-prd-v2` 流程（和 v1 PRD 写法完全一样）

---

## v2 的完整流程

与 v1 完全相同，5 个 Gate：

```
draft-prd-v2 ──→ [G1]
draft-tech-design ──→ [G2]
plan-sprint ──→ [G3] ──→ iterations/v2/queue/ 任务就绪
develop（含独立审查 + 自合并到 master）
generate-integration-tests → 全部通过
manual-test ──→ [G4]
deploy + wrap-up-iteration ──→ [G5]
```

每期文档独立存放在 `iterations/v2/` 下，不覆盖 v1。

---

## 多期并行的注意点

v1 和 v2 同时进行时，有几点需要关注：

**代码冲突**：同一个文件如果两期都在改，合并时需要解冲突。CR 阶段提前留意有重叠改动的 PR，提早沟通合并顺序。

**任务独立**：各期 queue 天然隔离（`iterations/v1/queue/` 和 `iterations/v2/queue/`），互不干扰，可并行认领。

**B 类任务**：始终放入当前活跃迭代的 queue，不为 B 类单独建目录。

**部署**：默认合并部署——master 上所有"已验证"的 commit 一次性上线，不按迭代单独拆分部署。如果两期代码都在 master，一次部署全部带上。

---

## hact-app 里

多期并行时，hact-app 项目页面同时显示 v1 和 v2 的 Gate 状态，一眼看出两期各走到哪里。开发者看板可按迭代筛选，互不干扰。

---

## 积累会越来越好

每一期，`project.md` 更新一次，`decisions.md` 增长一段，`reusables.md` 新增几个组件。从第三期开始，CC 理解现有系统的速度明显加快——背景文件越完整，越省沟通成本，新功能也越来越难出现"跟已有设计不搭"的问题。
