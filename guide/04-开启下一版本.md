# 情境：开启下一版本（v2+）

流程沿用 [一期完整流程](02-一期完整流程.md)，新期需求进入 [draft-prd](../tasks/draft-prd.md)，不用另建一套版本流程。

## 新旧期衔接

通常上一期 G5 后开始下一期。提前准备时，保留原有取舍：上一期 G3 前不建议并行起新期，G3 后可先做新期 PRD/TRD；下一期 dispatch 不早于上一期 G4，具体多迭代边界见 [现有约定](../skeleton/06-gates.md)。各 Task/Gate 前置仍按现行契约，不因准备提前就授权开发或部署。

向当前项目中的 Codex/ChatGPT 说明新期版本和目标即可，不要求仅因切换迭代另开会话。新期目录及文档按 Task 创建，保留上一期文件和历史事实。

## 读取哪些已有事实

按当前 Task 的 Required/Conditional Inputs 读取有效 `project.md`、decisions、reusables、design、backlog 等内容，用于了解已实现能力、仍适用的决定和真实欠账。无需用户重新搬运完整历史，也不预加载所有材料。

只更新本期真实变化的稳定事实。decisions/reusables 不必每期新增条目；已有内容不因被保留就自动成为当前约束。不把材料增长本身当作模型效率改善的证据。

## 并行与发布

- 各期目录隔离只避免混放产物；认领仍须满足 readiness、依赖和共享写冲突约束，不能因此认定可并行修改同一资产。
- B 类不依附活跃迭代，按 [B Intake](../protocols/b-intake.md) 使用项目根 `b-queue/{task-id}.md`，动态状态在 `status.yml`。
- 默认可合并发布已验证结果，但实际 deployment scope、snapshot 和 target 必须被现有接受/授权覆盖；代码同在 Accepted branch 不等于所有内容都已获部署授权。
