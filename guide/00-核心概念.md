# 核心概念：10 分钟读懂这套方法

> 读完这篇，你会知道：这套方法的底层逻辑是什么，有哪些基本概念，工作时从哪里开始。

---

## 一句话概括

**你是谁不重要，你在做什么才重要。**

这套方法不依赖"角色"来分工——不是"你是开发所以做这件事"，而是"这个任务需要什么，就加载对应的规范去做"。同一个人，上午写 PRD，下午拿任务包写代码，换的是"任务"，不是"身份"。

---

## 三层结构：工作、存储、可见

这套方法的所有活动分布在三层：

```
CC 对话（工作层）
    ↓ 写文件、推代码
Gitee 仓库（存储层）
    ↓ Webhook 实时同步
hact-app（可见层）
```

- **CC 对话**：所有实际工作发生的地方。AI 在这里写 PRD、拆任务、写代码、跑测试、执行部署。
- **Gitee**：文件和代码的权威来源。PRD、TRD、任务包、代码、Gate 签字——一切以文件形式存在于项目仓库。
- **hact-app**：团队的可见层。任务状态、Gate 进度、开发者看板、集成测试结果——不需要翻文件，打开网页就能看到整个项目的实时状态。

> **一句话**：文件走 Gitee，信息走 hact-app。

---

## 两个工作区

所有工作只在两个地方进行，按"你现在在做什么类型的事"来区分：

| 工作区 | 物理位置 | 做什么 |
|---|---|---|
| **hact-method**（方法论区） | `hact-method/` 目录 | 调整方法论、立新项目 |
| **项目根**（项目区） | `{project-name}/` 目录 | 一切与具体项目相关的工作 |

切换工作区 = 关闭当前 CC 会话，打开新目录，开新会话。  
每次 CC 启动时，会自动读取当前目录的规范文件，知道"现在在做什么"。

> 绝大多数工作都在**项目根**进行，包括写 PRD、写技术方案、拆 sprint、写代码、部署。

---

## 12 个任务类型

每件事都对应一个 `task.type`，这是加载规范的路由键：

| 阶段 | 任务 | 做什么 |
|---|---|---|
| 立项 | `init-project` | 创建项目目录和初始文件 |
| 准备 | `draft-prd-vN` | 写本期 PRD（产品需求）→ G1 |
| 准备 | `draft-tech-design` | 写 TRD + 三份 standards → G2 |
| 准备 | `plan-sprint` | 拆任务包入 queue → G3 |
| 跨段 | `revise-doc` | 修订已签的 PRD/TRD/standards |
| 开发 | `develop` | 拿任务包写代码 + 推 PR |
| 开发 | `code-review` | 复核 PR，给反馈或通过 |
| 开发 | `generate-integration-tests` | 写联调脚本 + 跑测试 |
| 开发 | `manual-test` | 人工验收对照 PRD → G4 |
| 收尾 | `deploy` | 部署到服务器 |
| 收尾 | `wrap-up-iteration` | 迭代收尾三步 → G5 |
| B 类 | `dispatch-new` | 派新 BUG 或优化任务 |

---

## 5 个 Gate（质量检查点）

Gate 不是额外的审批流程，而是**某个阶段完成的确认动作**，附在对应任务的末尾：

| Gate | 附在哪个任务末尾 | 确认什么 |
|---|---|---|
| G1 | `draft-prd-vN` | PRD 完整，可以开始技术设计 |
| G2 | `draft-tech-design` | TRD + standards 就绪，可以拆 sprint |
| G3 | `plan-sprint` | 任务包入 queue，可以开发 |
| G4 | `manual-test` | 验收通过，可以部署 |
| G5 | `wrap-up-iteration` | 迭代收尾完成，本期关闭 |

Gate 是可选签的——任务做完后，CC 会问"要签 G? 吗"，由有权限的人决定。

---

## A 类 vs B 类

| | A 类 | B 类 |
|---|---|---|
| 定义 | 正常迭代功能开发 | 线上 BUG 或功能优化 |
| 流程 | 走 5 个 Gate，完整主线 | 不走 Gate，直接派任务 |
| 入口 | `draft-prd-vN` 开始 | `dispatch-new` 开始 |
| 周期 | 按迭代（v1、v2……） | 恒定 2 会期：派任务 + 修复合并 |

B 类任务可以随时发起，不受当前迭代状态影响，与 A 类并行。

## queue：开发者的任务池

`plan-sprint` 完成后，所有开发任务会以文件形式放入 `queue/` 目录。  
每个任务包是一个独立的 `.md` 文件，包含：任务说明、完成判据、依赖关系。

开发者**主动拉取**：打开 queue，选一个没人认领的任务，开始做。完成后任务包移入 `queue/done/`。

这个设计让协作边界清晰——每个人知道自己在做什么，不踩踏，不重复。

---

## 一次典型的 A 类主线（简图）

```
init-project
    ↓
draft-prd-vN ──→ [G1 签字]
    ↓
draft-tech-design ──→ [G2 签字]
    ↓
plan-sprint ──→ [G3 签字] ──→ queue/ 有任务了
    ↓
develop（可并行多个）→ code-review → merge
    ↓
generate-integration-tests → 失败 → develop(integration) → merge
    ↓
manual-test ──→ [G4 签字]
    ↓
deploy ‖ wrap-up-iteration ──→ [G5 签字]
```

## hact-app：团队看板

hact-app 是配套的 Web 应用，给整个团队提供项目可见性。**人只读，CC 来写**——状态变化由 CC 通过 API 写入，Gitee Webhook 触发同步，人在 Web 上看结果。

| 在 hact-app 里能看到 | 对应什么 |
|---|---|
| 项目总览 | 各迭代 Gate 进度、sprint 完成率 |
| 开发者看板 | 哪些任务待认领、谁在做什么、哪些已合并 |
| 集成测试清单 | 当前联调脚本的通过/失败状态（5 秒刷新） |
| Gate 状态 | G1–G5 签字情况，实时同步 |
| 迭代历史 | 已完成迭代的完整记录 |

登录方式：Gitee OAuth（用已有 Gitee 账号直接登录，无需单独注册）。

## 开始工作的正确姿势

1. **打开对应工作区的目录**，开新 CC 会话
2. CC 会自动读取状态，告诉你当前阶段和建议的下一步
3. **声明任务类型**，CC 加载对应规范
4. 按规范完成任务，在末尾签或不签 Gate
5. 关闭会话；下次继续时重复步骤 1

> 详细步骤见各情境文档（[启动新项目](01-启动新项目.md) / [一期完整流程](02-一期完整流程.md) 等）。
