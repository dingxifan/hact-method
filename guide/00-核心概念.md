# 核心概念：10 分钟读懂这套方法

> 读完这篇，你会知道：这套方法的底层逻辑是什么，有哪些基本概念，工作时从哪里开始。

---

## 一句话概括

**你是谁不重要，你在做什么才重要。**

这套方法不依赖"角色"来分工——不是"你是开发所以做这件事"，而是"这个任务需要什么，就加载对应的规范去做"。同一个人，上午写 PRD，下午拿任务包写代码，换的是"任务"，不是"身份"。

---

## 协作与存储

这套方法的所有活动分布在两层：

```
ChatGPT（reasoning、设计、内容、计划、验收）
    ↓ BASE_SHA + 用户人工复制稳定的 Execution Packet / 文件
Codex（repository execution、验证、Git）
    ↓ RESULT_SHA + 用户人工复制 Result Packet
Git 仓库（Shared Project Truth）
```

- **ChatGPT**：形成需求、PRD / UX / TRD 内容、计划和 acceptance judgement；ChatGPT Chat 本身不是真相源。
- **Codex**：在 repository 中落盘 artifact、修改代码、运行 command/test/checker，并执行 Git operation。
- **用户**：只人工搬运稳定的 Packet / 文件并作 Human Authority 决策，不负责编排两个 AI、不维护会话，也不搬运中间 reasoning。
- **Git**：文件和代码的 Shared Project Truth。PRD、TRD、任务包、代码、Gate 签字——一切以文件形式存在于项目仓库。

> **一句话**：一切以文件为准，仓库就是真相源。项目的机器可读状态集中在项目根 `status.yml`（字段见 `skeleton/07`），人同样读取 status；sprint 是规划索引，不存实时状态。

## 三个工作区

所有工作在三个地方进行，按"你现在在做什么类型的事"来区分：

| 工作区 | 物理位置 | 做什么 |
|---|---|---|
| **hact-method**（方法论区） | `hact-method/` 目录 | 调整方法论、立新项目、收割个人积累上提 |
| **项目根**（项目区） | `{project-name}/` 目录 | 一切与具体项目相关的工作 |
| **hact-notes**（个人积累区） | `hact-notes-{你的名字}/` 目录 | 私有，随手记自己的经验（规范 / 坑 / 心得），自己 push |

切换工作区时选择对应项目目录；相关任务在原会话接续，独立工作才另开会话。Codex 在 repository execution 前读取当前目录的规范文件。

> 项目 artifact 与代码都在**项目根**持久化；ChatGPT 可以先形成 PRD、技术方案和 sprint 内容。跨边界时以明确 `BASE_SHA` 出发：大正文走文件、Packet 只带控制信息；Codex 落盘、验证和交付后返回 `RESULT_SHA`，ChatGPT 重新读取该 snapshot 再作判断。
> 个人积累区是你私有的：别人读不到；你记的 `[规范]`/`[checklist]`/`[方法论]` 由管理者用 `harvest-notes` 收割上提为团队公共规范，`[心得]` 永不上提。

## 13 个任务类型

每件事都对应一个 `task.type`，这是加载规范的路由键：

| 阶段 | 任务 | 做什么 |
|---|---|---|
| 立项 | `init-project` | 创建项目目录和初始文件 |
| 收割 | `harvest-notes` | 收割成员个人积累，去重择优上提到公共规范层 |
| 准备 | `draft-prd-vN` | 写本期 PRD（产品需求）→ G1 |
| 准备 | `draft-tech-design` | 写 TRD + 验证入口 → G2 |
| 准备 | `plan-sprint` | 拆任务包入 queue → G3 |
| 跨段 | `revise-doc` | 修订已签的 PRD/TRD/foundation |
| 开发 | `develop` | 拿任务包写代码 + per-task 独立审查 + 推 PR 并自合并到 master |
| 开发 | `integration-verify` | System Verification：整体语义独审 + runtime 联调验证 |
| 开发 | `manual-test` | 人工验收对照 PRD → G4 |
| 收尾 | `deploy` | 部署到服务器 |
| 收尾 | `wrap-up-iteration` | 迭代收尾三步 → G5 |
| B 类 | `dispatch-new` | 派新 BUG 或优化任务 |

---

## 5 个 Gate（质量检查点）

Gate 不是额外的审批流程，而是**某个阶段完成的确认动作**，附在对应任务的末尾：

| Gate | 附在哪个任务末尾 | 确认什么 |
|---|---|---|
| G1 | `draft-prd-vN` | PRD 完整，可以开始技术设计 |
| G2 | `draft-tech-design` | TRD + 验证入口 就绪，可以拆 sprint |
| G3 | `plan-sprint` | 任务包入 queue，可以开发 |
| G4 | `manual-test` | 验收通过，可以部署 |
| G5 | `wrap-up-iteration` | 迭代收尾完成，本期关闭 |

Gate 由 Human Authority 对明确 Accepted snapshot 决定；Codex 负责所需的落盘与事实核验，不绑定某个 AI surface。

---

## A 类 vs B 类

| | A 类 | B 类 |
|---|---|---|
| 定义 | 正常迭代功能开发 | 线上 BUG 或功能优化 |
| 流程 | 走 5 个 Gate，完整主线 | 不走 Gate，直接派任务 |
| 入口 | `draft-prd-vN` 开始 | `dispatch-new` 开始 |
| 周期 | 按迭代（v1、v2……） | 恒定 2 会期：派任务 + 修复合并 |

B 类任务可以随时发起，不受当前迭代状态影响，与 A 类并行。

## queue：开发者的任务池

`plan-sprint` 完成后，所有开发任务会以文件形式放入 `queue/` 目录。  
每个任务包是一个独立的 `.md` 文件，包含：任务说明、完成判据、依赖关系。

开发者**主动拉取**：打开 queue，选一个没人认领的任务，开始做。完成后任务包移入 `queue/done/`。

这个设计让协作边界清晰——每个人知道自己在做什么，不踩踏，不重复。

## 一次典型的 A 类主线（简图）

```
init-project
    ↓
draft-prd-vN ──→ [G1 签字]
    ↓
draft-tech-design ──→ [G2 签字]
    ↓
plan-sprint ──→ [G3 签字] ──→ queue/ 有任务了
    ↓
develop（可并行多个；含独立审查 + 自合并到 master）
    ↓
integration-verify（System Review + Runtime Verification）→ 失败 → develop(integration，含审查 + 自合并)
    ↓
manual-test ──→ [G4 签字]
    ↓
deploy ‖ wrap-up-iteration ──→ [G5 签字]
```

## 开始工作的正确姿势

1. reasoning / design 为主时，可先在 ChatGPT 形成内容和判断；repository execution 为主时，进入 Codex
2. 每次跨边界固定 `BASE_SHA`，用短 Packet 和必要文件交接
3. Codex 验证、落盘、测试、机械闭环，并返回 `RESULT_SHA`
4. ChatGPT 或用户重新读取明确 snapshot 后作下一判断或 Human Authority 决策
