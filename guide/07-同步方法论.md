# 安装与升级当前方法论

新工作默认跟随官方 `dingxifan/hact-method` Accepted `main`，无需协作者手工选择版本。`_meta/method-sync.json.source` 是实际安装回执及执行/审查的固定依据，不是各项目长期自行选择的更新通道。main 表示统一的升级目标，不承诺已验证每个项目的兼容性；项目兼容性通过后才算采用。

新规则面向新工作；已完成历史保持原貌，进行中的链按既有契约接续。新项目直接安装；已接入项目正常升级。只有安装 metadata 无法直接校验、文件所有权不明或需合并入口时，才按 [`08-旧项目全面接入新版.md`](08-旧项目全面接入新版.md) 定向处理安装边界，不要求整个项目历史进入当前 schema。

## 0. 新工作入口自动尝试升级

```text
node ../hact-method-lab/scripts/sync-method.cjs --startup --root .
```

此命令核验实际安装、查询官方 main 并取得精确目标对象，不改项目文件，也不切换方法论仓分支。不使用本地 main、缓存 remote-tracking branch 或协作者自己的 remote 代替官方查询。输出：

- `current` / 退出 0：本次查询与安装一致，可以进入任务；
- `upgrade-required` / 退出 3：由主线 Codex 自动执行下列升级流程；这不是已完成升级，也不是等待用户再次批准；
- 退出 1：来源/安装漂移、官方查询或取对象失败、ahead/diverged 等，停止新工作并报告。网络不可达不声称已是最新。

主线读取输出 target 的本文：`git -C ../hact-method-lab show <target>:guide/07-同步方法论.md`。一次升级始终绑定该 SHA，不在验证中追逐远端后续提交。现有 `--install --ref` 保留为底层固定候选工具；新项目同样从官方 main 解析精确 SHA 后安装。

自动尝试限于已接入项目的新工作边界；正在执行/审查的链及委派单元不发起升级。存在未完成链且无法证明升级不改变该链规则时，先完成原链或报告需要协调，不能自行切换 Method。协作者开始或恢复写入前，比对该链 Method 与实际 manifest，避免旧窗口继续使用旧规则。

1. 核项目身份、干净工作树、实际安装 SHA 与进行中的工作。未提交改动、其他活跃写入、定制冲突或无法确定边界时停止；不自动 stash/reset、改项目规则或重写历史报告。
2. 在以项目当前 HEAD 为基线、带本次任务标识的独立 worktree 中，用固定 target 执行安装或必要的 normalization。复用既有文件所有权、三方合并及迁移审查边界，不改变 hook 或项目存量配置。已知的双边定制冲突停止报告，不凭自动升级授权裁决冲突。
3. 验证安装来源和内容，并针对当前工作实际依赖且受本次改动影响的路径执行兼容性回归。checker 读取旧 evidence 的行为有变化时，用相关真实链定向对照原 checker 与候选 checker；不扫描或重新验收全部已完成历史。必要时运行 `node scripts/check-sprint.js --review-chain <task-id> <项目根> --in-progress`，按该链原有完成边界判断。不重写 rejected/repair 报告；格式不匹配先查读取兼容性，不直接归为业务缺陷。官方 fixtures 和摘要一致不能抵销已出现的实际回归。
4. 按适用 Review 规则取得必要结论；当前动作所需验证未运行、失败或缺原始证据时，仅停止受影响动作，明确缺口。历史本身不因缺新版字段失效；已有证据仍须适用于实际候选，兼容读取不等于把旧 PASS 转给新候选。
5. 固定通过验证的候选 diff。重新核对原项目 HEAD、manifest 与工作区未变化且无活跃写入后，通过正常 Git patch 应用同一 diff（先 `git apply --check`，再默认原子应用；不得 `--reject`）。manifest 与受管文件一并纳入 patch，不逐文件直接覆盖工作目录。应用后运行安装验证、runtime-check 及受影响验证，再进入新工作；Git 接受/PR/推送沿用原权限，不由自动升级取得。
6. 任一候选步骤失败时保持原项目安装，报告实际安装 SHA、目标 SHA、原始错误与下一步。临时 worktree 按仓库清理规则回收；有未提交诊断材料确需保留时列明路径、分支、状态与负责人。应用后的环境验证失败时停止新工作，保留准确现场，不宣称回滚或升级成功，不覆盖后来的协作者改动。

启动检测由命令负责，隔离准备、项目验证与应用由主线 Codex 连续完成；不新增定时器、版本注册中心、release 分支或项目状态账。第一次采用此入口仍需逐项目授权迁移；发布本版不会自动修改尚未接入的项目或已经打开的会话。

## 1. 新项目安装

在干净项目 worktree 中运行：

```text
node ../hact-method-lab/scripts/sync-method.cjs --install --root . --ref <Method SHA>
```

安装器读取 `templates/method-install-policy.json`：

- `method-owned`：必须与固定 Method source 一致，可由后续升级安全替换；
- `merged`：允许项目规则与 Method 入口合并，manifest 同时记录 source 与 installed digest；
- `project-owned`：存在时保留，Method 不据此覆盖项目事实。

安装写 `_meta/method-sync.json`（`hact-method-install/v2`）。遇到已有但未归属的文件、merged 双边变化或任何无法证明的所有权时 fail closed，不覆盖。

安装不 commit、不 push、不改 Gate/Task state。检查 diff 与项目测试后，由用户另行决定交付。

## 2. 当前项目升级

在工作树干净且现有 v2 manifest 可验证时，运行同一 `--install` 命令。升级会：

- 更新未漂移的 Method-owned 文件；
- 对未定制的 merged 文件跟随 Method 更新；
- merged 文件同时有项目改动与上游改动时停止，要求显式三方合并；
- 只删除上一 manifest 中已退休、未漂移的 Method-owned 文件；
- 保留 retired merged/project-owned 文件，由项目另行决定是否退出。

若 merged 文件发生双边变化，使用 Guide 08 的 plan/apply 流程生成可复现三方合并候选；该工具同样接受现有 v2 manifest，但仍只在升级边界运行，不进入日常 Core。

## 3. 旧项目接入

禁止删除旧 `_meta/method-sync.json` 后直接安装，也禁止把 Git clean 当作“没有项目定制”。按 Guide 08 先生成 normalization plan：

```text
node ../hact-method-lab/legacy-migration/normalize-legacy-project.cjs \
  --root . --ref <Method SHA> --out <外部临时目录>/legacy-adoption-plan.json
```

消除全部 blockers 后重新生成，再应用：

```text
node ../hact-method-lab/legacy-migration/normalize-legacy-project.cjs \
  --root . --ref <Method SHA> --apply <外部临时目录>/legacy-adoption-plan.json
```

normalizer 只处理必要的安装来源与所有权，不重写 Task/Gate/review 历史，也不是每次升级的必经流程。历史重复 ID 只作诊断；只有当前选中 Task 无法唯一定位时才在该动作处理，不要求为安装先整理历史。

## 4. 验证

```text
node ../hact-method-lab/scripts/sync-method.cjs --verify --root . --ref <Method SHA>
node ../hact-method-lab/scripts/sync-method.cjs --runtime-check --root .
```

这里的 schema 校验限于安装 manifest；来源缺失、安装漂移或所有权冲突仍须停止相关安装动作。它不要求历史证据符合当前 schema。旧 evidence 的判读使用兼容读取或原固定来源，不把未知格式直接视为通过。

## 5. 读取 adopted Method

```text
node ../hact-method-lab/scripts/sync-method.cjs --read tasks/develop.md --root .
```

运行时只从 `_meta/method-sync.json.source` 指向的 immutable SHA 读取 Method。
