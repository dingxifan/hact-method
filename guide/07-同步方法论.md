# 将现有项目同步到最终版方法论

这是“脚本准备 + 本仓 Codex 完成约束迁移”的单仓升级流程。脚本不调用付费模型、不创建侧栏任务、不自动推送或部署，不访问私人 notes。不要在方法论仓运行目标项目的升级。

## R2.3：显式 Adoption Boundary

既有项目采用本方法时，迁移必须在 `_meta/method-sync.json` 中冻结 adoption boundary，而不是由 checker 根据“缺新字段”猜历史身份：

- `accepted_truth_base`：采用前项目已经提交的 Git HEAD；这是 pre-adoption Project Truth 的固定边界。
- `legacy_accepted_tasks`：只列该 boundary 的 `status.yml` 中已经 `merged` 的任务。身份从 boundary 事实机械导出，不从 task schema、round 缺失或文件年代推断。
- `method_source`：建立该 boundary 时采用的方法 SHA。后续方法升级保留既有 boundary，不把新 HEAD 重写成“历史”。
- 新建项目记录 `kind: new-project`、`accepted_truth_base: null` 与空 `legacy_accepted_tasks`；不存在可 grandfather 的历史。

**兼容规则**：boundary 中已经成立且此后未被触碰的 Accepted Truth 可以继续被接受，不要求补造当时不存在的 `preflight.md`、round reports、固定 tree SHA、`rounds/code_rounds/spec_rounds` 或 `review_report_dir`。这是对既有事实的承认，不是声称旧工作曾执行当前 lifecycle。

**前向严格性**：grandfathering 只保护 history，不保护 future work。adoption 后的新任务、对 legacy task/task record/review evidence 的实质修改、以及 reopen 后再次 merged 的 delta，都必须完整满足当前 vNext 审计链。reopen 可以先进入 active 状态而不伪造“已完成”的 review；当它重新交付时必须产生当前证据。不得通过删除字段、降 schema 或改写 boundary 把 post-adoption 工作重新伪装成 legacy。

**禁止项**：不得为了通过 checker 事后编造历史 rounds、preflight、review reports、tree SHA 或 task package write-set；不得以“旧包”“缺字段”“早期 commit”等启发式自动赋予 legacy 身份；不得降低 checker 让未列入 boundary 的 merged task 静默通过。

## 最简使用方式

在每个项目仓的 Codex 对话中粘贴以下指令，一仓一次：

```text
将当前项目的方法论同步到 ../hact-method-lab 的 codex/context-reduction 最新本地提交。
本次是升级维护，以本指令和迁移说明为准，不启动业务开发，
不执行旧入口的自动同步或过时运行时加载。
先读取该仓 guide/07-同步方法论.md，然后运行：
node ../hact-method-lab/scripts/sync-method.cjs --prepare

按输出的独立 worktree 和 TASK.md 接着完成约束迁移，不停在“文件已复制”。
保留本仓业务约束、配置、hook、自定义检查、历史审查证据及其他工作树在制品。
把仍有效的 Standards 约束归回现有权威对象，并更新活跃任务引用与状态接线。
做独立迁移复核、必要检查与 hook 真触发，写精简复核记录，执行 --verify。
验证通过后 --finish；原工作树干净、原分支和 HEAD 未变时可加 --integrate 快进集成。
若原树有在制品，保留本地升级分支并回收临时 worktree，明确说明尚未集成，不覆盖原树。
不推送远端、不部署、不修改业务代码或真实数据。只有无法从记录裁决的状态冲突、
业务/安全承诺变化或必须影响活跃工作树的 hook 安装变更才向我提问。
```

方法论仓不在默认同级目录时，替换脚本路径并加 `--method-root {方法论仓}`。从项目任意子目录执行均定位到 Git 根；linked worktree 作为本次原工作树，不能把它当另一份独立仓。

“最新”指本地 `codex/context-reduction` 分支的提交。脚本不 fetch、不切方法论分支、不覆盖本地在制品，也不回退到 master。使用另一台机器前，先按用户批准的方式取得该分支；启动输出给出完整 SHA，确认不是旧版本。验证时方法论工作树须干净地检出该 SHA，避免用移动中的版本为旧包背书。

## 命令与结果

升级完成后，日常使用只认 `_meta/method-sync.json` 已有的 source SHA。首次启动/升级后 `--runtime-check` 核项目脚本是否匹配该 SHA 及实际 hook 是否接通；`--read {规范相对路径}` 按同一 SHA 读取正文，方法论工作树后来切分支或有在制品不影响读取。命令不 fetch、不修改配置或注册另一套版本。规范内脚本命令使用已核对的项目 scripts 副本。出现“方法论版本漂移”须先同步，不能以 no-verify 把版本错误当作任务证据问题绕过。既有项目 hook 和自有检查保持原委托方式。

```powershell
node ../hact-method-lab/scripts/sync-method.cjs --runtime-check --root .
node ../hact-method-lab/scripts/sync-method.cjs --read specs-execution/develop.md --root .
```

```powershell
# 只读预检：不建 worktree、不改任何项目文件
node ../hact-method-lab/scripts/sync-method.cjs --check

# 准备：从当前已提交 HEAD 创建 codex/method-sync-{SHA} 独立工作树
node ../hact-method-lab/scripts/sync-method.cjs --prepare

# 后续命令从原项目目录执行，把工具返回的路径填入 --root
node ../hact-method-lab/scripts/sync-method.cjs --verify --root {升级工作树} --ref {固定SHA}
node ../hact-method-lab/scripts/sync-method.cjs --finish --root {升级工作树} --ref {固定SHA}

# 明确要求立即集成时；仅原树干净、分支/HEAD 未改变才快进
node ../hact-method-lab/scripts/sync-method.cjs --finish --integrate --root {升级工作树} --ref {固定SHA}
```

| 结果 | 含义 |
|---|---|
| `prepared` / `resume` | 有升级在制品，接着迁移；不是升级完成 |
| `branch-exists` | 同版本已有本地分发分支；先核是否待集成，不造第二份 |
| `committed` | 升级已本地提交、临时 worktree 已回收，但原项目尚未集成 |
| `integrated` / `already-integrated` | 指定原工作树已接收该版本；没有推送远端 |
| 非零退出 / `integration-failed` | 不报成功；按错误与保留分支恢复 |

脚本默认不执行命令时等价于 `--check`。一次只针对一仓。Node.js 20+ 与 Git 为前置；Windows hook 验证使用 Git 随附的 shell。

## 自动处理与 Codex 必做判断

脚本从固定提交读取入口、4 个角色、Gitee 操作说明、现行检查脚本和门卫模板。不会复制项目数据、状态模板或历史报告来覆盖现状。`status-reviews/` 与 `status.yml` 一样属于项目数据：同步不得覆盖、不得生成候选、不得清理，迁移执行人只在本仓状态对账确有需要时按 `skeleton/07-status-contract.md` 原样搬运。纯模板以 Git 历史 blob 识别（容忍 CRLF/LF），缺失文件新增、已知旧模板更新；不能证明来源的文件保留原样，新版放 `_meta/method-sync-pending/files/`。

原树有未提交改动也可以准备，因为新树只取已提交 HEAD；原树的修改、暂存区与未跟踪文件都不纳入、不清理。迁移时必须识别原树在制品可能影响的活跃任务，不能宣称这些未提交内容已同步。

Codex 在隔离树中完成：

1. **入口和配置**：合并 AGENTS 的项目身份、真实权限与命令，删除旧运行时加载和强制 notes/学科准入。检查 AGENTS.override.md 及子目录入口是否遮蔽新约定。保留用户 `.codex/config.toml` 和明确的模型覆盖；旧模板自身的固定档位可随模板更新退出。
2. **约束归位**：读根部三个 Standards，逐项判定通用教程、已有机械约束或项目独有承诺；最后一种分别归 Foundation、project 技术层、PRD/TRD/design、任务 do-not。不得把未知项删除，也不得把全文换名挪进新大文件。没有依据改变业务/安全承诺时请求用户裁决。
3. **活跃任务**：更新未 merged 包的 reference、do-not 与退役规则字段；保留目标、AC、依赖与实际进度。已完成包、profile 附件、审查报告原样作为历史。无需回填旧 report schema、轮次或时间。
4. **状态**：核 status 与旧 Gate、任务记录及实际 PR/Git；只调整表达形态，不生成新签署。原文冲突不能用“status 优先”跳过首次迁移对账。迁移后 status 为单一动态入口，已有 `status-reviews/` 文件逐字节保留且只由 status 索引进入；它们不是模板或未知候选。旧 Markdown 留历史、不双写。
5. **检查器**：核心副本与固定版本保持一致。自定义检查不能被删掉，应保留独立脚本并接回项目 hook/CI；不能仅删掉候选文件就认为已经合并。旧 profile/runtime/retention 脚本先搜消费者，确认无用途再退役；不要删除业务检查。
6. **hook**：修改版本控制下门卫时保留原有业务规则，接入 status-only Gate 与 merged 审计路由。检查 `core.hooksPath`、直接委托或 Husky 全链。不改全局 Git 配置，不覆盖既有 hook。有效 hook 位于共享 Git 目录，操作它会影响其它 worktree；有活跃开发时先协调，不能因本树隔离就直接替换。只读诊断通过不是完整的实际触发证明。
7. **复核与收尾**：独立复核原始约束、迁移 diff、活跃任务和风险边界；运行适用项目检查与有意义的 hook 正反例，不调用生产数据库或真实外发。结果写 `_meta/method-sync-review.md`，包含约束去向、状态依据、自定义配置保留、hook 接线和已运行/未运行证据。清掉已处理的候选文件后运行 `--verify`。

`--verify` 核固定版本、候选清理、根 Standards 退役、活跃引用、Codex 文件形状、核心脚本版本和语法、hook 静态连通及复核记录存在。它不能证明语义迁移正确或业务全部回归；这些由上述独立复核与实际测试负责。

## 回收、失败与撤回

`--finish` 只提交本次允许的方法载体，生成本地提交，不推送。可选的 `--integrate` 只做 fast-forward；不强行合并、不切原分支。提交后的干净 worktree 立即通过 Git 回收，并核目录和登记均消失；本地分支/提交保留，不等 PR 合并。

准备/验证失败且已有在制品时保留带批次名的 worktree；输出路径、分支及下一步，由当前项目 Codex 负责接续。不得手工删除文件夹或用 force 清除在制品。若提交后中断，先核分支提交和 Git 状态；工作树干净即可 `git worktree remove {路径}`，再双重确认，不删除分支。

升级尚未集成时，原项目不受影响。已集成后需要撤回，应基于升级提交评估 `git revert`，不执行 reset --hard 或覆盖业务工作。首次采用新入口建议新开项目 Codex 会话；当前会话不能仅因磁盘已修改就声称它已重新加载全部指令。

配置依据经 OpenAI Docs 核对：项目角色文件与模型继承见 [Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents)，入口遮蔽/加载顺序见 [AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md)。这些产品配置事实不替代项目迁移授权。
