# 06 · 连接与凭据配置

> 每台开发机**配一次**，之后所有项目自动复用。新成员上机、换机、换服务器时回来看这份。

## 为什么要有它

一个项目跑起来要连的东西不少：Gitee 远端、部署服务器、数据库、第三方 API。这些信息有两种性质，**必须分开放**：

- **坐标**（哪台服务器、哪个目录、哪个 alias）——团队都该看得见，改了要能 review，所以**入库**；
- **凭据**（token、口令、密码）——**永远不入库**，一旦进 git 历史就只能靠轮换补救。

所以是两份文件，一份跟项目走、一份跟机器走：

| 文件 | 跟谁走 | 装什么 | 入库 |
|------|--------|--------|:----:|
| `{项目仓}/connections.yml` | 项目 | 坐标 + `${secret:NAME}` 引用 | ✅ |
| `~/.hact/secrets.env` | 机器 | `NAME=值`，全部项目共用 | ❌ |

`deployment.config` 不受影响，继续管它的构建 / 重启 / 健康检查命令——那是项目命令，不是连接信息。

## 首次配置（每台机器一次）

在任意项目仓根目录：

```bash
node scripts/check-conn.js init
```

它会播种两份骨架（已存在则跳过）。然后：

**1. 填凭据** —— 编辑 `~/.hact/secrets.env`：

```
HACT_GITEE_TOKEN=<Gitee → 设置 → 私人令牌 生成，需 projects 权限>
```

格式就是 `NAME=值`，值不用加引号。**不支持行内注释**（凭据可能含 `#`），整行 `#` 开头才是注释。

> **名字怎么起**：这个文件是**全机共用的一张平表**，撞名就是静默覆盖，所以分两类——
> - **身份类**跟人走，跨项目共用一份，轮换只改一处：`HACT_GITEE_TOKEN`、`HACT_SSH_<别名>_PASSPHRASE`
> - **项目资源类**跟项目走，**必须带项目前缀**：`HACT_MAIL_AI_DB_PROD_PASSWORD`、`HACT_ORG_KRM_V2_DB_PROD_PASSWORD`
>
> 反例是实打实存在的：mail-ai 和 org-krm-v2 都有 `DB_PASSWORD`、都在 `47.110.94.114`、连的是不同的库。两边都图省事叫 `HACT_DB_PROD_PASSWORD`，后填的把先填的顶掉，而且不会有任何报错。`check` 会对 `db.*` / `api.*` 下没带项目前缀的 handle 报 🧑。

POSIX 机器上 `init` 已自动 `chmod 600`；Windows 上自己确认一下该文件仅本账户可读。

**2. 填坐标** —— 编辑项目仓的 `connections.yml`，把用得到的段取消注释：

```yaml
gitee:
  remote: origin
  token: ${secret:HACT_GITEE_TOKEN}

ssh:
  prod:
    mcp-alias: hact-prod            # Codex 里配的 SSH server 名
    host: 47.110.94.114
    user: root
    identity-file: ~/.ssh/id_hact
    app-dir: /srv/my-project        # 服务器上的仓库目录
```

用不到的段整段删掉，别留空段。

**3. 验一次**：

```bash
node scripts/check-conn.js check --live
```

`--live` 会真打一次 Gitee API 和 SSH。日常不用带，只在配置后、换机后、排障时打。

## 日常怎么取值

```bash
node scripts/check-conn.js get gitee.token          # 机密已解析
node scripts/check-conn.js get ssh.prod.app-dir     # 普通坐标
```

项目的代码托管命令、`deploy` 和 `init-project` 已经这么取了，你一般不用手动跑。

已经在 shell profile 里配过 `GITEE_ACCESS_TOKEN` 的机器**不用改**——解析顺序是「环境变量 → `~/.hact/secrets.env` → 历史别名」，老配置照样认。

## 换机 / 新成员上机

1. 拷 `~/.hact/secrets.env` 过去（纯文本，可直接复用）
2. **另拷** `~/.ssh/` 下的私钥文件——它不在 `secrets.env` 里，那里只记路径
3. **重配** Codex 的 SSH MCP server，alias 名照 `connections.yml` 的 `mcp-alias` 填
4. `node scripts/check-conn.js check --live`，缺什么它说什么

后两条是换机最容易漏的，`check` 会分别以 🧑 和 ❌ 提醒。

## 三条红线

- **`connections.yml` 里绝不出现真凭据**。它入库，写进去即视为已泄露，必须轮换。pre-commit 门卫会在提交时拦住已知 token 形态和机密语义字段的裸串
- **`~/.hact` 不放进任何 git 工作树**，也别放进云同步盘里的仓库目录。`check` 判 FAIL
- **不新建第三处存放**。尤其不要往 `backend/.env` 里塞个人 token——那是应用运行时配置

## 排错

| 现象 | 处理 |
|------|------|
| `解析不到值：HACT_xxx` | 往 `~/.hact/secrets.env` 补一行 |
| `明文机密` FAIL | 挪进 `secrets.env`、改写 `${secret:NAME}`，**并轮换该凭据** |
| `凭据落位` FAIL | `~/.hact` 落在 git 仓里了，移出去 |
| `MCP alias 找不到` 🧑 | 新机没配 SSH MCP server；配置写法不同则忽略 |
| `--live` 下 Gitee 401 | token 失效，重新生成后改 `secrets.env` 一处即可 |
| 取到的值末尾被截断 | `secrets.env` 里写了行内 `#` 注释，删掉 |
