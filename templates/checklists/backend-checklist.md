# 后端测试品类清单

> 后端模块完成后，对照本清单确认**各测试品类是否都写了测试并跑绿**，输出【后端测试品类报告】。
> 目标从"逐条肉眼审代码"转为"是否为每类失败方式各写了一个会报红的测试"——没写的测试不会报红，漏洞静默通过，所以品类覆盖比逐行审更可靠。
> 测试是正确性的确定性验证；本清单只保证**测试品类不空缺**，逐条业务正确由测试本身（AC→G/W/T）兜。

---

## 一、测试品类（核心 · 必为每类写测试且全绿）

每类至少一个测试；本次改动确实不涉及某类时标 N/A 并说明（不是默认跳过）。

- [ ] **鉴权授权**：需登录接口未带 token → 401；越权访问他人资源 → 403；资源归属校验（附件/草稿等属当前用户）有测试
- [ ] **入参校验 · 边界**：无效/缺失必填入参 → 400；空数组 / 零值 / undefined / 极值有测试；whitelist 过滤——多余字段被丢弃、不静默落库
- [ ] **错误路径**：资源不存在 → 404（非空对象/null）；超限 → 409 带文案；第三方调用失败错误透传不吞；catch 块有 logger.error
- [ ] **契约**：响应体字段与 TRD/前端消费一致（DTO 平铺、字段名/类型对齐）；响应不含 password/secret/token 等敏感字段
- [ ] **数据 · 并发**：唯一性冲突走 `try/catch ER_DUP_ENTRY`（非先查后写）有测试；批量操作事务包裹、单条失败整体回滚有测试；upsert 依赖的 DB UNIQUE KEY 实际存在

> 不可视区 AC 的 Given/When/Then 例子（plan-sprint 从 TRD 操作化回链进任务包）须 **1:1 落成测试**——上面五类是 AC 测试之外的"失败方式"兜底品类，二者合起来才算覆盖。

## 二、归 lint（机械，由 `npm run lint` 管，不在此逐条人审）

下列项确定性可查，不靠肉眼：无 `any`；用 `req.user.sub`（非 `req.user.id`）；无硬编码密钥/密码/API Key；无 `console.log`（用 Logger）；无未使用 import；无 `// TODO`/`// FIXME`；无注释掉的废弃代码块。`npm run lint` 报错即修，不重复人工核。

## 三、留人判（测试测不动 / 属品味，逐项给结论）

- [ ] **N+1 查询**：关联数据是否用 `relations`/QueryBuilder 一次加载（性能，单测难覆盖，人看）
- [ ] **日志隐私**：日志未打印邮件正文/密码/用户隐私
- [ ] **冗余复用**：无与已有 Service/Repository/工具函数/共享类型重复的实现，已直接复用
- [ ] **深层并发竞态**：有状态操作（同步/队列/定时任务）的防重入、单飞保护——超出单测能稳定复现的部分，人工推演

## 输出格式

```
【后端测试品类报告 · <模块名>】

测试品类：
  鉴权授权 ✅(3 测试) / 入参边界 ✅(2) / 错误路径 ✅(2) / 契约 ✅(1) / 数据并发 ✅(1)
  不可视区 AC G/W/T → 测试：AC1✅ AC2✅ AC3✅（1:1 落地）
  测试运行：npm run test 全绿（XX passed）
  N/A 品类：[列出 + 原因]

留人判：
  N+1 ✅ / 日志隐私 ✅ / 冗余复用 ✅ / 并发竞态 ✅
  [发现的问题 + 处理]

待确认：[需用户决策的项]
```
