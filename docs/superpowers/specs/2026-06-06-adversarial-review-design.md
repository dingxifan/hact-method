# hact-method 对抗性审查系统 — 设计文档

**日期**: 2026-06-06  
**状态**: 已批准，待实现  
**目标**: 用多角色对抗性 Agent 全面审查 hact-method 方法论，产出结构化分析报告，为下一轮方法论改善提供输入

---

## 1. 背景与目标

hact-method 目前处于第三阶段（开发 hact-app），方法论骨架和规范层均已完成。在进入团队引入阶段前，需要一次系统性的对抗性审查，找出：

- 概念层的逻辑漏洞与未验证假设
- 执行层的操作盲区与隐性知识依赖
- AI 依赖的系统性风险与降级路径缺失

审查**不修改**方法论文件，只产出分析报告，由人决定后续如何改进。

---

## 2. 整体架构

```
Phase 1（并行）
  ├── Agent A：理论批评者  ──┐
  ├── Agent B：现场开发者  ──┼──→ Phase 2：合并 Agent → 统一分析报告
  └── Agent C：AI 风险审计者──┘
```

- 三个审查 Agent **并行运行**，独立阅读全量方法论文件，互不知晓对方结论
- 全量文件约 324 KB / ~90k tokens，模型 1M 上下文窗口，无降级风险
- 合并 Agent 去重、按严重程度排序，输出最终报告

---

## 3. 文件集（全量，三个 Agent 共用）

审查范围覆盖以下目录的所有 `.md` 文件（排除 `_meta/`）：

| 目录 | 内容 |
|------|------|
| `BRIEF.md` + `STATUS.md` + `CLAUDE.md` | 项目背景、阶段状态、工作区规范 |
| `skeleton/`（7 份） | 身份模型、工作区、学科、任务全谱、状态机、Gate、状态契约 |
| `specs-structural/`（14 份） | 每种 task type 的结构契约 |
| `specs-execution/`（14 份） | 每种 task type 的执行规范 |
| `guide/`（7 份） | 面向用户的操作指南 |
| `templates/`（全量） | standards、checklists、项目模板、hact-notes 模板 |

## 4. 三个对抗性 Agent 手册

### 4.1 Agent A — 理论批评者

**角色身份**  
资深方法论顾问，从未接触过 hact-method，见过大量"任务驱动""敏捷变体""人机协作"框架的兴衰。职责：找出概念层面的根本性缺陷——逻辑矛盾、未验证假设、被设计者忽视的反例。不关心执行细节，只攻击"这套思想本身是否成立"。

**攻击维度**

1. **任务驱动假设的边界**：`task.type` 能真的替代角色身份吗？当同一人持有多个 discipline 授权时，"你是谁不重要"是否仍然成立？
2. **Gate 价值质疑**：5 个 Gate 对 5-8 人小团队是增值还是增负？签字摩擦成本是否被低估？
3. **拉取池模型的隐含假设**：queue 假设开发者有足够上下文来自主选任务，这个假设在什么情况下失效？
4. **B 类恒定 2 会期约束**：真实 BUG 复杂度差异巨大，固定 2 会期是否是未经验证的赌注？
5. **`merged` 终态不变量**：用"修订路径"代替状态回退，在什么场景下会产生多个并存版本的认知混乱？
6. **23 条决策的内部一致性**：逐条检查 BRIEF.md 关键决策，找出相互矛盾或将来会摩擦的决策对。
7. **方法论自举悖论**：用 hact-method 开发 hact-app，方法论的缺陷会否污染其自身的验证过程？

---

### 4.2 Agent B — 现场开发者

**角色身份**  
能力正常的后端开发者，今天是加入团队的第一天，没有任何 hact-method 先验知识，只能依赖文档行事。职责：逐步骤地按规范走，记录每一个让你卡住、迷惑、或需要依赖隐性知识才能继续的点。不批判设计哲学，只报告"第 N 步我不知道该怎么做"。

**攻击维度**

1. **认领任务时的依赖盲区**：打开 queue/，有哪些任务间依赖关系没在文件里写清楚？
2. **develop 全流程自洽性**：`specs-execution/develop.md` 能否让我独立完成从拉任务到推 PR 的全流程？哪些步骤依赖"默认你知道"的上下文？
3. **PR 被打回后的路径**：CR 给了结构性建议，`pr-review` + `develop` 规范里，下一步是什么？路径是否清晰？
4. **status.yml 并发更新**：两名开发者同时修改 status.yml，规范里的冲突处理是否足够具体可操作？
5. **跨任务依赖阻塞时的行为**：我的任务依赖一个尚未完成的上游任务，规范如何告诉我该等待还是继续？
6. **B 类紧急 BUG 处理**：收到紧急 BUG，`dispatch-new.md` 的步骤是否完整？如何与进行中的 A 类任务并行？
7. **CC 会话重开后的接续**：关闭会话再重开，specs-execution 里是否有足够的实操指引让我知道从哪里继续？

---

### 4.3 Agent C — AI 风险审计者

**角色身份**  
专门审计"人机协作系统"可靠性的工程师，见过大量因过度信任 AI 而在生产环境翻车的案例。职责：找出 hact-method 对 CC（Claude Code）能力的过强假设，以及 CC 出错、迷失或不可用时，系统会在哪里静默失败或产生不可逆损失。

**攻击维度**

1. **上下文丢失的静默错误**：哪些任务规范依赖"CC 记得之前说过什么"？CC 在长会话中丢失上下文时，哪里会产生静默错误而非明显报错？
2. **task.type 误判无检查**：若用户声明了错误的 task.type，CC 加载错误规范，有没有早期发现机制？
3. **集成测试的 AI 幻觉风险**：`generate-integration-tests` 自动生成联调脚本，CC 可能生成"通过但测了假场景"的脚本。规范里有防幻觉设计吗？
4. **status.yml 写入可靠性**：多处规范要求 CC 在任务完成后更新 status.yml。若 CC 写入格式错误的 YAML 或遗漏字段，失败如何被发现？有 schema 校验环节吗？
5. **AI 测试与人工验收的边界模糊**：`generate-integration-tests` 是否在实际上替代了应由人做的验收？规范对边界的定义是否足够清晰？
6. **CC 不可用时的人工降级路径**：每种 task type 的 specs-execution 是否有"CC 无法操作时人工如何处理"的降级描述？还是系统性缺失？
7. **双源规范的污染风险**：`draft-tech-design` 从开发者个人 notes 拉取 `[规范]` 并入 standards，若 notes 里有错误规范，过滤机制在哪里？

## 5. 统一发现格式

三个 Agent 均使用以下格式输出每条发现：

```markdown
### [问题标题]
**严重程度**: P0（系统性缺陷）/ P1（重要漏洞）/ P2（摩擦点）/ P3（优化建议）
**所在层**: skeleton / specs-structural / specs-execution / templates / 跨层
**定位**: 文件路径 § 章节名
**问题**: [2-3 句，说清楚"什么假设在什么条件下失效"]
**影响**: [不处理会导致什么]
**建议**: [具体改进方向，不要求完整解决方案]
```

---

## 6. 合并步骤

合并 Agent 收到三份独立报告后：

1. **去重**：同一问题被多个 Agent 发现时，合并为一条，注明"多角色共同发现"
2. **排序**：P0 → P1 → P2 → P3，同级别按所在层排序（skeleton 优先）
3. **跨层矛盾检查**：专门扫描不同层文件间的定义不一致（如骨架层定义与执行层描述冲突）
4. **输出**：写入 `hact-method/_meta/plans/2026-06-06-method-audit/findings.md`

## 8. 不在本审查范围内

- 不修改任何方法论文件（由人根据报告决定）
- 不审查 `_meta/plans/` 下的过程文档
- 不审查 `skills/`（技术实现，非方法论内容）
- 不评估 hact-app 代码实现
