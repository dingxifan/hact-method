# task: deploy

**discipline**: `deploy`
**Gate**: —
**属性**: `target`

> 将已验收的代码部署到目标环境，验证服务正常。

---

## 前置条件

- **常规部署（A 类迭代）**：G4 已签（manual-test 通过）
- **B 类独立部署**：无进行中的 A 类迭代时，B 类 [merged] 任务积累到一定程度，由有 `dispatch` discipline 的用户主动触发；无需 G4
- **hotfix 快速通道**：`urgency=hotfix` 的 develop 任务 [merged] 后，可不等 G4，由有 `dispatch` discipline 的用户授权后立即部署
- **文件**：`deployment.config`（服务器地址 / 启动命令 / 健康检查端点等，首次部署时创建）

---

## 字段规范

| 字段 | 类型 | 必填 | 取值 / 说明 |
|------|------|:----:|------------|
| `target` | string | ✅ | 目标环境标识，如 `prod` / `staging` |

---

## 工作内容

**合并部署（默认）**：一次部署包含当前所有已验收的改动——A 类迭代 + B 类 normal + B 类 hotfix（若有）。

1. **本地构建验证**：`npm run build`（或对应构建命令）+ 类型检查；构建失败则阻断，不进行后续步骤
2. **推送代码**：将所有待部署分支合并至主分支，push 到远端
3. **服务器拉取**：在服务器执行 `git pull`，确认拉取成功
4. **服务器构建**：执行构建命令；构建失败则保留旧版本，不重启服务，记录错误上报
5. **重启服务**：执行重启命令（如 `pm2 restart`）
6. **健康验证**：curl 健康检查端点（见 `deployment.config`），确认响应正常；检查日志无异常错误
7. **记录部署结果**：写入部署日志（见"主要产物"）

**hotfix 快速通道**（仅 `urgency=hotfix`）：跳过步骤 1–2 中对非 hotfix 分支的合并，仅部署 hotfix 改动。


## 边界场景

| 场景 | 处理方式 |
|------|---------|
| 服务器构建失败 | 保留旧版本，不重启；记录错误，上报；等修复后重新走步骤 3–7 |
| 健康检查失败 | 检查日志定位原因；若无法快速修复，回滚到上一个成功版本 |
| hotfix 与当前未部署的 A 类改动代码冲突 | 解决冲突后再部署；不拆分部署（除非冲突无法短期解决） |
| 无服务器（纯静态 / Gitee Pages 等） | 跳过步骤 3–6，替换为对应平台的发布命令；健康验证改为访问页面确认 |
| 多环境（staging 先于 prod） | 按 `target` 依次执行，每个环境独立验证通过后再推进下一个 |

---

## 异常处理

| 情况 | 处理方式 |
|------|---------|
| 部署后发现功能异常（线上 bug） | 立即走 `dispatch-new(target-source=bug, urgency=hotfix)` → develop → deploy 快速通道 |
| 回滚后仍有问题 | 上报；暂时下线功能或切流量，等根因分析完成后再重新部署 |
| deployment.config 不存在（首次部署） | 先建 `deployment.config`，填入服务器地址 / 构建命令 / 健康检查端点，commit 后再继续 |
