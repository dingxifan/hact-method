# exec: draft-prd-vN

> CC 加载本文时，当前任务是通过三层渐进结构完成本期 PRD，签 G1。
> 三层顺序：**骨架**（方向对齐）→ **结构层**（功能契约）→ **收尾**（开放问题清零 + G1）

**上下文密度**：中。对话驱动，轮次多但单轮不重。需在关键节点阻断等待用户确认。

---

## 红线

- **禁止跳过场景还原**：五要素（谁/情境/问题/现有解法/不足）不完整前不进入下一步，不以"大概理解了"替代明确确认
- **禁止带假设输出骨架**：场景未确认时不输出任何功能清单，哪怕用户催促
- **禁止跳过开放问题清零**：PRD 中开放问题段落不为空时不签 G1
- **禁止保留写不出行为例子的"有行为"AC**：有行为的 AC（涉及逻辑/状态/权限/数据）必须能写成 `Given/When/Then` 例子（测试脊柱·幕 1）；写不出多半是 AC 模糊，当场追问澄清，不带模糊 AC 进 G1（纯视觉美学 AC 无行为，不在此列）

---

用户确认 → 执行：
```bash
mkdir -p "iterations/v{N}/queue/done"
```

开场说：「本次任务是完成 v{N} PRD。我会分三层推进：先对齐产品方向骨架，再逐功能写完整契约，最后清零开放问题签 G1。」

## 第一层：骨架（方向对齐）

### Step 1：场景还原

用「谁 / 情境 / 问题 / 现有解法 / 不足」五要素还原需求背景，输出格式：

```
用户：{画像}
情境：{使用场景}
问题：{核心痛点}
现有解法：{现在怎么做的}
不足：{为什么现有解法不够}
```

五要素不完整则继续追问，不跳过。迭代项目需说明"本期在已有基础上解决什么新问题"。

> **边界**：需求反复修改、超过 3 轮仍不稳定 → 上报，不在旧方案上无限打补丁。

🚫 等用户确认场景还原准确

---

### Step 2：发散 + 三角筛

列出 3–5 个可能解法，每个方案用三角评估：

```
方案 A：{一句话描述}
- D（用户价值）：{评估}
- F（技术可行性）：{评估，标注已知风险}
- V（业务可行性）：{评估}
推荐度：⭐⭐⭐ / ⭐⭐ / ⭐
```

给出推荐方案，说明理由。

> **异常**：用户不认可三角筛选结论 → 重新过一遍，不强行推进；循环超过 3 次则记录分歧点上报。

🚫 等用户选定方向

---

### Step 3：输出 PRD 骨架

基于选定方向，输出骨架——**每个功能只写一句话**，不展开细节：

```markdown
## PRD 骨架 · v{N} · {项目名}

产品目标：{一句话}

目标用户：{一句话}

功能清单：
1. {功能名}：{一句话描述}
2. {功能名}：{一句话描述}
...

MVP 边界（不做什么）：
- {排除项}
```

功能数量超过 6 个时，主动建议拆期，提供优先级排序，等用户决策后再继续。

🚫 等用户确认骨架方向正确（功能范围、排除项）

---

## 第二层：结构层（功能契约）

### Step 4：逐功能展开

骨架确认后，**逐个功能**写完整定义，每个功能写完后单独确认再写下一个。字段与结构化模板 `../hact-method/templates/prd.md` 的功能块**严格对齐**（固定 header `### 功能：` + 槽位标签，供 Step 7.4 linter 解析）：

```markdown
### 功能：{功能名}
**入口**：{用户从哪里触发，如"从任务列表点击进入" / "顶部导航新建按钮"}
**draft-ux**：需要 / 不需要（含新页面或多分支交互流程则填"需要"）
**涉及实体**：{本功能读写的数据实体，逗号分隔，如 Task, Sprint；纯展示无实体写"无"。实体名须与 TRD `### 表：{名}` 同名同形，供交叉对账}
**场景描述**：{具体使用场景}
**Acceptance Criteria**：
- AC-01：{可独立验证的条件}（3–5 条；id 全局唯一、跨功能连续编号 AC-01/AC-02/…，append-only 永不复用、允许空号——任务包据此 `(源：PRD AC-nn)` 回链，linter 机械核逐条覆盖）
  - 例：Given {前置/输入} / When {动作} / Then {期望结果}
**明确排除**：本功能不包含 {具体排除内容}
```

**AC 行为例子（测试脊柱·幕 1）**：每条**有行为的** AC 紧跟一行 `例：Given … / When … / Then …`，把"可独立验证的条件"落成具体的「应发生什么」。
- **你（产品）只需验证行为对不对**，不需要会写代码也不需要分前后端——例子由 CC 起草、你确认（"对，无权限就该被拒绝"），与你确认其它 AC 文本同性质。技术精度（确切状态码/错误码）不在这里写，留 `draft-tech-design` 幕 2 精化。
- **作用**：把"坏 AC"在需求阶段（最便宜处）就逼出来——有行为的 AC 写不成例子，多半是 AC 本身模糊，当场追问澄清，不拖到技术设计或开发才发现。这条例子是下游测试脊柱的源头（TRD 精化 → develop 物化成可运行测试），全程无损携带、永不蒸馏。
- **边界**：纯视觉/美学 AC（如"主色为蓝"、间距风格）无行为可写，省略例子，留 `design.md` + 原型走查；可视/不可视的切分是技术判断，不在此分，留 TRD/plan-sprint。

> **用户故事**汇总到顶层「## 用户故事」段（3–5 个，覆盖核心场景），不逐功能写。
> **开放问题**逐功能记在工作笔记里，Step 6 清零后落到顶层「## 开放问题」段（定稿须为空）——不进功能块。

🚫 每个功能写完后等用户确认，有修改则改完再继续下一个

---

### Step 5：视觉规格（首期项目必做，迭代项目按需）

**判断条件**：`project.md` 中无视觉规格记录，或本期有新页面 / 新组件类型。

四步完成视觉规格：
1. 让用户提供 1–3 个参考产品或截图
2. 提炼风格关键词（色系 / 字体感 / 间距风格 / 组件风格）
3. 逐节与用户确认（色彩 → 字体 → 间距 → 组件）
4. 写入 `design.md`

🚫 每节视觉规格确认后才写入，不一次性写完

---

## 第三层：收尾

### Step 6：汇总开放问题 + 清零

收集所有功能中标记的"开放问题"，逐条与用户确认：

- 有答案 → 更新对应功能定义
- 无法确定 → 记入 `backlog.md`，从 PRD 中移除

🚫 等所有开放问题处理完毕（PRD 中开放问题段落为空）

---

### Step 7：写文件 + 知识沉淀

套用结构化模板 `../hact-method/templates/prd.md`（固定 6 段 header + 功能块 `### 功能：` + 槽位）整合所有功能定义，写入 `iterations/vN/prd.md`。**不得偏离模板的 header 与槽位写法**——Step 7.4 的 linter 按此解析，偏离即误报。模板里的 `<待填>` 占位、HTML 注释提示、示例占位块**必须全部替换/删除**。

**迭代 PRD（v2 及以后）必须在文件开头加「vN 变更摘要」章节**，格式如下：

```markdown
## vN 变更摘要

> 供技术设计和开发阶段快速定位工作范围。继承项无需重新设计，仅需验证与新架构的兼容性。

### 架构层变更（有则写，无则省略）
| # | 变更 | 影响范围 |
|---|------|---------|
| A1 | {变更描述} | {影响的功能或模块} |

### 功能变更
| # | 功能 | 变更类型 | 说明 |
|---|------|---------|------|
| F1 | {功能名} | 继承 / 继承·微调 / 重构 / 简化 / 新增 | {一句话说明本期做了什么} |
```

同时，每个功能标题须带变更类型标签，与摘要表一致。**标签作后缀，header 仍以固定 `### 功能：` 起头**（保证 Step 7.4 linter 能切块）：

```markdown
### 功能：功能名 `继承`
### 功能：功能名 `继承·微调`
### 功能：功能名 `重构`
### 功能：功能名 `新增`
```

变更类型定义：
- **继承**：与上期完全一致，无改动
- **继承·微调**：主体不变，局部调整（如过滤规则、展示字段）
- **重构**：核心逻辑重写，但功能目标相同
- **简化**：移除部分子功能，范围收窄
- **新增**：本期首次引入

更新 `project.md` 产品层（目标 / 用户 / 功能边界）。

> **异常**：用户明确要求跳过某个段落 → 在对应段落注明"用户决定跳过：{原因}"，不留空。

---

### Step 7.4：结构 linter 自检（【linter】判据的最终判定）

签 G1 前跑确定性结构检查，把【linter】判据（段落缺/槽位空/draft-ux 枚举非法/功能无 AC/AC id 缺失或重号/开放问题未清零）一次性机械核定——这些是确定性的，**不再劳烦人或 subagent 肉眼扫**（子计划 3 已删 PRD 的 subagent 冷核）：

```bash
node scripts/check-docs.js --prd iterations/vN/prd.md
```

- 退出码 0（全 pass）→【linter】判据全部通过；语义判据由你（产品）确认后直进 Step 8 签字。
- 退出码 1（有 FAIL）→ 按报告逐条修 `prd.md`，重跑，直到 0。**不得手改报告、不得跳过。**

> 交叉对账（PRD `涉及实体` ↔ TRD `### 表`）此刻无法跑——TRD 尚不存在，留到 `draft-tech-design` 阶段两文件齐备时由那边的 linter 步骤执行。
> linter 只覆盖结构/一致性判据；**语义判据**（场景5要素/三角评估/AC 是否用户真要的；以及 linter 受限标签的括注部分：`入口` 是否明确指向触发来源、含新页面/多分支的功能 `draft-ux` 该不该是"需要"）由你在逐功能确认（Step 4）中把关、签字时复核——无需另派 subagent。
> 项目仓无 `scripts/check-docs.js`（存量项目未铺）→ 退回 `../hact-method/skeleton/06-gates.md` §7 G1/G2 段的人工逐条核对兜底（无 subagent），并提示"建议补铺 linter（见 init-project Step 3）"，不阻断。

---

### Step 8：G1

> **签字前置**：Step 7.4 linter 退出码 0（【linter】判据全过）+ 语义判据你已确认。

```
✅ PRD v{N} 完成：[功能数量] 个功能，开放问题已清零，视觉规格 [已/未] 输出。
要签 G1 吗？
```

🚫 等用户确认

用户确认 → 在 `iterations/vN/gates.md` 写入：
```markdown
- [x] G1：PRD 已确认 — {YYYY-MM-DD}
```

**更新项目根 `status.yml`**（机器侧状态契约，项目级单文件，由 init-project 创建；字段见 `../hact-method/skeleton/07-status-contract.md`；文件不存在则先从 `../hact-method/templates/status.yml` 补建）：
- 确保 `iterations.vN.gates` 块存在（v1 已由 init-project 建好；v2+ 在此新增该期 gates 块，G1–G5 全未签）
- 将 `iterations.vN.gates.G1` 改为 `{ signed: true, date: {YYYY-MM-DD} }`

执行 `git add iterations/vN/prd.md iterations/vN/gates.md status.yml && git commit -m "feat(prd): v{N} PRD 完成，G1 签署 [{项目名}]" && git push`

> **异常**：PRD 定稿后发现遗漏关键功能 → 创建 `revise-doc(target=prd)` task，不直接修改已签 G1 的 PRD。

**feedback 检查**（签 G1 后）：
- 场景还原需要超过 3 轮追问才确认 → 说明需求描述质量有提升空间，写入 `feedback.md`（格式：`{日期} | {发现} | 建议在下次 PRD 开始时要求提前准备场景描述`）
- 某类开放问题反复出现 → 写入 `feedback.md`，标注应在哪个环节提前明确
- 无发现 → 跳过

移交：「PRD 完成，下一步 `draft-tech-design`。」

## Subagent 使用

## 上下文管理

- 骨架确认后（Step 3 结束、Step 4 开始前）做一次 compact——场景还原和讨论过程可压缩，功能契约写作阶段需要保持完整上下文以确保跨功能一致性
- compact 前在 `_meta/sessions/draft-prd-progress.md` 记录：已确认的功能清单 + 各功能的骨架一句话描述 + MVP 排除项

**断点续做**：
- 读 `iterations/vN/prd.md`（内容存在 → 已过 Step 4）
- 读 `iterations/vN/gates.md`（G1 已签 → 任务完成）
- 读 `_meta/sessions/draft-prd-progress.md` 了解上次停在哪个功能
- 从未完成的功能继续，不重做已确认的内容
