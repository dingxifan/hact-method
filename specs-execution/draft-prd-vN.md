# exec: draft-prd-vN

> CC 加载本文时，当前任务是通过三层渐进结构完成本期 PRD，签 G1。
> 三层顺序：**骨架**（方向对齐）→ **结构层**（功能契约）→ **收尾**（开放问题清零 + G1）

**上下文密度**：中。对话驱动，轮次多但单轮不重。需在关键节点阻断等待用户确认。

---

## 步骤追踪协议

每步完成后输出：
```
✅ [步骤名] 完成：[2–3 句结论]
→ 下一步：[步骤名] — [一句说明]
继续？
```
🚫 标记处必须等用户明确回应后才继续。

---

## 会话启动

**第一步：读目录结构**（先 Glob 看全局，不要只读单个文件）：

```
Glob: iterations/**
Glob: _meta/input/*
```

**第二步：状态判断**（按顺序）：

**先决检查**：确认项目目录结构存在（`iterations/` 目录或 `project.md` 文件存在）。
不存在 → 阻断：「项目尚未初始化，请先执行 init-project 创建项目仓结构。」

| 观察到的状态 | 结论 | 处理方式 |
|-------------|------|---------|
| `iterations/` 为空 或 不存在 | 首期项目，v1 | 直接开始，version = v1 |
| `iterations/v1/` 存在但无 `gates.md` | v1 进行中，未签 G1 | 读已有内容，从断点接续 |
| `iterations/v1/gates.md` 含 `G1: ✓` | v1 PRD 已完成 | 告知用户，询问是否开始 v2 |
| `iterations/vN/` 存在，G1 已签 | 迭代项目，version = vN+1 | 读 `project.md` 了解现状，再开始 |

> ⚠️ `project.md` 内容为"未开始"是**首期正常状态**，不是"项目未初始化"的标志。判断是否初始化应看目录结构是否存在，不看 project.md 内容。

**第三步：加载上下文**：
- 首期项目 → 读 `_meta/input/background.md`（如存在）
- 迭代项目 → 读 `project.md` 了解已有产品现状和已排除功能

开场说：「本次任务是完成 v{N} PRD。我会分三层推进：先对齐产品方向骨架，再逐功能写完整契约，最后清零开放问题签 G1。」

确认版本号后开始。

---

## 第一层：骨架（方向对齐）

### Step 1：场景还原

用「谁 / 情境 / 问题 / 现有解法 / 不足」五要素还原需求背景，输出格式：

```
用户：{画像}
情境：{使用场景}
问题：{核心痛点}
现有解法：{现在怎么做的}
不足：{为什么现有解法不够}
```

五要素不完整则继续追问，不跳过。迭代项目需说明"本期在已有基础上解决什么新问题"。

🚫 等用户确认场景还原准确

---

### Step 2：发散 + 三角筛

列出 3–5 个可能解法，每个方案用三角评估：

```
方案 A：{一句话描述}
- D（用户价值）：{评估}
- F（技术可行性）：{评估，标注已知风险}
- V（业务可行性）：{评估}
推荐度：⭐⭐⭐ / ⭐⭐ / ⭐
```

给出推荐方案，说明理由。

🚫 等用户选定方向

---

### Step 3：输出 PRD 骨架

基于选定方向，输出骨架——**每个功能只写一句话**，不展开细节：

```markdown
## PRD 骨架 · v{N} · {项目名}

产品目标：{一句话}

目标用户：{一句话}

功能清单：
1. {功能名}：{一句话描述}
2. {功能名}：{一句话描述}
...

MVP 边界（不做什么）：
- {排除项}
```

功能数量超过 6 个时，主动建议拆期，提供优先级排序，等用户决策后再继续。

🚫 等用户确认骨架方向正确（功能范围、排除项）

---

## 第二层：结构层（功能契约）

### Step 4：逐功能展开

骨架确认后，**逐个功能**写完整定义，每个功能写完后单独确认再写下一个：

```markdown
### 功能 N：{功能名}

**场景**：{具体使用场景描述}

**Acceptance Criteria**：
- [ ] {可独立验证的条件 1}
- [ ] {可独立验证的条件 2}
- [ ] {可独立验证的条件 3}（3–5 条）

**用户故事**：作为 {用户类型}，我希望 {做什么}，以便 {达到什么目的}

**排除项**：本功能不包含 {具体排除内容}

**开放问题**：{此功能目前未确定的细节，无则写"无"}
```

🚫 每个功能写完后等用户确认，有修改则改完再继续下一个

---

### Step 5：视觉规格（首期项目必做，迭代项目按需）

**判断条件**：`project.md` 中无视觉规格记录，或本期有新页面 / 新组件类型。

四步完成视觉规格：
1. 让用户提供 1–3 个参考产品或截图
2. 提炼风格关键词（色系 / 字体感 / 间距风格 / 组件风格）
3. 逐节与用户确认（色彩 → 字体 → 间距 → 组件）
4. 写入 `design.md`

🚫 每节视觉规格确认后才写入，不一次性写完

---

## 第三层：收尾

### Step 6：汇总开放问题 + 清零

收集所有功能中标记的"开放问题"，逐条与用户确认：

- 有答案 → 更新对应功能定义
- 无法确定 → 记入 `backlog.md`，从 PRD 中移除

🚫 等所有开放问题处理完毕（PRD 中开放问题段落为空）

---

### Step 7：写文件 + 知识沉淀

将所有功能定义整合成完整 `prd.md`，写入 `iterations/vN/prd.md`。

更新 `project.md` 产品层（目标 / 用户 / 功能边界）。

---

### Step 8：G1

```
✅ PRD v{N} 完成：[功能数量] 个功能，开放问题已清零，视觉规格 [已/未] 输出。
要签 G1 吗？
```

🚫 等用户确认

用户确认 → 在 `iterations/vN/gates.md` 写入：
```markdown
- [x] G1：PRD 已确认 — {YYYY-MM-DD}
```
执行 `git add . && git commit -m "feat(prd): v{N} PRD 完成，G1 签署 [{项目名}]"`

**feedback 检查**（签 G1 后）：
- 场景还原需要超过 3 轮追问才确认 → 说明需求描述质量有提升空间，写入 `feedback.md`（格式：`{日期} | {发现} | 建议在下次 PRD 开始时要求提前准备场景描述`）
- 某类开放问题反复出现 → 写入 `feedback.md`，标注应在哪个环节提前明确
- 无发现 → 跳过

移交：「PRD 完成，下一步 `draft-tech-design`。」

---

## 红线

- **禁止跳过场景还原**：五要素（谁/情境/问题/现有解法/不足）不完整前不进入下一步，不以"大概理解了"替代明确确认
- **禁止带假设输出骨架**：场景未确认时不输出任何功能清单，哪怕用户催促
- **禁止跳过开放问题清零**：PRD 中开放问题段落不为空时不签 G1

---

## Subagent 使用

无。PRD 写作是纯对话过程，不需要 subagent。

## 上下文管理

- 骨架确认后（Step 3 结束、Step 4 开始前）做一次 compact——场景还原和讨论过程可压缩，功能契约写作阶段需要保持完整上下文以确保跨功能一致性
- compact 前在 `_meta/sessions/draft-prd-progress.md` 记录：已确认的功能清单 + 各功能的骨架一句话描述 + MVP 排除项

**断点续做**：
- 读 `iterations/vN/prd.md`（内容存在 → 已过 Step 4）
- 读 `iterations/vN/gates.md`（G1 已签 → 任务完成）
- 读 `_meta/sessions/draft-prd-progress.md` 了解上次停在哪个功能
- 从未完成的功能继续，不重做已确认的内容
