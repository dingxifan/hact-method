# exec: draft-ux

> CC 加载本文时，当前任务是从 PRD 出发，**以交互工程师身份**消化业务、构思画面、产出可交互 HTML 原型，为 TRD 提供业务依据。
>
> **角色姿态**：CC = 交互工程师；用户 = 客户。客户只参与上游业务沟通 + 下游设计稿走查，中间过程内部消化、不外露。

**上下文密度**：低-中。业务沟通多轮文字，内部消化不外露，最终交付 HTML 原型供用户走查。

---

## 红线

- **禁止跳过场景拆解和流程穿线直接出原型**：CC 内部消化必须穷举场景、连通流程，再生成画面
- **禁止只覆盖主路径**：所有替代路径（用户选择不同操作 / 不同入口）都必须在场景中穷举
- **禁止死路**：流程图分支必有明确去向；原型无死锚点（`href` 必有目标）
- **禁止系统内部逻辑混入**：场景和流程图只描述用户可见的操作与反馈，后端校验逻辑不出现
- **禁止让用户审查工作过程产物**：场景文字、流程图拓扑、ASCII 线框等需要"文字→画面"转换的产物不外露；对答只用中间产物（mini HTML / 小原型）或最终原型
- **禁止视觉创新**：视觉规范来自 `design.md`——CC 不在原型阶段做视觉创新（防漏服从、防迭代漂移）

## Step 1：业务沟通（含 design.md 视觉对接）

**目的**：把 PRD 没说清的业务问透，并定下视觉基调。

### Step 1.1：业务沟通

**涵盖参考清单**（CC 自判按需，不强制全覆盖）：

| 方面 | 例子 |
|------|------|
| 功能边界 | 这个功能负责什么、不负责什么 |
| 用户角色 | 谁会用、有几种角色 |
| 典型场景 | 用户主要从哪几条路径进入、做什么 |
| 业务约束 | 必须遵守的规则（删除前确认、金额上限、权限等） |
| 入口情况 | 从哪些页面 / 菜单进入 |
| 数据状态 | 初始 / 中间 / 最终态、空态 |
| 异常处理 | 可能出什么错、用户怎么知道 |

**进行方式**：自然对话，CC 主动按参考清单提问，多轮直到 CC 判"够了"。

### Step 1.2：业务理解总结

CC 觉得问够后，输出**业务理解总结**（结构化清单，按方面分段）：

```markdown
**业务理解总结 · v{N}**

- 功能边界：……
- 用户角色：……
- 典型场景：1. …… 2. …… 3. ……
- 业务约束：……
- 入口：……
- 异常处理：……
```

**不落盘**——临时对答手段。

🚫 等用户审业务理解总结：
- OK → 转 Step 1.3
- 改 → 按修改继续聊，刷新总结再审
- 主动加方面 → 加上继续

### Step 1.3：design.md 视觉对接

**若 `design.md` 已存在且填充充分**（v2/v3 迭代时通常如此）→ 跳过本子步，直接转 Step 2。

**否则**（首次做 UX，design.md 是空模板或缺失）：

CC 问 3–5 个视觉基调问题：

- 深色 / 浅色界面？
- 品牌主色（hex 或描述）？
- 字体偏向：正式 / 活泼？
- 圆角风格：硬朗 / 圆润？
- 控件密度：紧凑 / 宽松？

用户回答后，CC 写 `design.md` 初稿——填变量、给标准控件样例（按钮 / 输入框 / 卡片 / 表格）。

**落盘**：`design.md`（特例：项目级跨迭代文件，落盘规则之外）。

🚫 等用户审 design.md 初稿，OK 后转 Step 2。

## Step 2：CC 内部消化（不外露）

**目的**：CC 在内部把业务转成可生成原型的中间认知，**全程不展示给用户**。

**必走清单**（红线"禁止跳过"的具体形式）：

| # | 内部动作 | 颗粒度 |
|---|---------|--------|
| 1 | 场景拆解 | "用户从 X → 操作 Y → 到 Z" 内部清单（命名 S1/S2/…） |
| 2 | 流程穿线 | 连成路径，识别分叉/空态/错误，画 mermaid 内部草稿 |
| 3 | 画面构思 | **信息架构层为主**：承载方式（Drawer / 全页 / 内联）、区块组成（顶部信息卡 + 操作栏 + 列表） |

**组件细节（按钮位置、列宽等）留到 Step 4 HTML 原型阶段直接落**——不在 Step 2 把每个按钮位置先想清。

**结束出口（两选一）**：

| 出口 | 触发 | CC 动作 |
|------|------|---------|
| **X** | 识别到关键决策点（多种合理走法 + 影响下游多画面） | 告知用户「我识别到几个关键决策需要先对一下」→ 转 Step 3 |
| **Y** | 未识别到关键决策点 | 告知用户「业务理解和画面构思已就绪，准备出第一稿原型，可以吗？」→ 用户认同 → 转 Step 4 |

🚫 出口 Y 等用户认同；出口 X 用户知悉后直接进 Step 3。

---

## Step 3：关键决策中间产物对答（按需触发）

**触发**：仅当 Step 2 出口 X。

**典型决策示例**（帮 CC 识别 + 防漏识别）：

| 典型决策 | 选项 |
|---------|------|
| 表单承载方式 | Drawer / 全页跳转 / 居中弹窗 / 原地内联展开 |
| 列表组织粒度 | 一行一员工 / 一行一记录 / 分组折叠 |
| 多操作摆放 | 页面级 / 行级 / 工具栏 |
| 复杂数据呈现 | 卡片 / 表格 / 时间线 / 看板 |
| 多步流程编排 | 单页分区 / 分步向导 / Tab |

**中间产物形态**：

| 载体 | 何时用 | 约束 |
|------|--------|------|
| **mini HTML 片段**（默认） | 大多数决策 | 必须用 `design.md` 视觉变量（避免丑陋让用户分心）；单画面级（一区块/一表单） |
| **可点击小原型**（升级档） | 决策本身关于路径感（如"全页跳转 vs Drawer 哪个返回更顺"），不点不出感觉时 | 自包含 HTML，路径限定在该决策范围内 |

**禁止用结构化文字描述方案**（"方案 A：用 Drawer 承载；方案 B：全页跳转……"）——这等同于让用户做"文字→画面"转换，违红线 5。

**对答进行方式**：

- **一次一对一答**——CC 给 2-3 个方案（用中间产物呈现）→ 用户选 / 改方案 / 提第三方案 → 反复直到定
- **决策结论记录**：
  - 跨迭代影响 → 写入项目级 `decisions.md`
  - 单期影响 → 不落盘
- **全部决策对完** → CC 告知用户「关键决策已对完，准备出第一稿原型」→ 用户认同 → 转 Step 4

🚫 用户认同处。

## Step 4：生成 HTML 原型

**目的**：把 Step 1/2/3 全部定调一次性落到 `iterations/vN/prototype.html`。

**规模与组织**：单 HTML 文件、CSS/JS 内联、自包含；多画面用 vanilla JS 的"切换 div 显示/隐藏"机制。

**覆盖要求（红线性质）**：

| # | 要求 |
|---|------|
| 1 | 流程图每条路径都能在原型中走通，无死锚点 |
| 2 | 每画面信息架构落实（承载方式 / 区块组成） |
| 3 | Step 3 关键决策结论已落实 |
| 4 | 视觉规范落实（`design.md` 变量，无硬编码颜色/字号/间距） |
| 5 | 状态可见性（hover / focus / disabled / 空态 / 错误态） |
| 6 | 占位数据符合业务场景（"张三 / 工号 10086 / 财务部"，不是"xxx / yyy"） |

**动效**：Drawer 滑入、淡入等动效**可做**（提升体验把握），但成本不可控时跳过；不做动效不构成质量缺陷。

**CC 自检（写完后逻辑核查）**：

- 锚点连接性：每个 `href="#xxx"` 都能找到目标
- 路径覆盖：流程图每条路径都有对应 HTML 节点
- 状态可见性：每画面 hover/disabled/空态有对应 CSS 类
- 视觉规范遵守：grep `style=` 看有无硬编码颜色/字号

**不假装"浏览器打开"**——CC 不能真打开浏览器，只做逻辑核查。

**生成后**：转 Step 5。

## Step 5：用户走查 + 反馈调整

**CC 交付话术**：

> 「原型已生成：`iterations/vN/prototype.html`。请在浏览器打开走查。建议关注：
>
> - 业务路径是否符合预期
> - 信息架构是否清晰
> - 关键决策结论用起来是否顺
> - 视觉是否符合 design.md 基调
> - 状态可见性（空态/错误/禁用）是否够用
>
> 不强制按清单走，看到任何问题或不顺都可以提。」

**反馈调整循环**：

- 用户提反馈 → CC 逐条判：**改原型** / **记待办** / **认为属过度**
- 改完 → 让用户再走查
- 待办项 → 落到项目级 `backlog.md`（已有架构）
- 反复直到用户满意

**走查结束标志**：**用户主动说"OK 可以了"** → 转 Step 6。**不设 CC 主动判定**——是否结束由客户说了算。

🚫 用户"OK"处。

## Step 6：收尾移交

**先写 ux-flows.md 精简版**（从 CC 内部消化的场景拆解和流程穿线提炼），格式如下，仅两段：

````markdown
# UX Flows · v{N}

## 场景列表

### 功能：{功能名}
- S1：用户从 {入口}，执行 {操作}，到达 {去向}。
- S2：……

### 功能：{功能名}
- S3：……

## 流程图

```mermaid
flowchart TD
    ……
```
````

**完成判据自核**：

- prototype.html 在浏览器可走通全路径 ✓
- ux-flows.md 含场景命名表 + mermaid 流程图两段 ✓
- design.md 已存在并被原型实际使用（无硬编码颜色/字号） ✓
- 用户已确认走查 OK ✓
- 跨迭代影响的关键决策已写入 `decisions.md`（如有） ✓

**git commit**：

```bash
git add iterations/vN/ux-flows.md iterations/vN/prototype.html
# design.md 若 Step 1.3 已 commit 且本步无改动，则不再 add
git commit -m "feat(ux): v{N} 交互流程图 + 原型 [{项目名}]"
```

**输出**：

```
✅ draft-ux v{N} 完成：{功能数} 个功能，{场景数} 条场景，{路径数} 条流程路径；原型落实 design.md 视觉规范，全路径已用户走查确认。
```

**移交话术**：

> 「交互原型完成，下一步 `draft-tech-design`。TRD 接口设计时请参考 `ux-flows.md` 流程图和 `prototype.html` 确认前端数据需求与画面字段。」

## 边界场景

| 场景 | 处理方式 |
|------|---------|
| PRD 某功能描述过于模糊，无法在 Step 1 问清 | 阻断，列出具体问题，要求用户回 `draft-prd-vN` 先明确该功能再继续 |
| 流程图分支极多，mermaid 渲染混乱 | Step 6 落盘时拆为多张子图（按功能分），分别在 `ux-flows.md` 中呈现 |
| 用户在 Step 5 走查中提出原型外的视觉创新建议 | 红线 6 禁视觉创新——指引用户改 `design.md` 后再落到原型 |
| 用户认为某条场景不需要原型覆盖 | 在 Step 6 落盘的场景列表中标注"[跳过原型]"并注明原因，流程图中保留该路径 |
| 走查中发现 PRD 有逻辑矛盾 | 暂停，列出矛盾点，询问用户决策，不擅自取舍 |
| 用户希望直接看场景列表 / 流程图（违背新姿态） | 解释新姿态——这些是 CC 内部工作；如确实需要可在 Step 6 落盘后查看，但生成阶段不外露 |
