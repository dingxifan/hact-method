# findings — 地基层 + V0 走骨架

## 一、问题的根：跨切面关注点的"无人认领"盲区

起点是昨天（2026-06-28）的视觉地基三件套。把它放大看，它只是一类更普遍盲区的第一个被打疼的实例。

**质量防线按"东西的家住哪"分三种**：
| 家在哪 | 谁管 | 机制 |
|---|---|---|
| 每一行（哪写都得满足） | lint | 统一规则，跟切包正交 |
| 多个业务包（放任会重复） | 复用 | 收敛成一处权威源 |
| **全局根（不属于任何业务包）** | **地基** | 没人天生生产它，**必须专包认领** |

plan-sprint 按页/组件切包，切包只生产"挂在某页上的活"。住"全局根"的（reset、主题、错误形态、数据隔离）切包永远切不到 → 盲区在此繁殖。这就是 R2/R3。

## 二、盲区的两层楼：决策层 vs 落地层

- **落地层**（AC 质量线 / 独立审查 / lint / Gate）这一年建得很成功，但它们**全站在某个决策的下游**——验证"忠不忠实"，对决策的**缺席**天生失明。
- **缺失的决策不会以"检查失败"出现**：表现为 N 个各自局部自洽、却互相不一致的实现，每个单独都过审。任何单 PR 审查都看不到 PR 之间。
- 视觉地基好做，正因它的**决策层（design.md）早就存在**，昨天只补了落地层。交互/状态/错误形态是**两层楼都空**——这才是更深的洞。

## 三、形式模型（本轮核心产出）

### 五种形式 —「该用哪种形式不是你挑的，是业务代码怎么碰它决定的」
| 业务代码…… | 形式 | 例子 | 边的天然强度 |
|---|---|---|---|
| 说它 | 共享类型/词汇 | `AppError`/响应信封类型 | 弱（可不说）→ 加 lint |
| 穿过它 | 单例瓶颈 | 错误中间件、API client、鉴权拦截器、作用域 repo | **强**（只一个门） |
| 住进它 | 外壳 | `AppLayout`/路由外壳 | 强（不在里面就明显坏） |
| 被它笼罩 | 环境基线 | reset/主题/token | 中（能强行覆盖，lint 探） |
| 往里填 | 脚手架/义务 | 四态数据页 | 弱→中（可不用，得 check） |

### 强制边三档（这是诊断工具，不是描述）
1. **构造上不可能** —— 底料让违规根本写不出来（作用域焊进基类 repo；只开放 token API）。最强，无需巡逻。
2. **机械探测** —— 写得出但一写就红（stylelint 禁裸 hex）。视觉地基今天在这档。
3. **人审维度** —— 靠人看。最弱，会被橡皮章。

**用法**：对每块地基问"实际守在哪档 / 最高能守到哪档"，差距=风险=该投资处。能往上一档就别停下一档；安全项必须焊到构造级。

### 两个进料口
| 进料口 | 哪来 | 证据强度 | 在哪确认 |
|---|---|---|---|
| 技术内生 | 任何这个栈的应用都有（错误信封/分页/状态四态/视觉地基/请求管道/外壳） | 强（跨项目血债）→ 可做成清单 | 地基设计（V0） |
| 领域涌现 | 这个应用"是什么、解决什么"的早期探讨（核心实体/贯穿全局的作用域/业务状态机） | 弱（仅本项目早期判读） | init 共识讨论 |

**准入门槛（共用）**：已证明跨切面 + 稳定。证据不对称 → 技术内生敢前期多立；领域涌现只立瞎子可见的，含糊的留给 escape 提拔。领域涌现半边 = parked `2026-06-28-blueprint-layer` 的"领域地图 + 主数据 schema"精简版。

## 四、真项目实证（mail-ai + JHH-Nortion，2026-06-29 Explore 实测）

两个项目技术栈不同（mail-ai = NestJS+TypeORM+MySQL+Vue/EP；JHH = Next.js+NestJS+Supabase），却**各自独立长齐五种形式 + 领域涌现** → 形式表不是编的，是成熟项目实际组织方式。

**① 后端地基的真实形状 = 一条"瓶颈管道"**（前端对称 = 外壳 + http 单例 + 环境基线）：
```
请求 → 鉴权卫士 → 作用域注入 → 入参校验 → 【业务】 → 成功包装/异常包装 → 响应
```
- mail-ai：`JwtAuthGuard`(app.module.ts:105) → `AccountContextMiddleware`(:110) → 业务 → `SuccessInterceptor`/`GlobalExceptionFilter`(main.ts:16-17)
- JHH：`AuthGuard`(app.module.ts:43) → `ValidationPipe` → 业务 → `HttpExceptionFilter`(main.ts:18-19)
- 全在框架边界注册（APP_GUARD/useGlobalFilters）→ 全"构造上不可能"绕过。**这就是"建筑框架"的具体化。**

**② 异常处理 = 类+模块两角，承重的是模块（瓶颈）**：两个项目都没造胖 AppError，直接用框架内置异常 + 一个 filter 格式化。词汇可薄，瓶颈要实。

**③ 页面底板 = 三种形式叠在一起**：外壳(`AppLayout.vue`/`MainLayoutClient`) + 环境基线 + 四态脚手架。mail-ai `global.scss` 里赫然就是昨天 v8 缺的那套（`--el-color-primary:#3370ff`、"须在 EP css 之后"、reset、60 个 token）—— 昨天 hact-app 缺的，mail-ai 早有。

**④ 重点教训（核实过源码）：最重要的地基守在最弱的边上。**
- mail-ai 无 base repository，每个 service 方法手写 `where:{userId,accountId}`（archive-folders.service.ts）。TS 只强制**收到**参数，不强制**用进** where。
- **当场逮到约定已破**：同文件 `remove(id,userId)` 用 `where:{id,userId}`——**accountId 漏了**。
- JHH 同样：`.eq('user_id',userId)` 每个查询手敲（activities.service.ts:55/154/175/189…），无 base service。
- → **bar 不在上游立，再好的团队也默认滑到最省事的弱边。** 这是"地基蓝图必须在 PRD 前立 + 安全项焊构造级"的硬证据。Explore agent 把它误标"构造上不可能"，实为人审级，已核正。

## 五、为什么是"完整重构"而非"只写文档"（用户 D1）

- 只写 foundation.md（蓝图）= 只到 spec；下游若不真建，"在地基上累加"仍是口号。
- 真建出来 → ① "累加"变物理事实（V1 功能往跑通+测过+审过的真骨架上插）② 强制边在 build 时就被 develop 自带的独立审查拿应有档验收（mail-ai 的 remove 漏 accountId 在此进不了 V1）。
- 名字：**走骨架 / walking skeleton**（Cockburn）——穿透所有层、证明架构、不干实事的最小骨架。= 方法论自己的"搭骨架"+ `scaffold-first` 技能。

## 六、三个必须认的后果（诚实账，已和用户讲明）

1. **栈选型必须前移**：没定栈建不出 NestJS error filter；栈从 TRD 拎出来进地基设计。→ draft-tech-design 劈两半。
2. **视觉两趟**：主题框架 V0 建（占位 token），真值 draft-ux 填。接上昨天视觉地基包。
3. **过早抽象是本路最大悬崖**：解药 = walking skeleton 纪律——只建一根穿透到底的最薄切片，不建投机完整框架；活的，vN+1 增补。骨架"只立承重墙、不装修"。

## 八、命门：让"按规范做"成为最省力的路（用户 2026-06-29 输入，本设计的纲）

**核心原理**：消除重复/统一标准/降新人成本，从来不是靠"立规矩"（文档赶工期没人看）。唯一真起作用的逻辑：**把规范做成既成事实，让"图省事"和"守规范"变成同一条路。**

**检验标准（命门）**：> 一个图省事的人，不刻意遵守规范，顺手做出来的东西，有多大概率是合规的？概率越高，框架越成功。

**关键对接**：这个"概率"**就是我们的强制边档**，只是从背面说——
- 构造级 = 概率 ~100%（不合规写不出来）｜机械级 = 高（写得出但 merge 挡）｜人审级 = 低（靠人注意到）。
- 所以 foundation.md 的「实际档」列**本质就是在量这个概率**；foundation-review 就该直接问命门那句话。
- **审计对象是人类开发者的省力路径**——骨架虽由 CC（V0 develop）建，目的是让后续开发（现在 CC、五阶段后真人）顺手即合规。（方法论自己敢用重 spec，正因执行者是会读 spec 的 AI；项目框架必须靠"既成事实+范本+机器卡"，因为执行者是不读 spec 的人。）

**四机制 → 本设计覆盖审计**：
1. **代码生成消重** —— ✗ **整条拿掉（用户 2026-06-29 定）**。本环境 **CC 本身就是生成器**，"消除敲 CRUD 的劳动"已实测有效、早在享受，不搭模板生成器。连带"生成/手写隔离原则"也拿掉——其动机（重生成覆盖手改）因 CC 就地智能改而蒸发，剩下的分层价值 foundation 的"作用域 base repo"已含。**foundation.md 不加隔离行。**
   - ⚠️ **但留一笔账**：CC 替代了生成器的**劳动**，没替代它的**确定性一致**（模板生成器第 1 与第 50 个 CRUD 逐字节同；CC 每次新写 = 漂移源）。→ 一致性全压到 ②④、**尤其 ③** 头上。
2. **公共底座（框架只给一个工具、没别的选）** —— ✅ 已覆盖 = "穿过它/瓶颈 + 构造级"。
3. **标杆模块（活文档，人照例子学不照规范学）** —— ◐ 半覆盖 → **拿掉①后升为主力**：它是补 CC"功能模块长相漂移"的主防线（确定性生成器本免费给的一致，现在只能靠照抄范本 + lint 兜）。**补法**：V0 走骨架那根穿透切片建成**真实最小业务切片 + 按范本质量建**，登记进 reusables.md 当"参考实现/活文档"。
4. **工具卡（自动统一、红线挡 merge）** —— ✅ 已覆盖 = 机械级（check-*.js + 门卫 + lint）。

→ 收窄后净增量（① 已删）：**A** 命门当 foundation.md 的成功度量（头部写死那句 + 「实际档」列即概率答卷）；**B** V0 指定标杆切片（reusables 登记）；**C** foundation-review 直接问命门那句。

## 九、standards/reusables 的去向 + 设计/代码边界（用户 2026-06-29 两问）

**Q1 standards/reusables 还值多少**：没架空，**载荷重新分配**——地基层吸走"必须"那半（强边），standards/reusables 留"应该/可选"那半（弱边）。
- standards：从"执行机制（要人记的规矩）"→"**带执行者标注的索引 + 人审残量 + 设计理由**"，更短更诚实（散文→linter 那条线的延续）。提拔到构造/机械的条目降为说明；仍人审的（命名/日志粒度/品味）才是真载体。
- reusables：强制底料毕业进 foundation；reusables 留**真可选复用 + 标杆切片指针**。
- 三者边界（防打架）：**foundation.md=登记（哪块/什么边/什么形式）；standards=实现的具体编码约定；reusables=可选复用+标杆指针**，分层不重复（foundation 的"视觉地基"行指向 standards-frontend 的 stylelint 细则）。
- **「standards 诚实化」（每条标执行者）用户定先不动**，阶段 3 只搬不改。

**Q2 draft-foundation 产代码吗**：**不产，只产文档（设计）**。公共形式的代码（瓶颈管道/base repo/主题框架）是 **V0 `develop(source=foundation)`** 的活。理由 = 2026-06-16 铁律（设计预写代码=空中建筑，org-krm v5 15 条全废）+ 保 foundation-review 对抗审查。V0 与任何迭代同构：`draft-foundation(设计·G2) → develop(建·merged)`。连 lint/stylelint 配置也是"draft-foundation 在 standards 写明、V0 develop 接线"。

## 十、post-V0 地基如何增长（用户 2026-06-29 问，阶段 9 收口）

V0 只**建**地基；地基**长**的机制起初只对视觉半边接了线（plan-sprint design.md 变更触发），非视觉的（领域地图 + 错误信封/作用域/新跨切面）是"活文档"原则但无 spec 步喂它——真缺口。收口=与 V0 同构、摊进 V1+ 管线的两层：

| 触发 | 蓝图层（foundation.md 增补） | 底料层（建代码） |
|---|---|---|
| V1+ 设计期识别新跨切面关注点 | draft-tech-design Step7 增补（与 standards 对称、同 architecture、同准入门槛：已证明跨切面+稳定才进） | plan-sprint 拆地基跟进包（foundation.md 变更触发，泛化自视觉跟进包）→ develop 建 |
| 开发期 escape（强制边/审查逮到跳出地基） | feedback.md 注明"建议 foundation.md 增补"→ 下期 draft-tech-design 增补；紧急 revise-doc | 同上 |

要点：**准入门槛挡膨胀**（escape 驱动、只收稳定的）；复用现成机器（draft-tech-design 已增补 standards、plan-sprint 已有跟进包雏形、develop 已有 feedback 回流），增量主要是"foundation.md 纳入增补对象 + 跟进包从视觉泛化到全地基"。

## 七、几乎不需要新机器（降低重构成本的关键）

- 走骨架 = `develop(source=foundation)`，复用 develop 全套（写码+自测+独立审查+合并），只多一个 source 值 + foundation review brief。不新增 task type，不撞 #20。
- V0 = iteration v0（复用迭代一等公民结构，只是无 PRD/功能）。
