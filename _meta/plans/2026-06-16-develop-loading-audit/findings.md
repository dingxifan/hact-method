# findings · develop 预加载有效性 / 链路保真度审查

> 审查日期:2026-06-16 ｜ 对象:hact-method spec 本身（不含 hact-app 实例）
> 方法:三独立审查员并行(指针保真 / 链路损耗 / develop视角),各只读 spec、带各自对抗假设、互不通气
> 既有 `2026-06-06-method-audit`(全量广度 33 条)未覆盖本"信息保真度"透镜;本报告为聚焦补充

---

## 总览

用户原命题:**develop 阶段预加载的规则是否足够有效。**

审查结论:**有效性被一个结构性缺陷封顶。** 不是"加载太多淹没上下文"(那是误判,develop 是全流程加载最克制的一关),而是相反——**develop 的可见信息被一份白名单卡死,而决定这份白名单质量的上游环节没有任何保真闸门;更致命的是,唯一能兜底的质量网(Step 5.5 对抗审查)被刻意喂以和开发主线相同的贫信息,于是"网"和"盲区"是用同一个洞织出来的。**

三个审查员的对抗假设**全部成立**,且交叉命中。下面按"三角命中 → 单角发现 → 修复方向"组织。

---

## 🔴 三角交叉命中(三个审查员独立指向同一处 —— 最高优先级)

### X1. 对抗审查闭环盲点:质量网与开发盲区同源

- **命中者**:①(审的是代码 vs AC,不是指针 vs 源码)/ ②(发现4.1)/ ③(Step5.5 与主线共享盲区)
- **问题**:develop Step 5.5 对抗审查被设计成最后一道发现缺陷的网,但它的输入被严格限制为「任务包 AC + diff(+条件性 TRD 接口段)」,并明令「禁止传递任何关于实现意图的描述」。这意味着审查 sub-agent 和 develop 主线**共享同一个信息盲区**——都没有 PRD、没有完整 standards、没有 decisions.md。它能严密地证明"代码忠实于任务包 AC",却**结构性地无法发现"任务包 AC 本身已偏离 PRD"**。网是用和盲区同样的洞织的。
- **证据**:`develop.md:208-214`(严格限制传入)/ `develop.md:233-237`(5 类检查全以"AC 描述的行为"为基准)
- **严重度**:🔴 P0
- **为什么是 P0**:这是把后面所有损耗"锁死、不可发现"的总闸。哪怕上游漂移了,只要代码自洽满足那个漂移后的 AC,对抗审查输出 `findings: []`,平滑交付一个错的 PR。`develop.md:260` 的 revise-doc 逃生通道只在"同一阻断修 3 次仍出现"时触发,覆盖不到"代码顺利地满足了错 AC"这种最隐蔽的情形。

### X2. AC 验收主线在链路中段被物理切断

- **命中者**:②(发现2.1/2.2/5.1,headline)/ ③(产品意图层零接触)/ ①(无保真校验)
- **问题**:这是 X1 之所以致命的根因。追踪 AC 这条用户验收主线:
  - PRD 有 AC(G1 用户签字认可)
  - → draft-tech-design 写 TRD 的七段**没有一段承载 AC**,接口段只挂"服务于哪条 ux-flows 场景",不挂"满足哪条 PRD AC"→ **AC 在此被静默丢弃**(②发现1.1)
  - → plan-sprint 的必读文件清单**不含 prd.md**(只读 trd/standards/reusables/decisions/ux-flows)→ 它回不到 PRD(②发现5.2)
  - → 于是任务包的 `acceptance-criteria` 是 CC **从已剥离 AC 的 TRD 里重新发明的**,既不溯源 PRD AC,也无对齐校验
  - → develop + 对抗审查只认任务包 AC
- **证据**:`draft-tech-design.md:122-138`(七段无 AC)/ `plan-sprint.md:22-30`(必读不含 prd.md)/ `specs-structural/develop.md:36`(AC 字段只约束"3-5条可验证",不约束来源)
- **严重度**:🔴 P0
- **关键洞察**:全链路**无任何 AC 可追溯机制**——没有映射表、没有"任务包 AC 标注覆盖哪条 PRD AC"的要求,连机器契约 status.yml 的 tasks[] 都不承载 AC(②发现5.4)。G1 用户签字认可的内容,从 plan-sprint 起彻底退场、再无回链。

### X3. 加载指针只有"非空"闸门,没有"保真"闸门

- **命中者**:①(headline,reference/relevant-standards/ux-flows 全部)/ ②(发现3.1/3.2,ux-flows)/ ③(全局 standards 漏列即失明)
- **问题**:develop 的设计哲学是"精确指针 > 全量上下文",所以指针准不准直接决定 develop 读得对不对。但 plan-sprint 的字段完整性自检(`plan-sprint.md:126`)**只验"16 字段非空",不验保真**:
  - `reference` 填"全文-参考实现"(无具体行号、范围无限宽)→ 合规、可进 develop;develop 侧"只读 reference 行号范围",读错段或退化读全文,无回读校验
  - `relevant-standards` 漏点一个本该适用的 § → develop **静默不加载**那条强制规范(如 catch 块规范、DTO 验证),整条规范永不进入视野
  - 前端 ux-flows 行号靠 plan-sprint **手抄**进 reference("须补入"但无校验),漏抄则退化为 develop 侧脆弱的 title 字面匹配
- **证据**:`plan-sprint.md:126`(自检只到非空)/ `develop.md:71-73`(三条"只读 X 指向"全信任指针)/ `plan-sprint.md:128`("须补入" ux-flows,无 verify)
- **严重度**:🔴 P1
- **共性**:plan-sprint 自检是**存在性检查**,不是**保真性检查**;唯一的内容级闸门(api-contract 人工目检)也只是肉眼确认。

## ① 指针保真审查员 · 独有发现

- **files / context 字段同病**:结构层要求 `files` "精确到已知行号范围"、`context` 填"关键实现切入点",但自检同样只验非空,无校验其指向真实存在。(`specs-structural/develop.md:34,38`)严重度 中
- **api-contract 是唯一有闸门的指针,但闸门是人工目检**:"所有后端任务包写完后统一向用户确认字段结构"——非机器校验;且推导来源(前端 standards / 任务包 UI 描述)本身可能不全,漏字段则推导出的平铺结构就缺字段。(`plan-sprint.md:130-134`)严重度 中

## ② 链路损耗审查员 · 独有发现

- **疑点清单兜不住 AC 遗漏**:draft-tech-design 的疑点清单只问"技术边界不清晰的点",不问"PRD AC 漏没漏"——AC 即便清晰但被整条遗漏,疑点清单也不报。(`draft-tech-design.md:70-86`)严重度 中
- **plan-sprint 人工确认点不含 AC 对齐**:Step 2/2.5 用户确认的是"拆分粒度/依赖/交付方式",看不到 PRD AC↔任务包 AC 对照,无从发现漂移。(`plan-sprint.md:57-65`)严重度 中

## ③ develop 视角审查员 · 独有发现

- **后端从设计上拿不到分支路径**:draft-ux 红线明确"后端校验逻辑不出现在本产物中",而分支逻辑(取消/不同入口/失败回退)大量落在后端校验与状态流转上 → 2026-06-03 专为治"分支遗漏"加的 draft-ux,在后端实现侧**基本白加**。(draft-ux 红线 + `plan-sprint.md:128` 仅限 frontend)严重度 🔴 高
- **prototype.html 全程不进 develop**:draft-ux 三层中"让每条路径可走通"的最终可执行凭证,既不在精确加载、也不在对抗审查传入——穷举分支的成果彻底蒸发。(`develop.md:69-73,207-213`)严重度 中
- **全局横切 standards 无"通读建立全局感"步骤**:命名前缀/错误码体系/统一拦截器/分页/事务边界等横切约定,若没被显式列进 relevant-standards 就结构性失明,build/lint/type-check 不会报。严重度 🔴 高
- **16 字段是单任务局部视图,承载不了跨任务全局不变量**:多任务共享一张表/一个枚举/一个共享类型时,"谁是 source of truth、改了要同步哪些消费方"无字段承载;`known-risks`/`do-not` 都是任务内视角。(`specs-structural/develop.md:39-40`)严重度 高
- **无 design rationale 字段**:`description` 被刻意限制为"状态迁移"、剥离意图;多种合理实现路径中只有一种符合架构意图时,develop 无字段可依。严重度 中
- **decisions.md 不读**:可能"合理地"重新发明被架构决策否决过的方案。严重度 中
- **frontend 无对称的接口契约必填字段**:api-contract 只 backend 携带,frontend 并行开发且 backend 未合并时,手里没有权威接口形状,只能猜字段名/类型。严重度 中
- **backlog.md 只写不读**:develop 不知道这块代码上次留了什么坑。严重度 低
- **escalate-if / 上下文重置协议只对"撞墙"敏感**:触发器全是调试>20轮、改动超 files 3个、subagent 二次失败等显式失败信号;对"看不到全局却把 AC 字面实现得很顺、从而平滑做错方向"**完全不敏感**——而结构性盲区的定义就是 agent 意识不到。(`develop.md:428-432`)严重度 🔴 高

## 修复方向(spec 改动建议,本次只提方向不直接改)

按"治本→治标"排序:

1. **【治 X1+X2 根】给 AC 建立可追溯回链**。三选一或组合:
   - (a) draft-tech-design 七段增设"AC 覆盖映射"(每条 PRD AC → 哪个接口/模块满足),让 AC 不在 TRD 丢失;
   - (b) plan-sprint 必读文件加入 prd.md,任务包 AC 必须标注"覆盖 PRD 哪条 AC"(回链 ID);
   - (c) status.yml tasks[] 增 `prd_ac_ref` 字段,为将来 hact-app 做 traceability 留数据线。
   - 推荐 (b)——成本最低、直接打在断点上。

2. **【给 X1 的网补一个 source 兜底】**:develop Step 5.5 对抗审查,像现在条件性回注 TRD 接口段那样,**条件性回注 PRD 对应 AC**,至少让审查能抽查"任务包 AC 是否忠实于 PRD AC"。

3. **【治 X3】plan-sprint 字段自检从"非空"升级为"保真"**:增加可机械检查的判据——reference 必含行号、前端有分支的任务必链 ux-flows 行号、relevant-standards 至少覆盖 files 涉及文件所属的强制规范类。把静默漏读变成显式可查。

4. **【治 ③全局失明】**:在 standards-shared 里固定一节"全局横切约定"(命名/错误码/分页/事务边界等),约定 develop **每次必读**(不走 relevant-standards 白名单),给一个最小全局感锚点。

5. **【治后端分支白加】**:扩展 ux-flows 或在后端任务包增"分支/失败路径"必填项,让后端也拿得到替代路径。

6. **【治跨任务盲】**:任务包增"跨任务共享资产"字段(本任务改动的共享表/枚举/类型 + 其消费方任务 id),或令 develop 选择性读 decisions.md 中与 files 相关的决策。

> 这些都是 spec 层改动,需开 hact-method 方法论调整会话逐条议;本审查不直接改 spec。
