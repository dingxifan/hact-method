## 1. 问题一句话

跨前后端边界的用户输入字段，**归属权（用户说了算 / 系统说了算）从未被显式声明**；"前端可编辑、后端不一定听"这个第三状态本身就是缺陷。
机制层面：出 bug 的字段恰是 AI**看不见它是决策点**的字段——"根本看不见" > "知道但没说"。这种"看不见"来自训练先验、写在权重里，**同模型每个实例共享**。

> **关键纠正（旧稿 §1 措辞错误）**：解法**不是**"用机械触发器逼假设显式化"。机械化只是手段之一。真正抗盲区的本质是**穷举**（见 §2）。把"机械"当成抗盲区的标准，会误判 batch 1（AI 穷举层）"零达标"——其实它靠穷举免疫盲区，只是不靠脚本。

## 2. 核心框架：穷举原则（抗盲区的本质）

### 2.1 穷举消灭隐形

盲区靠"让某个字段显得平平无奇、可以跳过"藏身。一旦被强制**对每一个实例都说点什么**，"跳过那个不起眼的"这个选项就没了——你不需要事先知道 `to` 特殊，只需被逼着给每个字段填一格，填到 `to` 那格时埋着的决策自己浮出来。

→ **新上下文 subagent 治"锚定"（被原作者叙事带跑），治不了"盲区"（它自己也看不见）。** 任何"靠审查员自己注意到异常"的做法（"找 bug""列出你的隐性假设"）都依赖审查员先验、对真盲区无效。有效的唯一形状是**用结构把决策点逼到审查员面前、让它绕不过去**。

### 2.2 在"类别"高度僵化，在"实例"高度放开

这是"上机制又不僵化"的解：
- 在**实例**高度僵化（"检查 `to` 的归属权"）= 脆的死清单，只抓已知字段。✗
- 在**类别**高度僵化（"枚举每一个跨边界字段、逐个说归属谁"）= 一个**生成式穷举义务**，不是清单。✓

类别少数、缓增、可策展（归属 / null vs 缺省 / 时区单位 / 分页默认 / 错误 vs 空 …约 5–8 个）；实例无穷。机制加在"必须列全"上，判断完全放开。

### 2.3 穷举杀"跳过"，杀不了"自信填错"——两种失败模式要分开

| 失败模式 | 表现 | 解药 |
|---------|------|------|
| **盖橡皮章** | 偷懒、跳过 = **覆盖失败** | **机械化覆盖率**（数全集、缺则 FAIL） |
| **盲区** | 不跳过、但**误判** = **判断失败** | **从产物/代码倒逼具体结果**（spec-by-example 式：必须从 service 代码填出"用户改 to=X → 收件人是 ___"，由代码事实撞碎先验答案） |

→ 对本议题（隐性假设），**承重是"从代码倒逼具体结果"，覆盖率机械化是完整性保险**。两个都要，但别把覆盖率当主梁——它治盖章、不治盲区。

### 2.4 一原则两落地

机械层和审查层是**同一个动作在两个高度**——都是"穷举某类别、逐个表态"：
- **有外部锚**（如原型可编辑性）→ 自动化（linter）。
- **无锚**（只能人/AI 判）→ 交给带结构的审查员（强制穷举表 + 具体结果义务）。

不是"一部分机械、剩下靠感觉"，而是"处处穷举；有锚自动化，无锚交结构化审查员"。

### 2.5 边界：穷举只对"有限可枚举载体"的类别成立

| 类别 | 载体 | 穷举适用 |
|------|------|---------|
| 归属权 / null vs 缺省 / 时区单位 | 逐字段 | ✓ |
| 分页默认 / 错误 vs 空 | 逐接口 | ✓ |
| **并发谁赢** | 逐**对**写操作（组合爆炸） | ✗ |
| **排序稳定性** | 属性细微、无清晰"逐 X" | ✗ |

→ 涌现 / 交互态类别没有"逐个填一格"的天然载体，穷举退化成组合爆炸，只能退回"靠注意"——对盲区无效。**这条边界必须写进方法论**，否则拿穷举套并发会徒劳。

### 2.6 可持续性：穷举本身也会膨胀，用 task.type 路由化解

把"无限加 spec 字段"换成"一张缓增的类别表"是进步，但 5–8 类 × 每个 review 全字段穷举，**审查载荷自己会膨胀**——焦虑没消失，只是上移一层。
→ 复用**决策 #14「task.type 是路由键」**：类别按 task.type 路由（归属权只对含用户输入 DTO 的任务跑、分页只对列表接口跑），不在每个任务上跑每个类别。与 standards 加载方式同构，不是新机制。
→ 一个类别凭"跨项目反复复发"（harvest-notes / wrap-up 喂入）才挣得席位——和现有证据门纪律一致。增长的是类别表（每条是一个穷举义务），不是无限实例检查。

## 3. 范围声明（不声称什么）

**本方案只覆盖**：归属权里"**有外部锚（原型可编辑性）、因而可机械化**的 **honor 半**"——即"控件可编辑、后端却忽略"。

**明确不在范围、不声称解决**：
- **affordance 半**：用户本该能改某字段、但 UI 根本没给可编辑控件。它没有"可编辑控件"这个锚，是纯需求完整性问题，落 prd-review 现有"覆盖完整"类 + 用户拍板。L1/L2/L3/L4 都没真正针对它。
- **不可枚举类别**（并发 / 排序，§2.5）。
- **通用隐性假设**：归属权只是 §1 根机制的一个实例，且是少数自带外部锚的那个。我们**不声称解决了隐性假设问题**，只声称"抓住了带外部锚、因而可机械化的那一类"。

**残余的最后防线**（任何审查机制都闭合不了的真新颖盲区）：异构先验（换模型）+ Gate 上有真实世界上下文的人 + 生产反馈。正确姿态是**学习闭环**，不是闭合解——每个漏到生产、被真实世界抓回的新盲区，其价值是让你新增一个穷举类别，下次它就进了表。这正是 harvest-notes / continuous-learning 对准"隐性假设类别"。

> 写进方法论的一句话：**机械层穷举"有锚、能自动判"的类别；审查层穷举"无锚、只能人/AI 判"的类别；两者都靠穷举消灭隐形，而非靠注意力。审查的机制化加在覆盖率（必须列全）上，不加在结论上。新盲区不靠当场聪明抓，靠生产反馈升格成下一个穷举类别。**

### 5.1 keystone 怎么落（可编辑性如何被可靠捕获）
> ⏸ **本轮推迟（§0-C），不讨论。** 类7 建议级不依赖它；它是第二批 honor 半机械链的锚。
候选（须明选，含技术债记账）：
- **(a) 解析 HTML**：引轻量 HTML 解析依赖——违背 zero-dependency linter 风格、增技术债。
- **(b) 退回 subagent**：把"可编辑性 ↔ owner 标签一致"留 prototype-review subagent——符合现架构分工，但这块退回 AI 判断、不再是纯机械锚。
- **(c) 生成时结构化落盘**：draft-ux 生成原型时同步写结构化"可编辑"字段，linter 只核结构化字段、不解析 HTML。
- **(d，我倾向)**：**数标签不解析语义**——正则数 `<input|<textarea|<select` 个数，要求 prototype-map 表行数 ≥ 控件数（覆盖下限，§2.3 的覆盖率机械化用到 keystone 自己身上）。健壮、避开脆正则、不碰语义。可与 (c) 组合。
> 利用"可编辑性非易感盲区"（4.1）：这一事实可信，故 (c)/(d) 足够，不必上 (a)。**待定**。

### 5.2 审查机制取舍与措辞（无锚层怎么穷举）
> ✅ **本轮已决（§0-B，针对类7 这一类）**：采 ①穷举表 + ②具体结果义务 + ④覆盖率自证 + 噪声纪律，上 develop-review + adversarial-review，建议级。形态与验证见 `sub-B-穷举表brief样板+验证.md`。

候选机制（按"是否真破盲区"排）：
- **① 强制穷举枚举表**（最强、通用）：brief 改"产出一张表，列出前端每个可提交字段 + service 在哪消费 + 标出凭空消失/被覆盖的"，输出物是穷举表。
