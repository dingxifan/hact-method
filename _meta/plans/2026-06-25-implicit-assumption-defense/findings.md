# findings · 隐性假设防线（读码后的事实约束）

> 这些是 2026-06-25 读 hact-method 现状文件后得到的、直接约束设计的事实。
> design.md 的取舍全部建立在此之上。读过即可，不重复推理。

## 起点

讨论原文：`E:\Group-code-lab\mail-ai\docs\superpowers\discussion-2026-06-25-implicit-assumptions.md`

一个 reply bug（前端可编辑 `to`、后端静默用 `original.fromAddress` 忽略 `dto.to`）暴露出一类设计缺陷：
**跨前后端边界的用户输入字段，归属权（用户说了算 / 系统说了算）从未被显式声明**。
更深一层是 AI 的隐性假设机制——出 bug 的字段恰恰是 AI**不觉得它是决策点**的字段（"根本看不见"，非"知道但没说"）。

## 收获 1 · prototype-map.md 不携带"可编辑"维度

`prototype-map.md`（draft-ux Step 4 产出，check-ux.js 校验）当前只有两段：

```
## 前端 AC 覆盖
| AC | 场景 | HTML 锚点 |     # 锚点是 #btn-create-user / #list-screen 这类按钮和屏幕
## 排除 AC
| AC | 排除原因 |
```

可编辑控件（`<input>/<textarea>`）只活在 `prototype.html` 原始 HTML 里，**没有被抽进机器可读层**。
→ 把 prototype-map 当"可编辑字段触发锚"是**真 ADD**，不是顺手读现成数据。

## 收获 2 · TRD 请求体是自由文本，但有可抄的轻量 pattern

`templates/trd.md` 接口设计段：请求体 = 一个 `<待填>`，无字段级结构，**今天没有挂归属权的槽**。
但 TRD 里 `# 满足 AC：AC-01` 回链行是现成 pattern——check-docs.js 全局扫该行做对账、载体无关。
→ 归属权可走同款**一行轻量注解**，不必上整张结构化表。压低了第二批成本。

## 收获 3 · develop-review.md 6 类检查对 reply bug 全部放行

逐类过 `templates/review-briefs/develop-review.md`：

| 类 | 对 reply bug | 结果 |
|----|------------|------|
| 1 AC忠实性 | reply 功能确实实现了 | 过 |
| 3 标准合规 | 没违反响应格式/错误码 | 过 |
| 4 测试品类 | "reply 能发出"测试绿 | 过 |
| 2/5/6 | 够不着 | — |

→ **6 类全过，bug 溜过**。"用户输入去向追踪"是结构性缺失的维度，不在现有任何一类里。

## 收获 4 · 方向 B 能脱离声明独立先发（降级但真实）

develop-review 派的 subagent 自读 `git diff` + 任务包 `files`，请求 DTO 与 service 代码都在其中。
逐字段追踪"前端传入字段，service 消费了吗"是**纯机械、零新声明**。对 reply bug：`dto.to` 在 DTO 里、service 从不读它 → 当场抓到。
差别只在判级：无归属权声明 → 输出**建议**（留人判）；有声明且被违反 → **阻断**（机械确定）。
→ 选项 A（声明）是把方向 B 从启发式建议升级成机械阻断的**硬化补丁**，不是方向 B 的前提。这是分两批的依据。

## 收获 5 · 归属权声明的家在 TRD 边界，且单靠后端声明会被同向盲区骗过

归属权是前后端**边界字段**属性，得声明在字段名规范化、跨界真正发生处 = TRD 请求体。
prototype-map 是纯前端视角，不知道后端字段叫 `to` 还是 `toAddress`。
**关键**：若只在 TRD 声明（后端单源），而 TRD 作者与开发者**共享同一盲区**（都以为 reply.to 系统说了算），TRD 会声明 system-owned、develop-review 据此放行、bug 照样上线。
只有"原型里该控件可编辑"这个**外部可观察事实**与 TRD 声明对账，才能抓住同向盲区。
→ 第二批的完整形态必须是**跨源对账**（prototype 可编辑 ↔ TRD 归属权），这也是它最贵、要延后的原因。

## 时序约束（设计硬约束）

`draft-ux`（产 prototype-map）**早于** `draft-tech-design`（产 TRD/DTO）。
→ prototype-map 阶段 DTO 字段名还不存在，prototype-map 不能引用后端字段名。
→ 跨源 join 只能在 TRD 阶段做（那时两件产物都在，且 draft-tech-design 本就要读原型）。

# 两轮独立审查的代码级发现（2026-06-25，附我方独立复核）

> 独立审查员两轮 + 我方复核。标「✓复核」= 我自己读了源码确认；标「采信」= 未亲自实读、采审查员引述。

## 审查发现（按严重度）

- 🔴 **F1 keystone 风险**（✓复核 check-ux.js 69–75 行）：抗"同向盲区"的全部重量压在 check-ux 能否可靠从 prototype.html 解析"控件可不可编辑"上，而它**现只 `fs.existsSync`、不解析内容**。现架构是**故意**把 HTML 语义判断交给 subagent（prototype-review brief 第 1 类）、不交 linter（正则切 HTML 易碎）。我设计稿 §5.1 把它写成小补丁，**严重低估**——它是 linter 第一次涉足 HTML 语义。**这是我漏掉的真缺陷。**
  - **我方拆分**：可编辑性 ≠ 归属权。可编辑性**不是易感盲区**（reply bug 里原型如实把 `to` 做成可编辑、翻车在后端），故它可生成时如实记录 / 机械计数 → keystone 风险可降（见 design §5.1 候选 d：数标签不解析语义）。
- 🔴 **F2 §1 措辞过度声称**：§1 说"用机械触发器逼显式化、不依赖 AI 自报盲点"，但 batch 1 三层全是"派新 AI 注意"。**张力**：审查员同时又说 L3 免疫盲区——两句靠"机械(脚本) vs AI"和"免疫 vs 易感"两根轴才不打架。**解**：用户的"穷举"综合——抗盲区本质是**穷举**不是机械化；机械化是穷举有外部锚的特例。L3（AI 穷举）合法抗盲区。
- 🟠 **F3 B 类裸奔**（✓复核 adversarial-review skill 独立 5 类清单）：reply bug 自己就是 bug-fix，新检查只改 develop-review.md，B 类修复路径不开火。一行同步即补。
- 🟠 **F4 join key 倒退**（✓复核 check-docs.js 用 AC-nn 稳定 id + 存量兜底）：§5.3 用中文语义名 join，是在用代码淘汰过自由文本 join 的同一文件里走回头路。改稳定 id（FIELD-01）。
- 🟡 **F5 L1 弱 / L2 缺输入**：L1（AC 组合涌现）对本 bug 类命中≈0（可编辑性非 PRD 级事实），是通用 PRD 改进、不该撑"4 层"叙事，真实覆盖≈1.5 层。L2 新类要对照 PRD 但 prototype-review【自读输入】只有 prototype-map+prototype.html、缺 prd.md（**采信，未实读**）。
- 🟡 **F6 观察门无仪表**：§6 判据没定义谁记/记哪/precision/阈值/sunset。SDD 的门自己得可验证。

## 穷举综合（用户第二轮，全稿最大进步）

- **穷举消灭隐形**：盲区靠"显得可跳过"藏身；强制对每个实例都表态，"跳过"选项消失，埋着的决策自浮。
- **新上下文治锚定、不治盲区**：盲区来自训练先验、同模型共享；换窗口同模型给同样自然的错答。靠"自己注意异常"的审查法对真盲区无效。
- **类别僵化 / 实例放开**：机制加在"必须穷举全集"，判断放开。类别少数缓增可策展、按 task.type 路由防审查载荷膨胀，凭跨项目复发挣席位。

## 我方与用户/审查员的实质分歧（待 §5 落地时权衡）

- **D1 ②>④（异议用户排序）**：穷举杀"跳过"、杀不了"自信填错"。用户称④（覆盖率机械化）是"桥"，但④治**盖橡皮章=覆盖失败**；本议题核心是**盲区=判断失败**，治它的是**②（从代码倒逼具体 Then）**。两失败模式被用户并到了一起。承重是②，④是完整性保险。
- **D2 穷举有"可枚举载体"边界**：只对逐字段/逐接口类别成立；并发（逐对写、组合爆炸）、排序（属性细微）无天然载体，穷举退化。须写进方法论。
- **D3 keystone 数标签而非解析**：把④用到 keystone 自己身上——数 `<input|<textarea|<select` 标签数 vs 表行数（覆盖下限），不语义解析"是否可编辑"。比审查员的 (a)/(b)/(c) 三选一多一条更健壮的路。
- **D4 比审查员更狠的诚实**：连 L3+L4 也只解归属权的 **honor 半**（后端听不听）；**affordance 半**（该不该给可编辑控件）无外部锚、是纯需求完整性问题，新层一个都没真正针对。真实范围比"1.5 层"还窄。

# 第二轮裁决（2026-06-25，落地执行）

> 见 design.md §0。两条与本 findings 直接相关：

- **AC 组合涌现砍除**（决议 A，强化 F5/D 视角）：不只"不计入覆盖"，是移除。它无可枚举封闭全集、判断型、命中≈0、且属"靠注意力"那一档——撞穷举原则反面（design §2.1）。这与 D1「②承重、靠注意力对盲区无效」一脉相承。若"滥用"关切要留，须以自带载体的新枚举类别走证据门重入（第三类 b）。
- **类7 sub-B 验证采纳，但只到"小样本通过"**（支撑决议 B 的诚实边界）：6–7 真实样本精确 2 真 / 0 误报，**但噪声纪律是从同批样本反推的**（CreateRuleDto 噪声 → "审计字段不在 DTO 全集"规则），故证明的是"加这三条纪律、这批样本干净"，**非"纪律已证泛化"**。④覆盖率机械核对类7 比 HTML 易但非免费（NestJS `PartialType`/`OmitType`/继承字段令"数 DTO 属性"不平凡）——故本轮④只做 subagent 自证、不上脚本。这两点是只上**建议级**、爆炸半径小的依据，别写成"已证 0 噪声"。
- **skill 类6 的 diff-only 局限**（执行时发现）：adversarial-review 原只喂 AC+diff，而类6 穷举需看 DTO 全集 + service 消费——常在 diff 之外（reply bug 修复 diff 多半不含 ReplyEmailDto 文件）。若不补，类6 对催生本议题的 bug 路径恰好 N/A，F3 落空。**已在 skill 指示 agent 可直接读 DTO 文件 + 消费它的 service 方法全文**（权威源码、非开发叙事，不损独立性），化解。这是比"一行同步"略大的改动，但不补则 F3 形同虚设。
