## F3 · 独立审查的输入必须是权威原文，唯一兜不住的留人门是「设计品味」（2026-06-20，develop 执行模型翻转）

**触发**：把 develop 改成"全自动 loop + 独立审查取代逐步人工门"时，用户追问「独立审查员的输入源自哪里」。

**结论一·独审输入 = 权威原文，绝不喂执行体自评**。若审查员读的是执行 subagent 的「我做完了」总结，就是自己批自己作业、独立性归零（= 2026-06-18「自己对抗自己有效吗」那条）。权威原文 = 任务包（该建什么）+ git diff（建成了什么）+ standards 章节（约定）+ 测试代码+结果（正确性证据）。审查员**自读**这些（review-briefs/ 的自包含 brief 模式），主线只告知 task-id+layer+vN。这把 sub5/sub6 留人的「逐条 AC 忠实性」从签字人手里接到独立对抗审查手里。

**结论二·全自动 loop 唯一兜不住的是「设计品味」**。代码正确性有权威原文可机械（test/lint）+ 可独立核（审查读 AC↔测试↔代码）；do-not 越界、范围蔓延、标准违规都能被独审事后逮。**唯独「视觉/交互到位不到位、是不是用户真要的」无权威原文**（design §10 归用户）——这是 AI 自洽 loop 唯一的盲区，故留人，且只需 **一个 upfront 门**：开跑前确认 design.md 覆盖本批次全部画面。设计到位 → 执行中就不会冒"无据可依的视觉决策"（把那个中途 🚫 前移成开跑前一次）。backend-only 批次连这门都不需要。

**结论三·三层防线防"AI 判 AI 盖章"**。方法论亲口记过 Gate 冷核协议是"用 AI 治 AI 盖章的反模式"。解法不是不用 AI 审，是**分层**：deterministic 绿先过 → 独审只做绿之上的**语义 top-up** + **对抗式**（prompt 存疑即打回）+ **有界 loop**（3 轮升级人/revise-doc）。独审不是唯一质量线。

**可复用性**：「独立审查输入取权威原文不取执行体自评」对所有"生成→审查"环节通用（PRD/TRD/任务包 review 已是此模式，develop 是第四个）。「唯一留人门 = 无权威原文的品味判断」可用来识别**任何**流程里哪些门能自动化、哪些必须留人——有权威原文（机械/独立可核）的门都能下放，无权威原文的品味门留人。

## F2 · PR 粒度 ≠ 会话容量（2026-06-20，develop 站「展开」讨论）

**触发**：撤销 sub7 家族拆分、把单/批量会话合一为「任务集」后，用户追问"这一轮对话计划吃几个任务，谁来定"。

**结论**：develop 把两个**正交**维度捏成了一件，是结构性混淆——

- **PR 粒度**：一个 PR 装几个任务，**依赖驱动**。plan-sprint Step2.5「交付独立/批量」就在定这个（独立=下游需其合并后才能开发；批量=同层无跨层调用可合一分支）。该 plan-sprint 管，已管。
- **会话容量**：一轮对话做几个任务，**上下文驱动**。一个 CC 会话的 context 装得下多少。**谁都没管**——被等式「批量组 = 一 PR = 一会话」悄悄吞掉。

现状的后果：批量组多大，纯看"本层恰好无阻断依赖的任务有几个"（可能 8 个），而一轮对话未必装得下；spec 对"装不下"只有**被动**应对（上下文重置协议=做爆才回退），无主动定标。

**处置方向（develop 站）**：拆开等式——PR 粒度留 plan-sprint（依赖），会话容量交 **develop 拾取时主动定标**（按 files 估改动面提议"装得下一轮"的依赖序前缀子集 + 🚫确认），剩余留下轮；一批次=一分支=一PR（批次名须按批次唯一，破 `{layer}-batch-vN` 撞车）。中间实现段是两级 subagent 循环（任务级/模块级），subagent 隔离越好→批次可越大，**定标与循环耦合、要一起设计**。详见 task_plan「Phase 2 进度 ②」。

**可复用性**：这条「交付/PR 粒度 是依赖问题，会话/执行容量 是上下文问题，别混」对其它"批量执行型"任务（如 generate-integration-tests 批量派修复、manual-test 批量验收）可能同样适用，留意。

## F1 · standards 项目级活文档不会「越来越大变得没意义」（2026-06-20，draft-tech-design 站）

**触发**：standards 从 `iterations/vN/` 归位到项目根活文档后，用户问「项目越来越大，这文件会不会也越来越大、变得没意义」。

**结论**：不会失去意义。真风险不是「大」，是「陈旧」。六点论证：

1. **standards 会饱和，PRD/TRD 不会**。PRD/TRD 按功能累积、随项目线性长；standards 是「怎么写代码」的约定（命名/错误码/响应格式/权限/测试框架），**早期立掉大部分、之后趋于饱和**——只在出现真新品类（WebSocket→实时约定、支付→金额处理）时加几条。**亚线性、有平台期**。

2. **它「大」是因为全都还活着——这恰是它有意义的原因**。v1 立的命名约定到 v5 仍管着代码（v1 代码还在仓里维护）。对比：v1 功能"做完了"是历史，v1 约定**仍在生效**。size 跟代码库成熟度走、且全部 live → 大≠堆死重，是「整库当前规则集」。

3. **消费模型决定「大」≠「重」**。唯一全读的是 plan-sprint（规划本就该通览全部约定来路由）；下游全切片读——develop **只读 `relevant-standards` 指的章节**（context 负载与文件大小无关）、pr-review 按 layer、manual-test 只读测试环境段。文件变大不膨胀这些环节上下文。

4. **per-iteration 在「大」上反而更糟**。旧模型每期是上期**近全量副本 + delta** → 总字节随迭代数**翻倍**，且过时规则**冻死在每个迭代文件夹、删不掉**。活文档总占用更小、可原地剪枝。per-iteration 从没解决 size，是乘法；活文档是加法且可减。

5. **真风险 = 陈旧不是大**。文件真「没意义」是攒了**矛盾/废弃**规则（v1 立、v4 偷偷弃用却没删）。这是维护失败、非 size 问题。而活文档恰是唯一能治它的（`revise-doc(target=standards)` 原地替换/删除）；副本模型让死规则永生。

6. **mega-project 单文件硌手 = 分域拆分的活，正交于本决策**。`standards-backend.md` → `standards-backend-{api,db,auth}.md`，且 `relevant-standards` 本是「文件+章节」指针、天然兼容拆分。属「疼了再拆」，现在 bake 进去是过度设计。

**未采纳的小护栏（用户判先不动）**：在 draft-tech-design Step 7 加一句「增补时顺手剪掉本期 TRD 已推翻的过时约定、冲突时替换而非并存」——直接对着真风险（陈旧）。**留待**：若实跑中发现 standards 攒陈旧，再补这条剪枝提示。与 2026-06-16 audit 的「全局横切约定段 develop 必读」可一并考虑（结构化 + 小全局段 + 可查细节段，是 standards 在规模下可导航的形态）。
