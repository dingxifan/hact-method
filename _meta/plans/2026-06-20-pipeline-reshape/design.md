## 一、现形状 vs 目标形状（一句话对照）

| | 现形状（满宽横片瀑布） | 目标形状（竖切片 + 脊柱） |
|---|---|---|
| 切片方向 | **横**：PRD 写全部功能 → TRD 写全部接口 → sprint 拆全部任务 → develop | **竖**：单功能从 PRD 一路打到测试绿，再下一个功能 |
| 反馈环 | 横跨整条流水线——PRD 埋的错拖到末端联调/验收才证伪 | 塌成"当场"——一个竖片走完就验，错在本片内暴露 |
| 质量验证 | **末端一道闸**（integration-tests + manual-test 才真验输出） | **最前立起的可执行不变量**，全程任何阶段可跑 |
| 共享地基 | 隐含在 TRD §数据库设计 + standards-shared，与接口同会话写 | **前期成批先冻**（走路骨架），竖片穿过它 |

§十四 的准确结论复述：**分步骤（有顺序）不是 bug**；bug 是 ① 切满宽横片 → 反馈环横跨流水线；② 质量是末端向前一道闸，而非最前立起、全程带着的可执行不变量。**改这两条，不取消阶段。**

## 二、目标形状的三件套（拆解）

### 2.1 走路骨架先行（shared-type-first，§十四 14.4-3 的硬障）
共享数据模型（User/Department/Task 等实体）必须先**整体自洽**才谈得上竖片并行——否则各片独立定义产生隐性漂移（findings §二原始硬障）。
- **映射现结构**：走路骨架 ≈ TRD `§数据库设计`（所有 `### 表`）+ `standards-shared`（命名/错误码/响应格式/权限）。
- **改动**：把这两块从"与接口同会话写"提成"**先写、先冻、后续全部引用**"。这正是 loop 第二层的前置，也是 `scaffold-first` 技能讲的同一件事——两条线在此接上。

### 2.2 功能竖片穿过骨架
骨架冻结后，每个功能作为一条竖片：PRD-片 → TRD-片（引用冻结骨架）→ 任务包 → 代码 → 测试绿。竖片之间反馈环独立、可并行（呼应决策#17 迭代并行 + 决策#13 任务一等公民）。

### 2.3 测试脊柱前置
AC→可执行测试**从最前立起**，一路当不变量带下去，任何阶段可跑。
- **治蒸馏的损**（14.3）：永不蒸馏测试——它可执行、原样带下、无损。被蒸馏的只是软叙述（理由/探索）。最该保住的"正确行为长什么样"恰是那条不被蒸馏的。
- **治瀑布的形**：测试从第 1 阶段在场，"对不对"变连续可答。
- **是 sub2「AC→可运行测试」的放大版**：当前建成的是**末端操作化**（压到 draft-tech-design 才把 AC 变例子）+ 一道验证步；要改成**拉到最前、当全局脊柱**。

## 三、对着现结构的四个硬冲突（核心——纲落地必须先答这四问）

### Q1 · Gate 怎么办？（G1–G5 是横向阶段闸，竖片穿过会撞它）
- **现状**：G1=PRD 签 / G2=TRD 签 / G3=sprint 签 / G4=验收 / G5=收尾，是**全局阶段栅栏**，强制 G1 先于 G2 先于 G3。
- **冲突**：竖片世界里功能 A 可能已到 G4（测试绿）而功能 B 还在 G1。阶段栅栏溶解。
- **但有现成伏笔**：决策#13 已把"Gate 退为聚合视图，Gate N = 所属 task 集合的状态聚合"。竖片只是把聚合的粒度从"全功能"换成"单功能"。
- **拍法（提议，待确认）**：Gate 从**阶段栅栏**进一步退成**每竖片的检查点序列**——每条竖片内部仍 G1→G2→…→G4 有序（逻辑依赖不消失，14.4-1），但竖片之间无全局栅栏。项目级 Gate 视图 = 所有竖片该 Gate 的聚合状态。**这是决策#13 的自然延伸，不是推翻。**

### Q2 · 迭代怎么放？（迭代是一等公民，决策#17）
- **拍法（提议）**：迭代 = 一批竖片 + 该批的走路骨架工作。骨架 = 前期成批段；竖片穿过它。迭代层级不变（projects → iterations → slices/tasks），只是 iteration 内的组织从"按阶段横切"变成"骨架 + N 竖片"。

### Q3 · 测试脊柱在哪一棒由谁写？（真 fork，§五 — 本稿最硬的一处）
"拉到最前"不能字面理解成让非技术的 PRD 作者写可执行测试。两条候选：
- **(a) 编译式**：AC 在 PRD 仍是散文 + Given/When/Then 例子（产品能用自然语言写例子）；首个技术棒（TRD/draft-tech-design）把例子**编译**成可执行测试，此后当活不变量带下、每阶段可跑。脊柱 = 例子，可执行形态是它的编译产物。
- **(b) 纯前置**：测试基建 + 可执行骨架测试在走路骨架阶段就建好，AC 例子直接挂上去跑红→实现→跑绿。
- **关系**：(a) 更贴 §14.3「spec-by-example 放大版」+ 产品/技术分工现实；(b) 更彻底但要求 PRD 阶段就有测试运行器。**sub2 已做了一半 (a)（Given/When/Then 写进任务包），差的是把操作化点从 TRD 提前 + 当活不变量而非一次性验证步。**

### Q4 · 走路骨架是不是新 task type？
- **拍法（提议）**：**不是新 task**。是把 draft-tech-design 的 Step 3 重排成 3a（先冻共享类型/schema/standards-shared）+ 3b（per-接口引用冻结块）。与 loop 第二层的 shared-type-first 重构同一处落点。这样重定形状**不新增 task 谱系**，只重排既有 task 内部 + 改切片粒度。

## 四、不可回避的真冲突（撞墙前要知道，14.1 + 14.4）

1. **蒸馏不是干净的赢**：上游"为什么这么定"被蒸馏掉后，develop 撞到 AC 没预料的边界要回推时真损失。脊柱兜的是"正确行为"，兜不了"当初的理由"。→ 蒸馏的边界要靠测试脊柱钉死"必须无损带过去的核心"，软叙述才敢砍。
2. **顺序不消失**（14.4-1）：仍需先需求→再接口→再代码。改的是切片方向（竖薄片），不是取消阶段。
3. **测试治不了"需求对不对"**（14.4-2）：只验"实现做对了 AC 说的事"，验不了"这条 AC 是不是用户真要的"。🚫 人类检查点照留，且本就在前面。
4. **共享地基 vs 薄切片打架**（14.4-3）：地基要前期成批，功能逻辑要薄竖片。故非"纯一次一片"，是"先立走路骨架 + 竖片穿过"。

## 五、sub7 同源陷阱仍在（重启纪律，承 findings §四）
重定形状极可能加大量编排/交接散文（骨架先行 + per-片流转 + 脊柱携带）。design §2 的成功货币仍是**净收缩**。
**纪律**：每落一处，先回答"这具体让我从哪份 spec 删掉哪条散文 / 删掉哪个末端验证步"。删得动才是兑现；删不动诚实记成"形状改进"（学 sub7 诚实账，**不再把 reorg 误框成净收缩**）。
**注意**：重定形状的主收益本就可能是"反馈环变短 + 蒸馏有锚"这种**结构/质量收益**，未必直接表现为行数净收缩——这点要提前对用户讲清，避免又出 sub7 的框定争议。

## 六、提议的第一步（待用户拍板——本稿真正的 fork）

重定形状是 14 份 spec 量级的改动，且有 hact-app v1–v4 存量在跑。结构性审查那一轮的纪律是 sub1→sub7 增量、隔离分支、保护存量——重定形状更该如此，不全量推倒。三条候选第一步：

- **甲 · 先做一次竖片演练（廉价闸，强烈推荐）**：拿 hact-app 一个真功能（如 v4 某功能），手工走一遍"骨架冻结 → 单功能竖片 → 测试脊柱前置 → 测试绿"，量出：① 反馈环真的短了吗 ② 测试脊柱前置具体让哪些末端验证步可删 ③ 撞到 §四-1 蒸馏损了吗。**防"形状重定在纸面成立、落地撞墙"，对应防 sub7 陷阱的演练闸。**
- **乙 · 先定测试脊柱（Q3）落点 + 建运行器 owner**：脊柱是三件套里最有删散文潜力的一件（永不蒸馏 + 取代末端验证步）。先把 Q3 (a)/(b) 拍死、把"测试运行器谁建"的悬空补上（sub2 对抗审查已暴露这个洞），再谈切片方向。
- **丙 · 先重排 draft-tech-design 成 shared-type-first**（Q4 落点 + loop 第二层前置）：从走路骨架这块最具体、边界最清的地方动手，做成后竖片才有骨架可穿。

> 三者非互斥：**甲（演练）→ 据演练结果在 乙/丙 之间排序**是最稳的组合，但成本最高。若想快出第一块可落地改动，丙 边界最清。
