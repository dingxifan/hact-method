# hact-method 主链路总览 · 内容稿（供视觉化用）

> 用途：本文件只定义**要传达什么、要包含哪些内容**，不规定任何视觉样式或交互方式——表现形式（布局/配色/动效/是否交互）完全交由设计端决定。
> 主题：把 hact-method「A 类完整迭代」的开发主链路讲清楚——每个环节做什么、入线（输入）是什么、出线（产物）是什么、质检怎么做。
> 数据来源：自读 6 份 specs-execution + skeleton/06-gates.md + templates/scripts/ 四个脚本 + 4 份 review-briefs + BRIEF #24（均为权威原文，非印象）。

## 一、这份图要传达的核心信息（设计端先理解再表达）

读者：方法论使用者 / 团队成员，要"一眼看懂整条开发流水线长什么样、质量是怎么被一关关守住的"。

要让人 get 到的三件事：

1. **主链路是一条有序流水线**：从需求到上线，9 个主环节按固定顺序串起，中间卡着 5 道 Gate。
2. **每个环节都有清晰的"入线 → 加工 → 出线"**：上一环节的产物是下一环节的输入，文件一路传递。
3. **质量不是末端一次性检查，而是层层前移、四类机制分工**：越往源头越便宜的检查越早做。这是本方法论最近一次重构的灵魂（见下「原点」）。

## 二、必须出现的全局概念

### 2.1 原点 · 三条北极星（整套质检设计的判据，建议作为引子/总纲呈现）

1. **质审前移**——在最便宜、最早处验证质量。坏 AC 应在需求阶段暴露，而非拖到联调 / 验收。
2. **质量控制 ≠ 规范控制**——验"产物是否真的正确"，靠确定性检查（test / linter / 一致性检查器）+ 精准输入，不靠再加散文规范。
3. **优化上下文 + 精准输入**——更小上下文、确定性验证器、喂 subagent 权威原文（而非自评 / 转述），是真正能改变 AI 行为的三个杠杆。

### 2.2 四类质检机制（贯穿全链路，是理解"质检怎么做"的图例/钥匙）

| 机制 | 一句话定义 | 由谁承担 |
|---|---|---|
| **确定性检查器（linter / test）** | 跑确定性代码核结构与正确性，跑一万次结果一致、不受上下文失真 | `check-docs.js` / `check-sprint.js` / `check-gate.js` + 项目侧 `build·type-check·lint·test` |
| **门卫（pre-commit hook）** | 签字 commit 时按暂存文件自动跑对应检查器，红则拦 commit——让"跑判官"成为提交的唯一出路（forcing function） | `pre-commit-hook.sh`（init-project 装入 `.git/hooks/`） |
| **独立对抗审查（subagent）** | 派全新隔离上下文的 subagent，**自读权威原文**、**拒收被审者自评**、默认假设"产物有问题"、存疑即阻断 | 各阶段的 review-brief（prd/trd/task-package/develop-review） |
| **人工门（签字 / 品味）** | 机器判不了的语义 / 产品 / 视觉品味，由对应职能的人确认并签字 | 用户 / 各 discipline 签字人 |

> 关键认识（值得在图上点出）：**Gate = 确定性检查器全绿 + 语义人签**；**独立审查不是"AI 治 AI 盖章"**，因为它读权威原文、拒收自评——盖章的病根恰恰是"喂自评给 AI"。

### 2.3 测试脊柱（一条贯穿四环节的红线，建议单独高亮）

一条不可视区 AC 的行为例子，无损穿过四个环节，最终物化成可运行测试——把"坏 AC"逼到最便宜处暴露：

`PRD 幕1（写 Given/When/Then 行为例子）` → `TRD 幕2（精化为技术精确规格：状态码/错误码/断言）` → `任务包（写进 acceptance-criteria + 回链 tag）` → `develop（1:1 物化成 runnable 测试并跑绿）`

要点：TRD 阶段**只精化规格、不写可运行测试**（预写测试 = 空中建筑）；runnable 物化推迟到 develop（代码存在后测试才稳）。

### 2.4 develop 的三层质量防线（本方法论最近砍掉独立 pr-review 后的质量结构，建议单独成块）

- **① 确定性绿（硬底）**：build / type-check / lint / test 全绿。执行 subagent 增量自绿 + 末端全量检测。
- **② 独立对抗审查（语义 top-up）**：全新隔离 subagent 自读权威原文（任务包 / diff / standards / 测试），对抗式找问题、拒收自评、存疑即阻断、3 轮回炉超界升级。
- **③ 人工门（仅 2 处）**：前端设计到位（开跑前）+ 安全敏感改动（权限/认证/数据隔离）合并前 architecture 裁决。其余全自动合并到 master。

## 三、主链路环节逐个内容（9 个主环节，按顺序）

> 说明：每个环节给「定位 / 做什么 / 入线 / 出线 / 质检明细 / 所属 Gate」。质检明细里每条都标了是四类机制中的哪一类。
> 流程顺序与 Gate 位置：
> `init-project → draft-prd-vN 【G1】 → (draft-ux 可选) → draft-tech-design 【G2】 → plan-sprint 【G3】 → develop → generate-integration-tests → manual-test 【G4】 → deploy + wrap-up-iteration 【G5】`

---

### 环节 0 · init-project（discipline: management）— 前置基建，无 Gate

- **做什么**：创建 `E:\group-code\{项目}\` 独立仓；把 `check-*.js` + `pre-commit-hook.sh` 铺入仓并装进 `.git/hooks/`；建 `status.yml` / `gates.md` 空桩、standards 三份空桩；登记成员个人 notes 仓。
- **入线**：`_meta/input/background.md`（需求背景）；hact-method 全套模板。
- **出线**：项目仓骨架（代码区 + `iterations/`）；`status.yml`（机器侧状态契约）；门卫 `.git/hooks/pre-commit` 已装。
- **质检**：本身是基建任务、无 Gate；但它**铺设了后续所有环节的确定性检查器与门卫**——是整条链路质检能力的源头（可在图上点出这层"地基"含义）。

---

### 环节 1 · draft-prd-vN（discipline: product）— 【Gate G1：PRD 通过】 ★测试脊柱起点

- **做什么**：三层渐进写 PRD。骨架（场景还原 → 三角筛选 → 功能清单）→ 结构层（逐功能写契约，每条有行为的 AC 紧跟 `例：Given/When/Then` 行为例子）→ 收尾（开放问题清零）。红线：写不出行为例子的"有行为"AC = 坏 AC，当场澄清。
- **入线**：`background.md`（首期）/ `project.md`（迭代）；模板 `templates/prd.md`。
- **出线**：`iterations/vN/prd.md`（含 `AC-nn` 全局唯一 id + 行为例子）；`gates.md` 写 G1 + `status.yml` gates.G1。
- **质检**：
  - 【确定性】`check-docs.js --prd`：6 段齐 / 功能槽（入口·涉及实体·draft-ux 枚举）/ 每功能 ≥1 AC / `AC-nn` 全局唯一 / 开放问题段已清空。
  - 【门卫】签 G1 的 commit 暂存 `prd.md` → 自动跑 check-docs、红则拦 commit。
  - 【独立审查】Step 7.5 派全新 subagent 读 `prd-review.md`，自读定稿 prd.md（陌生视角），查内部一致性 / AC 可验性 / 覆盖完整，输出问题清单（禁 pass 盖章）。
  - 【人工门】逐功能确认（增量锚定）+ G1 签字——"是否用户真要的"产品语义只有人能判。

---

### 环节 2 · draft-ux（discipline: dev-frontend）— 可选环节，无 Gate，插在 G1 与 G2 之间

- **做什么**：角色姿态——CC = 交互工程师，用户 = 客户。业务沟通（多轮文字）→ CC 内部消化（场景拆解 + 流程穿线 + 画面构思，全程不外露）→ 出 HTML 原型（落实 design.md 视觉规范）→ 用户走查反馈。
- **入线**：`prd.md`（功能标 `draft-ux: 需要`）；`design.md`（视觉规格，本环节 Step 1.3 顺手生成初稿）。
- **出线**：`iterations/vN/prototype.html`；`ux-flows.md`（场景命名表 + mermaid 流程图）。
- **质检**：【人工门】用户直接看原型 = **真陌生视角**，故去掉 subagent 冷审（模拟反而冗余）。红线 6 条（含禁死路 / 禁让用户审过程产物 / 禁视觉创新）。
- **条件**：PRD 全部功能标 `draft-ux: 不需要` 时整段跳过。

---

### 环节 3 · draft-tech-design（discipline: architecture）— 【Gate G2：TRD + standards 通过】 ★测试脊柱·幕2

- **做什么**：写 TRD + 三份 standards。骨架（架构轮廓）→ 完整 TRD（数据库 / 接口 / 模块，每接口挂 `# 满足 AC：AC-nn` 回链）→ standards 三份（项目根活文档，双源：公共模板 + 本人 notes `[规范]`）。幕2：不可视区 AC 的 PRD 行为例子**就地精化**为状态码 / 错误码 / 断言（只精化不创造，runnable 守 develop）。
- **入线**：`prd.md`（G1 已签）；`ux-flows.md` / `prototype.html`；standards 模板 + 个人 notes；模板 `templates/trd.md`。
- **出线**：`iterations/vN/trd.md`；项目根 `standards-{shared,frontend,backend}.md`（含「测试框架约定」）；`decisions.md`；G2。
- **质检**：
  - 【确定性】`check-docs.js prd trd`：TRD 7 段 + 表块 / 接口块结构；**交叉对账**——PRD 涉及实体 ↔ TRD 表；PRD `AC-nn` ↔ TRD 回链（逐条正向挡悬空 + 逐条反向验覆盖）。
  - 【门卫】签 G2 commit 暂存 trd.md → 复跑 check-docs 兜结构漂移、红则拦。
  - 【独立审查】Step 5 派 subagent 读 `trd-review.md`，自读 trd + prd，查内部一致性 / AC 真承接（非仅 id 在场）/ 字段满足画面 / 覆盖完整。
  - 【人工门】Step 6 用户确认 TRD + G2 签字；语义残量（载体真承接、精化忠实）由签字人复核。

---

### 环节 4 · plan-sprint（discipline: dispatch）— 【Gate G3：开发包就绪】 ★测试脊柱·载入任务包

- **做什么**：拆 develop 任务，写 17 字段任务包入 queue。骨架（任务清单 + 依赖 + 交付方式）→ 逐个写完整任务包（套模板；backend AC 携幕2 精化例子 + `(源：PRD AC-nn)` 回链 tag）→ sprint.md 汇总视图 + 填 status.yml tasks[]。
- **入线**：`prd.md` / `trd.md` / standards（G2 已签）；模板 `templates/queue/task-package.md`。
- **出线**：`iterations/vN/queue/*.md`（任务包，状态 [可取]）；`sprint.md` + `status.yml` tasks[] + G3。
- **质检**：
  - 【确定性】`check-sprint.js vN`：17 字段完备 / `reference` 含行号（前端 ux-flows、后端 trd）/ AC 回链 tag + 逐条 id 存在性 + 逐条反向覆盖 / `depends_on` 在册 / queue↔sprint↔status **三方一致**。
  - 【门卫】签 G3 commit 暂存 queue/ + sprint.md → 跑 check-sprint、红则拦。
  - 【独立审查】Step 3.5 派 subagent 读 `task-package-review.md`，自读 prd/trd/standards/queue，查 AC 忠实性 / AC 完备性 / api-contract 推导 / relevant-standards 覆盖；阻断即修、3 轮升级 revise-doc。
  - 【人工门】确认拆分粒度 / 依赖 / 交付方式 + G3 签字；逐条 AC 忠实性（内容真覆盖）由签字人确认。

---

### 环节 5 · develop（discipline: dev-frontend / dev-backend）— 无 Gate，终态 [merged] 自落定 ★测试脊柱物化点

- **做什么**：从 queue 拾一个任务集（size≥1），主线只**编排**。每任务两阶段：**阶段 A 执行 subagent**（隔离上下文：读懂 → 计划 + 复用 → 写 → 自绿，把 AC 例子 1:1 物化成 runnable 测试）→ **阶段 B 独立审查 subagent**（对抗式自读权威原文）。整批通过 + 末端全量绿 → 推 PR → **自合并到 master**。
- **入线**：`sprint.md` [可取] 任务（G3 已签）；任务包 + standards + `reference`；frontend 额外读 `design.md` 全文 + `prototype.html`。
- **出线**：代码 + 测试（合并入 master）；PR `[merged]`；`status.yml` status=merged + `code_reviews[]` 审计留痕。
- **质检（三层防线，见 §2.4）**：
  - 【确定性·防线①】build / type-check / lint / test 全绿——阶段 A 增量自绿 + 末端全量检测（覆盖集合全部改动 + 所有 AC 测试）。
  - 【独立审查·防线②】per-task 独立审查 subagent 读 `develop-review.md`，6 类（AC 忠实 / do-not 越界 / 标准合规 / 测试品类空缺 / 留人判项 / 设计保真），拒收执行体自评、存疑即阻断、3 轮回炉超界升级。
  - 【人工门·防线③，仅 2 处】① 前端设计到位（frontend 开跑前一次性确认）；② 安全敏感改动（权限/认证/数据隔离）合并前 architecture 裁决。其余直接自动合并。
- **说明**：无 Gate——砍除独立 pr-review 后，代码质量由 per-task 独审 + 全量绿把关，终态 `[merged]` 由 develop 自落定。

---

### 环节 6 · generate-integration-tests（discipline: integration-testing）— 无 Gate，是 G4 前置之一

- **做什么**：所有 sprint 任务合并后，生成脚本（后端 curl/.http + 前端 pinchtab，前端 ≤15 条场景）→ 按模块并行执行端到端 → 处理失败（[阻断] 走 develop 修复或快速通道直修；[不阻断] 记 backlog）→ 复测重跑全部 → 三条件确认。
- **入线**：`sprint.md` 全 `[merged]`；PRD AC / TRD 接口 / ux-flows / prototype；`backlog.md` 中 `[CR-建议]`。
- **出线**：`integration-tests/scripts-vN.md` + `result-{日期}.md`；`status.yml` integration_tests[]。
- **质检**：
  - 【确定性】端到端真实全栈跑（curl + pinchtab）——这是连接"不可视区"与"可视区"的桥，让后端正确性通过可视表面变得可观测。
  - 【人工门】三条件确认：所有场景有结论 / 主流程无 [阻断] / [不阻断] 已记 backlog 分级。

---

### 环节 7 · manual-test（discipline: product）— 【Gate G4：开发完成 + 验收通过】

- **做什么**：提供测试环境 → 告知验收范围（**聚焦可视区 + 业务可接受性**；不可视区 AC 已由测试脊柱 + 联调机械验过、不重复手验）→ 收集用户反馈派修复（快速通道直修 / develop 任务包）→ 用户明确"验收通过" → 写验收报告 + 签 G4。
- **入线**：`result-{日期}.md`（联调三条件满足）；`prd.md` acceptance criteria 段。
- **出线**：`iterations/vN/acceptance-report.md`；修复任务（source=manual-test）+ G4。
- **质检**：
  - 【确定性】`check-gate.js G4 vN`：source=manual-test 修复任务全 `merged` + 验收报告结论 = "通过"。
  - 【门卫】签 G4 commit 暂存 gates.md（新增 G4）→ 跑 check-gate、红则拦。
  - 【人工门】用户**人工验收可视区**（design 钉死"可视区留人走查"）+ 明确说"验收通过" + G4 签字——CC 不替用户判通过。

---

### 环节 8 · deploy + wrap-up-iteration（discipline: deploy / management）— 【Gate G5：迭代收尾】 ※两者并行

- **做什么**：
  - **deploy**：master 上"已验过"commit 一次性合并部署（pm2 重启后端 + nginx 前端，SSH MCP 执行）。
  - **wrap-up-iteration**：偏离对账（backlog `[偏离]`）+ feedback 分流（誊入成员个人 notes）+ project.md 跨迭代合并。
  - 两者并行、无强依赖（部署失败 / 纯文档迭代不阻断 G5）。
- **入线**：G4 已签（开发 + 验收完成）；`feedback.md` / `backlog.md`；`deployment.config`。
- **出线**：部署上线 + `deploy-log.md`；`project.md` 合并 + feedback 清空 + G5。
- **质检**：
  - 【确定性】`check-gate.js G5 vN`：`feedback.md` 已清空 + `project.md` 无"开发中"标注。
  - 【门卫】签 G5 commit 暂存 gates.md（新增 G5）→ 跑 check-gate、红则拦。
  - 【人工门】G5 签字；语义残量（backlog `[偏离]` 处理是否得当、feedback 分流是否准确）由签字人确认。

## 四、5 道 Gate 一览（可作为流程上的"关卡"标注）

| Gate | 内涵 | 签于哪个环节 | 确定性检查器 |
|---|---|---|---|
| G1 | 本期 PRD 通过 | draft-prd-vN 尾部 | check-docs.js（PRD） |
| G2 | 技术设计通过（TRD + standards） | draft-tech-design 尾部 | check-docs.js（PRD↔TRD 交叉） |
| G3 | 开发包就绪（sprint 拆解完成） | plan-sprint 尾部 | check-sprint.js |
| G4 | 开发完成（全 merged + 联调 + 人工验收） | manual-test 尾部 | check-gate.js G4 |
| G5 | 迭代收尾（偏离对账 + feedback 分流 + project.md 合并） | wrap-up-iteration 尾部 | check-gate.js G5 |

> 统一模型（值得呈现）：**每道 Gate = 对应检查器全绿（机械） + 语义残量由签字人确认（人工）**。门卫在签字 commit 时强制跑检查器，"跳过 linter 偷签"机制上做不到。

## 五、想强调的重点（供设计端决定如何突出，不规定怎么做）

1. **质检越往源头越早**：同一种缺陷（如坏 AC），在 PRD 阶段被行为例子 + prd-review 逼出，比拖到联调/验收便宜得多——这是整张图的灵魂，建议让"前移"这件事被一眼看到。
2. **四类质检机制的分工**：确定性检查器管"结构/正确对不对"、门卫管"强制跑"、独立审查管"语义内容有效性"、人工门管"品味/产品语义"。每个环节用到哪几类，是"质检怎么做"的核心信息。
3. **测试脊柱是一条贯穿线**，不是单点——它把 PRD / TRD / 任务包 / develop 四个环节串成一条"正确性"主轴。
4. **develop 是特殊环节**：无 Gate、全自动、三层防线、自合并到 master（治理上唯一保留的人工门是"安全敏感改动"）。
5. **入线↔出线的传递关系**：上一环节出线 = 下一环节入线（prd → trd → 任务包 → 代码 → 联调结果 → 验收报告），文件一路流动，建议让这种"接力"关系清晰。
