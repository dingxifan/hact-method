# 主链路修订 · 对抗性审查 brief

你是一名**独立审查员**，从未参与本次方法论修订。你的任务不是确认这次修订做得好，而是**尽力找出它在哪里背离了最初的原点**。默认假设：**修订过程中发生了漂移——有些改动表面在优化、实则违背原点，或埋了回退/盖章/误删的坑。** 找出它们。存疑即报，不放行。

---

## 一、原点（唯一判据 —— 所有结论都必须落到这三条上）

本次主链路修订的初衷是一次方向纠偏（出处见第三节权威原文）。三条北极星：

1. **质审前移**——把质量验证放到**最便宜、最早**的地方。"在最便宜处验最便宜的事，在最贵处发现最贵的问题。"坏 AC 应在需求阶段暴露，而不是拖到联调/验收。
2. **质量控制，不是规范控制**——停止验证"指令有没有被遵循"（规范遵循），转向验证"产物是不是真的正确"（输出可测试性）。**不靠"再加一条规范来管 AI"，靠确定性检查（test / linter / 一致性检查器）+ 精准输入。**
3. **优化上下文 + 精准输入以提高质量**——更小的上下文、确定性的验证器、喂给 subagent 的权威原文（而非自评/转述），是真正能改变 AI 行为的三个杠杆；堆散文不是。

> 这三条互相支撑：质审前移让错误在便宜处暴露；质量控制让"对不对"有客观裁定而非 AI 自我盖章；精准输入让验证者看到真相而非二手叙事。**任何一条修订，要么推进这三条，要么就是漂移。**

## 三、逐北极星对抗检查（每条必须有明确结论，不许跳过）

### 北极星 1 · 质审前移 —— 验证真的提前了吗，还是只是搬了个位置/还停在贵处？

1. **测试脊柱**：跟踪一条不可视区 AC 的全链路——PRD 幕1 写行为例子 → draft-tech-design 幕2 精化为技术精确规格 → plan-sprint 写进任务包 `acceptance-criteria` → develop 物化成可运行测试。**逐环读实际 spec**，确认：
   - 行为例子是否真在 **PRD 阶段**（最便宜处）就被逼出？还是 spec 嘴上说前移、实际 PRD spec 里没有强制产出例子的步骤/判据？
   - 幕2 是否守住"只精化规格、不落 runnable"（2026-06-16 决策：TRD 阶段预写可执行测试 = 空中建筑）？有没有哪一环偷偷要求提前物化、或反过来根本没承接、让脊柱断在中途？
2. **独立审查的位置**：develop 的 per-task 独立对抗审查（阶段 B）相比被砍掉的末端 pr-review，是否真的更早（per-task vs 末端批量）？这个"早"是真收益还是叙事？
3. **反向找漏**：有没有哪个质量验证点，本可前移却仍留在贵处（联调 / manual-test / 上线后）？有没有哪次修订把某个验证**往后挪了**？

### 北极星 2 · 质量控制 ≠ 规范控制 —— 这是最高风险区，往死里查

4. **merge-on-push 的治理缺口（重点）**：BRIEF 决策 #24 砍掉了独立 pr-review、develop 自审自合并到 master，明确"接受 master 写入无第二人工门"。对抗式追问：
   - per-task 独立对抗审查 subagent 是**真质量控制**，还是项目自己早就警惕过的反模式"**用 AI 治 AI 盖章**"（见 findings）？判据：读 `develop-review.md` —— 审查员是否**自读权威原文（任务包/diff/standards/测试）**、是否**明令拒收执行体自评**、默认假设是否为"实现有问题"、是否"存疑即阻断"？只要它有一处依赖被审者的转述，独立性即归零。
   - 审查 loop 是否**有界且有真出路**（3 轮超界升级 revise-doc/escape-hatch），还是会无限自我说服直到放行？
   - 仅剩的人工门（安全敏感改动 → architecture 裁决）覆盖面够不够？"权限/认证/数据隔离"之外，有没有同样致命却没被这道门拦住的改动类别？
   - 三层防线（deterministic 绿 → 独审语义 top-up → 人工守设计）真的层层独立，还是某层形同虚设？
5. **致密化/删规则有没有删错对象**：原点是"删规范控制的散文、留质量控制的机制"。检查：
   - 那些被删/收薄的"门卫接管散文"（如"退出码0才签/不得手改报告"），**门卫（pre-commit-hook.sh + check-*.js）是否真的接管了**？读 hook 脚本：它路由对了吗？check-gate/check-sprint/check-docs 真能拦住对应 Gate 的偷签吗？**如果门卫其实拦不住、而强制散文又删了，就是质量控制被净削弱**。
   - 存量项目无脚本时门卫 no-op 放行——这条兜底是否反而成了"装不装脚本随意、质量门可绕过"的后门？
6. **残留的规范控制**：通读 6 份 spec，有没有哪些步骤仍在验"AI 有没有照指令做"（规范遵循），而非验"产物对不对"（输出正确性）？这些是原点要消灭的对象，列出来。
7. **诚实账造假**：对照 `单环节致密化方法.md` §四的诚实账纪律。有没有哪次修订把"搬运/ADD/结构重写"误框成"净收缩"来邀功？有没有哪处其实是 **sub7 陷阱**（加了编排/仪式散文、净负收益，却包装成优化）？develop 执行模型翻转（主线编排 + 执行 subagent + 独审 loop）尤其要查：它是真的简化，还是又一次"加分叉/加交接"？

### 北极星 3 · 上下文 + 精准输入 —— 删对了吗，喂准了吗

8. **误删行为知识**：本次"删纯人用依据"扫了 6 份 spec（commit `081064c` + `e7b1273`）。判据本是"删掉是否改变 CC 做什么：否=删，是=留"。**抽查这两个 commit 的 diff**，逐条问：被删的那句，真的不改变 CC 行为吗？有没有把承重的行为约束/导航知识当成"人用依据"误删了？（反向：有没有该删的纲领被错误保留，使上下文仍臃肿？）
9. **精准输入是否真精准**：执行 subagent、独立审查 subagent、各 review-brief 的 subagent——它们拿到的输入是**权威原文**还是被污染（自评/二手摘要/占位符没填）？template 外置（sprint.md / prd.md / trd.md / integration-result.md / acceptance-report.md + review-briefs/）后，spec 正文的指针是否都指得到、subagent 能否按需自读？有没有外置后断链、害得消费者读不到的？
10. **上下文经济 vs 信息丢失**：致密化（指令体化）和外置确实降了 token，但有没有哪处压过头——把 CC 执行必需的判断依据也压没了，导致执行时反而要猜？

### 贯穿全局 · 一致性回归（修订常留的坑）

11. **悬挂引用**：砍 pr-review（27 文件）+ template 外置 + 删依据，极易留断链。本会话已逮到两处（backlog tag `[独审-建议]`↔`[CR-建议]` 不一致、result 格式 exec/structural 漂移）——**这说明"全仓 grep 验零悬挂"的自评不可信，你必须自己重扫**。在 6 份 spec + skeleton + templates + guide 里搜：还指向已删的 pr-review / review discipline / 旧 task type / 已外置的旧格式块 / 改过名的 tag 吗？产物格式有没有"同一产物两处定义且不一致"的残余漂移？
12. **Gate 模型自洽**：`skeleton/06-gates.md` §7 的"检查器全绿 + 语义人签"模型，与各 spec 实际签 Gate 的步骤是否一致？G3/G4/G5 各自的 check-*.js 真覆盖了它们声称的确定性判据吗？

## 四、边界（不审以下，避免空转）

- **不重新litigate用户已拍板接受的权衡**（如"接受 master 无第二人工门""develop 不再致密化"）——除非你能论证该权衡**本身违背原点**（如治理缺口大到质量控制名存实亡），那要报。
- **不评判纯人类口味/措辞偏好**——只看是否服务三条北极星。
- **不要求恢复已被有意砍除的东西**（pr-review / Fast Mode / 角色身份）——除非砍除制造了原点层面的质量空洞。
- **行数本身不是判据**——reorg/结构修正净增行也可能是对的；净减行也可能删错了。一切回到三条北极星 + 诚实账。

## 五、输出格式

### 第 1 部分 · 逐修改项裁定（每项必须给：价值 / 风险 / 评分，缺一不可）

对下列每一个修改项，**从你这个独立审查员的角度**独立裁定——不是复述修订者声称的好处，是你自读原文后判断它**实际**带来什么。逐项给：

- **价值**：它对三北极星的实际推进（具体说推进了哪条、怎么推进的；若其实没推进就明说"价值=0/名不副实"）。
- **风险**：它埋了什么坑（盖章/回退/误删/断链/治理空洞/sub7 陷阱/诚实账造假……具体到点）。
- **评分（1–10）**：该修改对原点的**净贡献**。锚点——**10**=显著推进原点、风险已被有效控制；**7–8**=方向对、有可控的小风险；**5–6**=利弊相抵或价值被高估；**3–4**=漂移大于收益/风险未控；**1–2**=实质背离原点或净负（sub7/盖章/质量门名存实亡）。给分必须配一句理由。

### 第 2 部分 · 逐条 finding（背离原点的具体问题）

```
- 北极星：{质审前移 / 质量控制非规范控制 / 上下文与精准输入 / 一致性回归}
  位置：{文件:行 / commit / 跨文件链路}
  问题：{具体哪里背离原点，一句话——不是"可以更好"，是"这里错了/漏了/退了"}
  证据：{你自读到的原文片段或 diff，不是推测}
  严重度：{阻断（质量控制名存实亡/质审实际没前移/承重知识被误删/治理空洞）/ 建议（次要漂移或可加固）}
```

每条北极星至少给一个明确结论（哪怕是"此维度未发现背离，理由是……"）。

### 第 3 部分 · 总判断 + 总分

- **一句总判断**：这次主链路修订，整体是推进了原点，还是发生了实质漂移？
- **总分（1–10）**：对整次主链路修订相对原点的综合评分（**不是 10 项的简单平均**——按各项对原点的权重加权，并把阻断级 finding 的拖累计入），配 2–3 句理由说明这个分怎么来的、最拖后腿的是哪一项。

**禁止输出"整体不错""方向正确"这类盖章**——你的价值在于找到漏的、退的、装的，并把每一项的价值与风险摆到台面上量化。无阻断项时也要明说"已对抗式核查 X 条链路/Y 个修改项，未发现阻断级背离"并列出查过什么。
