### [queue 任务包内的任务间依赖关系无统一机器可读格式]
**严重程度**: P1（重要漏洞）
**所在层**: specs-execution / specs-structural
**定位**: `specs-structural/plan-sprint.md §sprint.md 格式说明` + `specs-execution/develop.md §拾取任务`
**问题**: `sprint.md` 中 `依赖` 列是自由文本（填写 `task-id` 字符串），任务包 `known-risks` 字段也是自由文本；规范只说"被依赖任务先合并才能开始"，但没有定义：当同一个 queue 里有两个都标了 `交付=批量` 的任务、其中一个依赖另一个时，开发者该如何识别和验证这条依赖已被满足。任务包 16 字段中有 `depends-on` 字段（在 status.yml 契约中写为 `depends_on: []`），但任务包 `.md` 文件的字段列表（`specs-structural/develop.md §字段规范`）里没有这个字段，只存在于 `status.yml` 契约。两处定义没有对应，导致任务包文件里没地方写 `depends-on`，开发者只能靠读 `sprint.md` 的自然语言判断。

### [PR 被打回后的"结构性建议"：develop 和 pr-review 都没有明确的处理路径]
**严重程度**: P1（重要漏洞）
**所在层**: specs-execution
**定位**: `specs-execution/pr-review.md §升级条件` + `specs-execution/develop.md §上下文重置协议`
**问题**: `pr-review.md` 定义了两种打回情形：普通 `[阻断]` 和"升级条件（停止，等人介入）"。对于"CR 给出的是方案/结构层面的建议（不是简单的代码问题，但也没触发升级条件）"这个中间地带，规范没有明确指路。`pr-review.md §升级条件` 只覆盖安全敏感、和同一 `[阻断]` 三次仍未解决两种情况。开发者拿到包含结构性 CR 建议的打回后：是改了再次推 PR？是回退任务到 `[可取]` 让别人重做？还是先开 `revise-doc`？规范中这三条路径都有迹可循但都不完整。`develop.md` 的"阻塞于 revise-doc 结论"一节说"任务保持 `[taken-by]` 不变"，但没有覆盖"根因是在实现方案层而非文档层"的情形。

### [status.yml 并发更新：文件式软锁只保护任务拾取，不保护状态更新步骤]
**严重程度**: P1（重要漏洞）
**所在层**: specs-execution / skeleton
**定位**: `skeleton/05-state-machine.md §3 软锁机制` + `skeleton/07-status-contract.md §五、写入协议` + `specs-execution/develop.md §Step 8 更新状态`
**问题**: `05-state-machine.md` 的软锁机制只覆盖"拉任务"这个动作（`可取 → taken-by`），靠 git push 时序实现。但 `status.yml` 是项目级单文件，在多人并行开发场景下，两个开发者可能在同一天分别完成各自任务（Step 8），都要往 `status.yml` 的 `tasks[]` 写入自己任务的状态变更。两人各自在本地修改 `status.yml` 后 push，后 push 的人必然遭遇 git 冲突——规范对"非拾取动作的 status.yml 并发写入冲突"如何解决只字未提。`skeleton/05` 说"冲突时后到者重选任务"，但这是针对拾取冲突的，状态更新冲突性质不同（不能"重选"，只能解决冲突）。
**影响**: 在一个有 5-8 人并行开发的团队里，同一 sprint 期间多名开发者同时提交代码时频繁遭遇 `status.yml` git 冲突，且合并策略不明确，容易因为手动解决冲突时弄错字段值而导致 hact-app 取数错误。
