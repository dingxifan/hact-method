# 蓝图层与 hact-method 的关系 · 讨论小结

> 日期：2026-06-28　|　工作区：hact-method-lab
> 用途：本文是一次发散讨论的结论交接。后续将**另开工作区**专门讨论某个具体项目（中大型国际物流企业级 ERP）的蓝图。本文写成自包含，便于在新工作区里单独读取，不依赖原对话上下文。
> 性质：方法论层面的设计判断（不是某项目的蓝图本身）。

---

## 0. 起因

问题：要在 hact-method 基础上做一个**中大型国际物流企业级 ERP**，事先规划怎么做？

ERP 不是"更大的看板"，而是一堆子系统：订单(OMS)、运输(TMS)、仓储(WMS)、报关/清关、计费(freight/billing)、结算/财务、主数据(MDM)、对外集成网关(船司 EDI / 海关 / 报关行)，再叠多组织 / 多币种 / 多时区 / 多语言 / RBAC / 审计 / 合规。这些在第一个 `draft-prd-vN` 之前就得有答案。

由此聚焦到真正的话题：**"蓝图"这层规划和 hact-method 是什么关系？塞进方法论里撑得住吗？放外面又是什么关系？**

---

## 1. 核心判断：方法论缺一个"蓝图层"（Altitude 1）

hact-method 现在的"事先规划"全部发生在**单迭代尺度**：

```
init-project → draft-prd-vN(G1) → draft-ux → draft-tech-design(G2) → plan-sprint(G3) → develop → ...
```

它假设你能在一个迭代范围内把 PRD→TRD→sprint 一气呵成走完——这对 hact-app（一个看板）成立，对多子系统 ERP 不成立。

`project.md` / `decisions.md` 只是跨迭代快照，**不是一个被刻意生产出来的蓝图**。所以蓝图这层工作在方法论里目前**无家可归**。

---

## 2. 关键区分：收敛执行 vs 发散设计

这是整个讨论的转折点。

- **hact-method 的本体 = 收敛执行**：task 是一等公民，有清晰 spec、可重复、靠 task.type 路由，Gate 是 task 集合的聚合视图。整条流水线是"把已定的事按规格做出来"。
- **蓝图工作 = 发散设计**：一次性、高复杂、难标准化（切领域、定主数据契约、选贯穿切片）。

而方法论里**早就有一条线划开了这两种**——决策 #20：

> 方法论调整本身是发散性工作，没清晰 spec——由 management discipline 的 user 按需直接做，**无固定任务包**。本原则适用于**所有低频 + 复杂 + 难标准化的活动**。

**蓝图规划和"方法论调整"是同一个 profile。** 方法论自己其实已经回答了一半。

---

## 3. 三个位置及其受力分析

### A. 塞成流水线里的 task + Gate（如加 `draft-domain-map` / `draft-master-schema` task + G0）——撑不住

三个结构性受力点：

1. **Gate 模型会裂**：G = 某迭代 task 集合的状态聚合，是**迭代内**语义；蓝图是**跨迭代 / 前置于迭代**的，硬加 G0 不符合聚合语义，是挂在外面的假 Gate。
2. **数据模型没有这一层**：`projects → iterations → sprints/tasks` 没有"前置于 v1 的跨迭代设计产物"槽位；硬加会涟漪到 status.yml、init-project、hact-app 看板数据模型。
3. **和决策 #20 直接打架**：为低频 + 发散的活动写 spec，要么空洞（"认真想清楚领域边界"），要么变紧身衣（每个 ERP 领域切法都不一样）。这是 sub7 陷阱搬到方法论尺度。

### B. 放外面，当纯输入（background.md 的放大版）——撑得住，零改动，但最贵决定裸奔

蓝图随便用什么方式产出，作为 `_meta/input/` 材料喂进 `draft-prd-vN`，关系等同 background.md 之于迭代：**纯输入，方法论消费但不拥有、不生产、不治理**。

输入槽已存在（hact-app 当初就把 background.md 放进 `_meta/input/`），所以零改动。**代价**：项目里最贵的决定（主数据契约）落在所有质量机器之外——没 review、没 linter、没继承校验。ERP 里这恰恰最不该裸奔。

### C. 两者之间：#20 形态 + 极简治理（推荐落点）

- **蓝图当发散工作做**（不 task 化、不刚性 Gate），形态等同方法论调整：由 management + architecture discipline 在 v1 之前做。
- **产物大部分已经有家**：跨切面架构决策 → `decisions.md`；编码/技术约定 → `standards-*`；视觉 → `design.md`。
- **真正新增的只有两个产物**：
  1. **领域地图**（限界上下文 + 子系统归属）
  2. **主数据 schema**（跨子系统共享核心实体：货物 / 订单 / 运单 / 客户 / 组织 / 计费项 —— 归谁、长什么样、谁能改）
  
  这两份落项目根**活文档**，成为 v1 之后每个 `draft-prd-vN` / `draft-tech-design` 的**继承约束**（机制等同现在迭代读 standards / decisions）。
- **治理只投在主数据上**：给 master schema 配一道 review（复用现成 adversarial-review subagent 模式）+ 接上 parked 的 **schema 可视化工具**（蓝图阶段产 schema，工具养回敏感性、逮死表）。其余蓝图产物走 #20 的人工裁量，不上机器。

**这样方法论结构一行没动**——没新 task type、没 G0、没数据模型新层，只多"两份活文档 + 迭代继承它们"一条接线，而这条接线和"迭代继承 decisions/standards"是同一个机制。

---

## 4. 一句话收口

**蓝图不该是流水线里的一站，而该是流水线之上、和"方法论调整"同源的一类发散工作。** 方法论对它的关系，不是"包含一个阶段"，而是"消费两份活文档约束"（领域地图 + 主数据 schema）。

---

## 5. 蓝图本身该锁什么（也只该锁什么）

防止退回瀑布（方法论刻意反瀑布：iteration 一等公民、standards 边用边补）。原则：**重到足够锁住"贵且难改"的决定，轻到不退回瀑布。**

只锁三样最贵且最难改的：

1. **领域边界（限界上下文）**：把 ERP 切成子系统、画清谁拥有什么。后面所有 `draft-prd-vN` 的 scope 来源。
2. **主数据契约**：跨子系统共享核心实体的归属 / 形态 / 写权限。ERP 最贵的决定。
3. **上线序 + walking skeleton**：不是"先做完 OMS 再做 TMS"，而是先打通**一条贯穿全系统的最薄端到端业务线**（例："一票货：下单→配载→出运→报关→签收→计费→结算"只做骨架），用它验证子系统切分对不对；然后把各子系统映射到一串（可能并行的）iteration。

其余——字段细节、界面、非核心计费规则——**全部留给各子系统迭代涌现**，不进蓝图。

---

## 6. 顺带记下的两处"方法论会被 ERP 压出来的"伸缩点（本次未深入）

- **status.yml 会撑不住**：现为"项目级单文件"，对 hact-app 够用；ERP 多子系统 × 多条并行迭代线会变竞争热点 + 格式地狱，大概率要按子系统 / 产品线分区。
- **PRD 模板是 feature-centric**：ERP 的非功能性需求（多币种 / 时区 / 权限 / 审计 / EDI 对接）是一等公民，需要承载位置，不能在每个 feature 的 AC 里重复。

---

## 7. 新工作区接续时建议先钻的硬骨头

把第 3 节 C 的判断真正落地，唯一的硬骨头是这两份活文档：

- **领域地图**：具体长什么样、谁产、怎么进 init-project / 怎么被迭代继承。
- **主数据 schema**：形态、生命周期（v1 播种 / 后续增补）、与 schema 可视化工具如何咬合、那道 review 怎么配。

> 注意：本文是**方法论层面**的结论。新工作区要讨论的是**那个具体 ERP 项目的蓝图内容**（真去切它的领域、定它的主数据）。两者不要混——本文是"蓝图这层和方法论什么关系"的答案，不是"这个 ERP 的蓝图"。
