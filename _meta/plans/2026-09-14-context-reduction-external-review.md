## 一、总体结论

**这批瘦身站得住，而且方法本身比多数「精简」克制。** 三条证据：

1. **每条减法都有承接对象，且承接对象是既有的、不是新造的。** Standards 退役后接到 PRD/TRD、Foundation、`project.md` 技术层、任务 `do-not`、真实 check/test/config——五个都是原来就在跑的对象。没有为了删一个机制而立一个新机制，这是「瘦身」与「换个马甲」的分界线。

2. **有一张写明保障代价的处置表。** `_meta/plans/2026-09-06-review-trust-scope/审查机制处置表.md` 逐行给「当前承接环节 / 收益证据或重复 / 去向与保障代价 / 本批状态」。删 review profile 的理由写的是「已是候选却仍必生成；无已核实的独立缺陷命中收益」；合并接缝审查时直接写下「失去合并前独立上下文，问题发现后移到联调」。**把代价写进同一张表，才使这张表能被后来的人反驳。**

3. **有明确的不删清单。** 同一张表里，PRD 独审、TRD 独审、G3 整批任务包独审、per-task 代码独审四项都标了「三批：不并入」，理由是缺同类对照样本。能忍住不删的减法，比删得多的减法可信。

报告自身的诚实度同样是结论的一部分：「不是取消规格、取消独审、取消测试」「已完成的是规则与配套实现」「不能宣称全仓代码行数净减少」——这几句应当在后续任何转述里保留。

## 二、逐项评估

### 2.1 站得住，不需要附加条件

| 减法 | 判断依据 |
|---|---|
| **三个 Standards 全链退役** | 原链是「生成→匹配→回填→收缩审计」的自循环：`standards_checked` 的唯一消费者就是 Standards 自身，回填动作本身不产生缺陷命中。**承接不是纸面**——`init-project` Step 5 给每个项目播种 `foundation.md`（不只是走 V0 的），`draft-tech-design` 每期原地增补并立「应有档」，安全项仍是构造级不可议价。已沿这条链核到承接方真实存在。 |
| **review profile（强制 JSON / 生成器 / 分区·版本·继承校验）退役** | 机器生成的检查候选清单没有独立收益证据，却每次 full 必须产出。改由审查员按原始契约与实际改动选范围；失去的是机器候选清单这一项便利，不是检查职责。 |
| **逐维度「无发现」、逐字段填表、重复覆盖表取消** | 空结论不能证明查过。`develop-review-round.md` 仍要求 findings 有 evidence、`diff_sha256` 由真实 Git 对象机械重算、`conclusion: pass` 时不得残留 open blocking——硬约束一条没少。 |
| **status.yml 单源** | 删副本的同时补了「status-only 签署或新 merged 提交仍路由到对应 Gate/审查检查」，避免删掉双写后检查触发一并消失。这一步容易漏，这里没漏。 |
| **管理附加链退出必经**（notes 建仓、收割游标、学科准入、成本计时、feedback 清空、按数量归档） | 这批本来就是为完整性存在的强制项，没有一项是质量证据。`01-identity.md` 把权限收回「用户明确授权 + 仓库权限 + 保护分支」，`discipline` 降为可选知识索引，比原 `user_disciplines` 模型更接近现实。 |
| **审查信任前提收窄** | 本批价值最高的一条。`review-scope.md` 把「假设开发者有意绕过」排除出审查范围，掐掉了审查员无限加固的发散源；同时保留外部输入/越权/不可信代码执行，并写明「当前代码实际违规仍按原判级处理，不因可信豁免」。**更关键的是它防了自身滥用**：范围纠正须由隔离审查单元核实、沿用原 finding id、标 `verified-closed`、不清零已用轮次，主线不得自行删 finding。 |

### 2.2 成立，但需要在真实项目里盯

**① develop 长程自主执行。** 收益是实的——原来的停顿多半不是质量门，只是流程问句。护栏也配齐了：授权范围与当前批次分开记、结束判据三问、escape-hatch 区分「可恢复」与「必须由人」、失败与轮次「换会话/换工作树不清零」。

但**失败模式换了方向**：从「停太多」变成「悄悄多做」，而后者不可见。要盯的不是速度，是有没有出现超出 `files` 的静默扩围、以及「阶段性成功当完成」的声明。

**② B 类 `governed`。** 本批最大的一处松绑：共享契约的局部兼容变更进了无 Gate 通道。机械护栏是真的——`check-b-task.js` 对 governed 仍拦数据库 DDL 信号与禁止路径、强制 `asset-writes` 非空、并在固定 diff 上复核未声明文件。但判据「已有明确意图下的局部兼容」是语义判断，检查器自己声明「不能证明语义兼容」。

**真正的风险不是单次，是累计**：每次都兼容，若干次之后契约已经不是签过的那份。建议在 `wrap-up-iteration` 加一次本期 governed 包的汇总回看（只回看、不新增门）。

**③ 接缝审查并入联调。** 处置表的理由是「独立接缝审只记录了静态回放，未找到独有命中对照」——这是**没找到收益**，不等于**证明无收益**。成本确定、收益未证，删掉在账上说得通，报告也诚实写了「减少一个独立视角、发现时点后移」。

建议给它一个复评触发条件：**若联调阶段抓到一个本可在合并前发现的跨包缺陷，这条回滚。**

**④ V0 改为证据触发。** 方向对：V0 最容易膨胀成「提前做 V1」，「V1 会用」不再是理由、超过一个中型 develop 就继续删，都是对的约束。反向风险是该建的地基被判 `V1+`，而晚建代价真的发生；准入四条要同时满足，门槛偏严。

建议把每次判 `V1+` 的行留在 `foundation.md`（现行文本就是这么要求的），并在 wrap-up 回看有没有踩中——让这条形成闭环，而不是单向删减。

**⑤ 每任务 3 轮代码审查上限。** 防磨是必要的，「换 finding、根因、会话或工作树不清零」也堵住了刷轮。要防的是反向滥用：**为了不超轮，把 blocking 降成 advisory。** 现有文本没有对称约束。

### 2.3 一个值得补的缺口

**未走 V0 的项目里，新增地基行的「应有档」声明缺少等价的独审证据要求。**

- 走 V0 时：`templates/review-briefs/foundation-review.md` 要求判构造级/机械级前**亲手撞反例**、自绿须在干净环境复现（2026-07-12 收紧的成果）。
- 未走 V0 时：`specs-execution/draft-tech-design.md` 同样要求增补 `foundation.md` 并立应有档，且写明「≥机械级不能空口立，必须落到文件:行 / 规则名」。但承接这一步的 `templates/review-briefs/trd-review.md` 只核到「设计不得静默改变 Foundation 不变量」，**没有承接「档位声明需实证」这条**。

V0 既然改为不默认走，未走 V0 会成为常态，这个缺口的暴露面比改造前更大。修法很轻：在 `trd-review.md` 增一条——本期 `foundation.md` 若有新增行且声明 ≥ 机械级，须核其落地位置存在且能拦住所承诺范围。

**本次未实施**，留作后续决定。

## 四、建议的验证口径

报告第七节把账算得老实：正文净减 2,978 行，检查脚本 +821、测试 +938、过程记录 +2,109，合计 **+890**，并明确「不能宣称全仓代码行数净减少」。这个诚实度应当保持。

但有一个结构性问题：**本批同时动了六组机制，而四个关键指标一个都没有基线。** 多机制齐动 + 无度量 = 一旦出问题无法归因到具体哪条。

建议在下一个真实项目跑完一期时，只采集四个数——四个都能从现有的 round report、`status.yml`、PR 遗留问题与 `foundation.md` 里直接读出，不新增任何记录义务：

1. 重大缺陷的**发现时点**（合并前 / 联调 / 验收）——对应 2.2 ③ 是否回滚；
2. B 类 `governed` 包的**数量与累计契约面**——对应 2.2 ②；
3. 长程 develop 中**超出 `files` 的扩围次数**与「阶段性成功当完成」次数——对应 2.2 ①；
4. 被判 `V1+` 的地基行中**实际发生晚建代价的比例**——对应 2.2 ④。
