# 运行时适配分支 vs master：方法论差异讨论底稿

> 状态：讨论稿，不代表已决定移植或合并  
> 对比日期：2026-08-09  
> 主干：`master @ d4a3654`  
> 适配分支：`codex-runtime-adaptation @ ba00711`  
> 共同基点：`2d31383`  

## 一、这次对比要回答什么

本稿不是一般性的代码 diff 摘要，而是借两个分支在同一基点后的不同演进方向，讨论 hact-method 下一步的方法论形态：

1. 适配分支解决了什么结构性问题；
2. master 在适配分支分叉后又补上了哪些方法论能力；
3. 哪些内容应移植，哪些只能吸收语义、不能照搬字面实现；
4. 两条演进路线合并后，方法论的分层、证据和强制机制应该怎样重新定义。

本轮只形成讨论底稿，不执行分支合并，也不修改正式方法论正文。

## 二、核心判断

两个分支优化的不是同一个维度：

| 维度 | `codex-runtime-adaptation` | `master` 分叉后演进 |
|---|---|---|
| 主要问题 | 方法论正文与 Claude Code 的机制、称谓、模型名绑定 | 方法论现有环节在真实项目中出现漏判、假绿、失真和闭环断点 |
| 主要解法 | 能力接口抽象 + 运行时映射 + 双入口薄壳 + 防回潮检查 | 反例探针、穿透测试、检查器、欠账闭环、退役账、审计留痕 |
| 优化性质 | 架构性剥离、可移植性 | 经验驱动的判据收紧与机制补格 |
| 主要风险 | 抽象过度后丢失执行约束；映射表漂移 | 把 CC/模型/工具的具体实现重新写回正文；方法持续增重 |

因此，两者不是替代关系。更合理的目标是：

> 以适配分支的“运行时中立架构”为骨架，吸收 master 的“实证后方法论增量”；保留能力语义，重写运行时字面实现。

若只取 master，会回到运行时耦合；若只取适配分支，则会丢失 2026-07-10 之后四周真实项目换来的方法论收紧。

## 三、适配分支带来的结构性价值

### 3.1 正文从“工具词”转成“能力接口”

适配分支新增 `templates/runtime/interfaces.md`，把正文所需机制定义成运行时中立接口，例如：

- 隔离执行单元；
- 隔离审查单元（廉价档 / 默认档）；
- 并行预读；
- 脚本批执行单元；
- 浏览器场景执行；
- 远端命令通道；
- 代码托管操作；
- 入口引导；
- 纪律强制机制。

这一步的意义不是换词，而是把“方法论要求什么”与“某运行时怎样实现”拆开。原来正文里的 `subagent`、`haiku`、`Explore`、`Skill(...)`、`pinchtab`、`codex exec` 等词，同时混合了：

1. 方法目的；
2. 执行机制；
3. 产品 API；
4. 成本档位。

适配分支把第 1 项留在正文，把第 2–4 项下沉到 `templates/runtime/{cc,codex}.md` 和 runtime 配置。

### 3.2 启动协议成为单一源

分支把项目入口拆成：

- `templates/CLAUDE.md`：Claude Code 薄壳；
- `templates/AGENTS.md`：Codex 薄壳；
- `templates/boot-protocol.md`：共享启动协议；
- `templates/runtime/{cc,codex}.md`：各运行时的能力映射。

这是比“复制一份 Codex 版 CLAUDE.md”更重要的改动。它避免两套完整流程分别维护、长期漂移。

### 3.3 输出契约坚持单一源

适配分支把兼容底线定义为：

- 任务包只有一份 schema；
- `status.yml` 只有一份契约；
- sprint 状态、Gate、Git 流、检查器退出码、sessions 留痕只有一份定义；
- 不同运行时可以混用，但必须产出相同结果。

这把“运行时兼容”从“两个工具都能执行”提升成“两个工具产出的项目状态可互相接续”。

### 3.4 防回潮从约定变成检查器

分支新增 `_meta/scripts/check-runtime-neutral.sh`，对运行时消费正文扫描硬编码机制词。它实际上为方法论建立了一道新的架构边界：

> 正文可以依赖能力，不可以依赖某个运行时的产品名、模型名和调用语法。

### 3.5 适配分支仍留下的风险

1. **接口名中立，不等于语义完整。** 例如“并行预读”如果没有规定“必须同时发起”，运行时可以顺序执行却仍自称符合接口。
2. **隔离程度可能不等价。** 新进程、全新会话、同进程新上下文，在信息泄漏和文件共享上的保证不同。
3. **廉价档/默认档只有相对名，没有质量下界。** 若 runtime 映射随产品升级变化，方法论可能在不知情时退化。
4. **映射表本身缺少一致性验证。** 正文不再漂移后，风险会转移到 runtime 映射是否仍忠于能力契约。
5. **共享启动协议仍是分叉点旧版本。** `boot-protocol.md` 的 Step 0 仍吞同步错误，说明“抽成单一源”只解决了重复维护，没有自动获得 master 后续修复。

### 4.1 M1：同步协议不是“启动文案”，而是事实报告协议

master 的 `sync_repo` 修复包含四个互相关联的约束：

1. 不吞 stderr；
2. `pull --ff-only`，冲突/diverged/凭据失败原样报错；
3. hact-method 必须位于主干；
4. “拉取 N 个 commit”必须由 HEAD 前后差值实测。

适配时不能把 master 的 `templates/CLAUDE.md` 整份复制过来。正确落点是分支 `templates/boot-protocol.md`，让两个入口共同消费。

这里值得讨论的不是命令写法，而是：

> 方法论是否应把“事实声明必须有可复算来源”上升为跨任务通用原则，而不只写在 Step 0？

### 4.2 M2：探针把“档位”从描述变成可证伪声明

主干对 foundation-review 的关键收紧是：每个 ≥机械级声明都必须亲手制造违规并验证检查真红；构造级还必须确认常见绕过出口也被封死。

这与适配分支的能力接口天然相容，因为它规定的是证据义务，不依赖具体运行时。需要 runtime 映射的只是：怎样创建临时反例、怎样运行 type/lint/DB/路由检查、怎样保证清理。

这里形成一个重要分层：

- 正文定义“必须主动构造反例并被阻断”；
- 项目栈定义反例类型和检查命令；
- 运行时定义执行与清理机制；
- 审查产物记录“撞了什么、结果是什么”。

### 4.3 M3：GIT 的目的从“覆盖更多场景”转成“撞接缝”

master 把后端联调从按接口列正常/异常场景改为：

- 每个不同终态/分支决策一条穿透流；
- 一个真实实体从入口走到终态；
- 禁止 fixture 构造中间态抄近路；
- 每步断言转换真实发生；
- 外部桩点构成“边界闸”，真调需用户授权；
- 即使全绿，也必须把 as-built 逐处对照 TRD/PRD 契约。

它背后的方法论变化是：

> 测试层的价值不再按“发现了几个 bug”衡量，而按“它是否击中了其他层覆盖不到的失效面”衡量。

这对运行时适配提出新问题：正文可以写“浏览器场景执行”“脚本批执行单元”，但“不得使用 fixture”“必须按真实实体隔离”“断点即停报”这些可观察约束不能在中立化时被压成一句泛化的“执行测试”。

### 4.4 M5：欠账与反馈分池，是按处理时效而不是按文本形态分流

master 区分：

- **规范应该怎样改** → `feedback.md`，在 wrap-up 分流；
- **本期代码具体缺了什么** → `backlog.md [欠账]`，必须在 G4 前交用户定夺。

完整链路是：

`develop/独审发现` → `backlog [欠账]` → `manual-test` 在 G4 前逐条定夺 → 留下期的写入验收报告 → 下期 `draft-prd-vN` 开场重新过账。

这里修复的是“载体的时间语义”：内容写进了某个文件，不等于它会在需要的时间被消费。

### 4.5 M6：退役账把减法从“删除代码”扩成“解除维护义务”

`supersedes` 记录本任务取代的旧实体。后续必须二选一：

- 已下线：在本次 diff 中指出删除位置；
- 保留：写清理由和解除条件。

G5 再逐条核账。其核心判据是：

> 零路由、无业务调用方但仍注册、仍被测试维护的东西，不叫“已下线”。

这个机制与运行时无关，适合直接进入中立正文。需要讨论的是 `supersedes` 是否应该继续由 plan-sprint 人工枚举，还是逐步引入依赖图/引用扫描作为独立证据。

### 4.6 M7/M10：仪器要有“响不响”的第二道检查

主干先增加了 `code_reviews[].rounds`，随后真实项目里出现：字段已经定义，但 11 个新任务 0 个填写，甚至有任务连 `code_reviews[]` 条目都没有，而所有流程照常通过。

因此又在 `check-sprint.js` 增加 merged 任务的审计留痕核验。这给出一条可一般化的原则：

> 新增度量字段时，必须同时回答“谁在何时写”和“谁机械检查它真的被写”；只定义 schema 不算落地。

这与适配分支的“纪律强制机制”接口直接相关：该接口不应只描述有哪些强制方式，还应要求每个关键纪律存在可观察留痕和缺失检测。

## 六、两条演进路线真正值得讨论的张力

### 议题 1：能力接口应该只定义“目的”，还是也定义“可观察保证”

当前 `interfaces.md` 更接近能力名称与解释。例如“并行预读”表达了目的，但没有规定：

- 是否必须并发发起；
- 最大扇出；
- 是否共享工作树；
- 返回顺序和失败处理；
- 怎样证明它没有退化为串行。

若接口只定义目的，映射实现很自由，但方法论可能静默退化。若把执行细节全写进接口，又可能重新与某类 harness 绑定。

建议讨论一个中间层：**能力的可观察契约**。例如：

> 并行预读：多个互不依赖的读取任务须在同一调度批次发起；产物记录本批任务数与各自结果；失败允许主线顺序补读。

这里不写产品 API，却保留了“真并行”和可审计性。

### 议题 2：运行时中立是否会退化成“最小公分母方法论”

某些运行时能构造隔离新进程、并行审查、浏览器自动化、自动审批；另一些只能顺序执行。若正文只保留所有运行时都有的能力，方法论会被最弱运行时拉低。

另一种定义方式是：

- 方法论定义必要能力与证据；
- runtime 不具备时必须显式标记 `blocked` 或降级；
- 降级不能声称等价通过；
- 是否允许降级由具体 Gate 决定。

这比把高级能力从正文删掉更符合适配分支已有的“无工具则未运行，不得声称通过”方向。

### 议题 3：模型档位到底是成本配置，还是质量判据的一部分

master 的实证表明，审查模型过弱会系统性误报；适配分支把模型名抽成廉价档/默认档。还缺一层：档位如何被验证。

可以考虑给档位定义结果要求，而不是固定模型：

- 廉价档：适合结构核对、纯执行、低语义残量；
- 默认档：适合敏感任务、foundation、复杂语义审查；
- 若廉价档在一段时间内出现高误报/漏报，runtime 映射必须回调；
- 映射变化写入决策与实证，不在正文改模型名。

### 议题 4：正文中立化时，哪些具体约束绝不能被抽掉

以下内容看似实现细节，实际承载方法论价值：

- 审查单元必须自读权威原文，不能接收执行方自评；
- 穿透流不得用 fixture 构造中间态；
- 安全反例必须验证端到端可达；
- 浏览器“消失”断言必须按可见性而非 DOM 计数；
- 临时探针必须清理，不能进入 commit；
- 事实声明必须来自可复算结果。

这些都应留在中立正文，因为它们定义的是证据可信度，而不是某个工具的调用方式。

### 议题 5：检查器“存在”与纪律“生效”之间谁负责

master 的 `check-reusables.js` 经验显示：脚本写进模板，不代表项目仓已铺；项目仓有脚本，不代表 hook 在跑；hook 在本机 `.git/hooks/`，换机器又会消失。

适配分支新增了“纪律强制机制”接口，但还没有回答部署可复现性。可讨论四种层级：

1. init 时复制一次；
2. 启动协议核对模板与项目副本；
3. `core.hooksPath` 指向仓内版本化目录；
4. CI 作为跨机器门卫。

问题不只是选哪个方案，而是：

> 一个方法论机制满足什么条件才算“已落地”——文件存在、有人手跑过、自动门已接线，还是换机器后仍可复现？

### 议题 6：主干持续收紧会不会让运行时映射变成新的大文件

正文抽象以后，运行时映射可能逐步堆积所有实现细节，最终变成第二份 execution spec。需要明确映射表边界：

- 只解释能力接口如何调用；
- 不重述业务步骤和 Gate 判据；
- 运行时共有的证据义务回正文；
- 项目栈命令去 standards；
- 产品 API/配置示例留 runtime 映射；
- 映射可以更换，输出契约与证据义务不可更换。

### 议题 7：历史账应按“分支来源”合并，还是按“方法论事实”重建

直接合并 STATUS/history 会保留完整时间线，但也会带入两边对同一事件的不同状态：master 记录“运行时适配未并主干”，分支则认为适配已完成；master 删除实验区，分支归档实验区。

建议把治理记录分三类：

- **事实事件**：两边都保留，按时间合流；
- **当前状态**：以合并后事实重写，不保留互相冲突的现态句；
- **决策理由**：并列保存，必要时新增一条“合流决策”说明最终选择。

## 七、一个可能的目标分层

| 层 | 负责回答 | 建议载体 |
|---|---|---|
| 方法语义层 | 必须做什么、为什么、证据义务和 Gate 是什么 | `specs-execution`、`specs-structural`、review briefs |
| 能力契约层 | 所需能力及其可观察保证、允许的降级 | `templates/runtime/interfaces.md` |
| 运行时映射层 | CC/Codex 如何调用这些能力 | `templates/runtime/{cc,codex}.md` + runtime config |
| 强制与验证层 | 怎样机械发现未执行、假绿、登记失真和留痕缺失 | `templates/scripts/check-*.js`、hook/CI |
| 治理与实证层 | 为什么改、何时回调、哪些议题已关闭 | `BRIEF.md`、`_meta/plans`、status history |

这个分层的关键约束是：

1. 方法语义层不得出现运行时产品 API；
2. 能力契约层不得只有名词，必须包含可观察保证；
3. 运行时映射不得重述完整流程；
4. 每个关键字段/纪律必须有生产点、消费点和缺失检测；
5. 治理记录不能成为正式流程的隐含依赖。

## 八、若决定合流，建议的实施顺序

### 阶段 A：先合低冲突机械层

1. 取 master 最终版 `check-docs.js`、`check-sprint.js`、`pre-commit-hook.sh`；
2. 加 `check-reusables.js`；
3. 同步任务包字段、status schema、init-project 铺设项；
4. 先让机器契约对齐，再改大量散文正文。

### 阶段 B：按能力组做语义合并

建议顺序：

1. Step 0 真同步 → 分支 `boot-protocol.md`；
2. foundation 探针；
3. GIT 穿透 + 边界 + 契约对账；
4. 归属真空 + 欠账链；
5. supersedes + 退役账；
6. as-built / AC 可达性 / 调用方锚 / 双侧实证；
7. rounds / risk-note / 审计核验。

每组都同时处理：生产端、消费端、模板、检查器、状态契约，避免半落地。

### 阶段 C：再合治理账

1. 三方合并 `_meta/plans/方法论待议.md`；
2. 保留主干关闭/合并结论；
3. 保留分支决策 #30 和适配实证；
4. 重写合并后的当前状态；
5. 历史记录按时间追加，不做单边覆盖。

### 阶段 D：双重验收

至少包括：

- `_meta/scripts/check-runtime-neutral.sh`：正文无运行时硬词回潮；
- `node --check`：全部 Node 检查器语法通过；
- `check-sprint.js`：对存量代表项目做 dry-run，区分真命中与代差；
- `check-reusables.js`：代表项目无批量假阳性；
- 能力特征核对：M1–M10 的生产点、消费点和缺失检测均在；
- 两入口输出契约一致：CC/Codex 从同一项目状态推断相同 task.type；
- 治理账无丢失：master 新条目/关闭项与分支 #30 同时存在。

只读 `git merge-tree` 演练显示：两边共有 26 个文件同时改动，实际文本冲突集中在 13 个文件、24 个冲突块。冲突主要位于 execution specs、入口/状态历史和任务包模板；工作量可控，但不适合用“全部选 ours/theirs”处理。

## 九、建议优先讨论的问题

1. “运行时中立”是否应包含能力的可观察契约，还是只保留抽象名称？
2. 某 runtime 无法等价实现隔离/并行/浏览器能力时，允许降级到什么程度，哪些 Gate 必须阻断？
3. 廉价档/默认档由什么实证触发回调，是否需要周期性校准？
4. `check-runtime-neutral.sh` 是否应只扫硬词，还是进一步检查映射表覆盖了正文使用的全部能力？
5. hook/检查器满足什么条件才算“已部署”：模板存在、项目副本存在、自动接线，还是跨机器可复现？
6. GIT 的穿透与边界纪律是否要上升为通用“测试层不重复相邻层”的设计原则？
7. `supersedes`、归属真空、AC 可达性是否可以共享一个更一般的“关系必须闭合”判据？
8. 新字段是否强制同时交付生产点、消费点、缺失检查和存量兼容策略？
9. runtime 映射表怎样防止长成第二份 execution spec？
10. 合流后，`codex-runtime-adaptation` 是作为一次性迁移分支结束，还是长期作为运行时兼容验证线存在？

---

## 十、暂定建议

在进一步讨论前，可先把立场压缩成四句：

1. 适配分支的运行时分层应保留，它解决的是主干尚未解决的结构性耦合。
2. master 分叉后的 M1–M10 应吸收，它们来自真实项目的漏判与假绿，不是一般润色。
3. 吸收单位应是“能力闭环”，不是提交或单文件；凡涉及运行时字面实现都需翻译。
4. 下一轮讨论的重点不应是“用 CC 还是 Codex”，而应是“方法论能力怎样在不同运行时下保持同等证据强度”。
