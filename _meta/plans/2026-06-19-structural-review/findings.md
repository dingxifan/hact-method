## 一、Gate 冷核与独立审查的关系（已厘清，无待议）

**结论**：G3 冷核（plan-sprint Step 4.7）与 Step 3.5 独审不重复，G4 冷核与 develop Step 5.5 不重复。

- **Step 3.5** 只审 4 类（AC忠实性/完备性/api-contract/relevant-standards），显式跳过：依赖关系、交付方式、sprint.md 一致性、reference行号
- **G3 冷核** 覆盖整张完成判据（含上述被 Step 3.5 跳过的项），并做 meta-check（Step 3.5 是否真跑了）
- **develop Step 5.5** 是单任务代码质量（diff 粒度）
- **G4 冷核** 是迭代粒度（all develops merged + 集成测试 + 人工验收），两者无交叉

## 二、generate→validate loop 架构逐阶段分析

**核心命题**：规则从 generator 的 context 移到 validator 的 context，generator 保持极简，靠 loop 而非规范记忆来保证质量。

### PRD
- **适用性：差**
- 质量瓶颈是语义层（需求是否对），不是语法/格式合规
- validator 能查格式，查不了"AC 描述的是否是用户真正要的行为"——这只有人能判
- 当前"逐步骤等用户确认"的对话结构本质上已经是把人当 validator，这是最合适的模型
- **结论**：不改

### draft-UX
- **适用性：低~中（仅原型生成步骤）**
- 原型 HTML 生成是有界任务，适合专注 subagent + validator 检查覆盖率/死链/design.md 变量
- 但 UX 质量的核心是交互方案决策，validator 只能判"方案是否合规"，不能判"哪个方案更好"
- 业务沟通（Step 1）是强交互的，不可 subagent 化
- **结论**：原型生成步骤可提取为 subagent，边际收益有限，不作为优先改造点

### TRD
- **适用性：强，但有结构性硬障**
- 每个 API 模块单独 subagent 设计，context 干净；validator 可机械检查字段覆盖/错误码/service flow 标注
- **硬障**：多个 API 共享数据模型（User/Department/Task 等实体），各自独立 subagent 会产生隐性定义差异，比单一会话写出来的 TRD 更危险
- **解法方向**：先跑"共享类型定义" subagent 产出 schema 文件，后续 API 生成 subagent 全部引用这份文件
- **结论**：有改造价值，先解决 shared-type-first 方案再推进

### develop
- **适用性：已基本成立（Step 5.5 就是 validate）**
- 现状：写完所有代码 → 跑一次 validator；改进方向：模块级 loop（每个模块/文件写完即验）
- **输入密度问题 loop 解决不了**：context 压力相当部分来自"必须读 standards + 代码文件"（输入密度），不是会话累积；精确加载（按任务包 files 只读相关 standards 段）是独立的优化，与 loop 架构正交
- **结论**：主要改进是 Step 5.5 粒度细化，无需架构重写

## 三、独立 subagent 结构审查结果（8项）

### 原则性错误（最高级别）

**#8 Context 窗口依赖**
- 方法把"CC 在长会话中稳定执行复杂规范"当前提假设
- 规范越长 → 会话越长 → context 失真概率越高 → 规范执行越不可靠 → 正反馈退化回路
- STATUS.md 历史有直接证据：`5cfdedb` 自称"格式化"实际删87行；hact-app v4 PRD 缺字段
- 所有"禁止跳过X"等文字约束本身也在 context 里，同样会被失真
- subagent 冷审/compact 协议是补丁，生效依赖"CC 在失真前先执行它们"——条件不可保证
- **这个矛盾无法在"写更好的规范"方向上解决**

### 结构性问题（高严重度）

**#1 develop 不是一个 task type，是五个**
- source=sprint / integration / manual-test / bug / optimization 五条路径，上下文加载/反馈去向/checklist 完全不同
- 强行压进一个471行规范，靠属性分支内部路由
- 打破了 BRIEF.md 决策#14"task.type 是路由键"的承诺
- 规范膨胀的根本原因

**#3 Gate 无机械闸门，质量保证条件性**
- Gate 底层假设："CC 和 subagent 会诚实执行"——这正是规范存在的理由
- 协议自承"堵不住整步跳过或把 FAIL 洗成 pass"
- 唯一兜底：人抽看凭证——当人是非技术背景管理者时，这道兜底也失效（见 #4）

**#4 非技术管理者与 🚫 节点判断要求之间的结构性鸿沟**
- BRIEF.md 定位"管理者非技术背景"，但大多数 🚫 节点需要判断架构/接口/代码质量
- "判断交付方式" = 需懂架构；"抽看冷核凭证" = 需懂完成判据；"确认 api-contract" = 需懂接口设计
- 实际使用中大多数 🚫 节点会变成橡皮图章

**#6 B 类/A 类边界静默渗透**
- 分类标准是"来源（bug/optimization）"，真正的边界应该是"是否修改共享契约（TRD/standards）"
- 这两个维度不等价：一个 B 类优化任务可能实际修改了接口契约
- 发生时：绕过 G2/G3 的保护，无任何机制检测，跨迭代静默积累技术债
- **在真实项目中是必然发生的，不是偶发**

**#7 多工作区同步成本被低估**
- hact-method→项目仓：靠开发者手动 git pull，规范更新滞后无机械检测
- hact-notes→hact-method：靠管理者记得跑 harvest-notes，无自动触发
- 项目仓→hact-notes：纯自愿，无完成判据核对
- "使用中的规范"与"最新规范"之间的漂移在正常操作条件下是常态，不是例外

### 结构性问题（中严重度）

**#2 信息流两个已知漏洞**
- TRD 中 AC 注释是软约束（`# 满足 AC：xxx` 靠写作者记得加，无结构约束）
- relevant-standards 字段靠语义判断（机械查不了），漏列导致 develop 静默不加载强制规范
- 两者都在规范中被承认，修复方案是"手工补救"而非结构层消灭

**#5 规范膨胀是 #1 的症状，不是独立问题**

## 四、全局结构性错误定性（最重要）

### 全局错误 A：质量模型建立在错误方向

**现状**：规定输入 → 假设输出正确  
（规范是在告诉 CC 怎么做，Gate 是在检查指令是否被遵循，不是在验证输出是否真的正确）

**正确方向**：产出输出 → 验证输出是否正确

Gate、冷核、独立审查都是在检查"规范是否被遵循"，而不是"软件是否真的能用"。唯一做真正输出验证的是 generate-integration-tests 和 manual-test——但它们在流水线最末端，前面五个阶段的所有问题在这里才被发现，修复成本最高。

**方法论在最便宜的地方验证最便宜的事（格式合规），在最贵的地方发现最贵的问题（功能不对）。**

### 全局错误 B：AI 不可靠性被当作规范写作问题处理

AI 是"可以通过缩小任务边界和验证输出提高可靠性的概率性系统"，但方法论把它当作"可以通过详细规范驯化的确定性系统"。

对概率性执行者，写更长的指令会让问题更严重——更长的规范 = 更长的 context = 更高的失真概率。

generate→validate loop 的正确性在于：不是试图通过更好指令让生成更可靠，而是接受生成可能有误、用验证来兜住。

### 根源

方法论的设计隐喻是**合同**（契约）：写清楚要求，让执行方按合同行事。  
软件开发有效质量保证的隐喻是**测试**：写可以自动运行的验证，让"是否正确"成为可机械检查的事实。

specs-structural 的完成判据应该是测试，但它是人工清单；Gate 应该是自动验证，但它是对话确认点；冷核 subagent 应该是自动化回归测试，但它是一次性人工触发任务。

## 五、下一步方向（尚未决策，待下次会话推进）

优先级排序（基于影响范围 × 可操作性）：

| 方向 | 对应问题 | 备注 |
|------|---------|------|
| develop 拆分成多个 task type | #1 + #5 | 同时缓解 context 压力，改动范围大 |
| B 类任务升级触发检测（"是否改动共享契约"） | #6 | 堵最危险的静默渗透 |
| TRD shared-type-first 架构 | generate→validate loop 分析 | 解锁 TRD 并行化的前提 |
| 质量验证前移（从文档合规检查转向输出可测试性） | 全局错误 A | 方向性转变，影响整个方法论设计哲学 |

**明确不做（当前）**：
- PRD 改为 generate→validate 架构（质量是语义的，不适合）
- Gate 硬化（已在待议清单，与本次结论相关但独立线）
