## 1. 范围（已定案）

**做**：
1. 新建**结构化 PRD/TRD 模板**（空槽 + 固定 header，方案 a 规范化散文）。
2. 建 **linter**，跑完成判据里的结构 + 一致性规则。
3. linter 可手动跑、出报告（pass/fail 逐条带位置 + 非零退出码）。

**不做（边界）**：
- AC 可执行形态（Given/When/Then）→ **子计划 2**。地基 AC 留普通槽。
- linter 怎么卡签字（hook / Gate 凭证）→ **子计划 3**。地基只到"可手动跑 + 出报告"。
- 散文规则的实际删除 → 多数随子计划 3 把 linter 接进 Gate 时落地（见 §6 净收缩账）。

**对象**：PRD、TRD 两份产物（完成判据含交叉引用的就这两份）。status 已有 `status.yml`，不在本子计划。

## 2. 模板形态（方案 a：规范化散文 + 空槽 + 固定 header）

### 2.1 PRD 模板（新建 `templates/prd.md`）

功能块样张（核心功能段，每功能一块）：

```markdown
### 功能：{功能名}              ← 固定 header `### 功能：`，linter 按此切块
**入口**：{用户从哪触发}        ← 空槽，空着 FAIL
**draft-ux**：{需要 / 不需要}   ← 枚举槽
**涉及实体**：{Entity1, Entity2} ← 标签槽，抽来对账 TRD 表
**场景描述**：{散文，人写人读}
**Acceptance Criteria**：
- AC1：{……}                    ← 普通槽（形态留子计划 2）
**明确排除**：{本期不做什么}
```

6 个必含段落用固定一级/二级 header（产品目标 / 目标用户 / 核心功能 / 用户故事 / MVP 边界 / 开放问题），对齐结构层契约「PRD 必含段落」。

### 2.2 TRD 模板（新建 `templates/trd.md`）

7 个必含段落固定 header。数据库设计段每张表用固定 header：

```markdown
## 数据库设计
### 表：{表名}                  ← 固定 header，linter 抽来对账 PRD 涉及实体
- 字段 / 约束 / 索引 / 外键 / 唯一性…
```

接口设计段每个接口块（路径 / 方法 / 请求体 / 响应体 / 错误码槽位）。

> 模板只规整"linter 要解析的点"（header + 槽位），叙事部分仍是自由散文。不引入 YAML sidecar。

## 3. linter 规则集（来自现有完成判据）

### 3.1 PRD 规则

| 规则 | 来源判据 | 判法 |
|------|---------|------|
| 6 段落 header 齐、无空段 | "6 个段落全部存在无空段" | 查固定 header + 段内非空 |
| 每功能块 `入口`/`draft-ux`/`涉及实体` 槽非空 | "每个功能含明确入口" 等 | 槽标签后非空 |
| `draft-ux` ∈ {需要, 不需要} | "已标记 draft-ux" | 枚举校验 |
| 开放问题段为空 | "开放问题段落为空" | 段内无条目 |
| 每功能块有 ≥1 条 AC | （AC 槽存在性，非形态） | 至少一条 `- AC` |

### 3.2 TRD 规则

| 规则 | 来源判据 | 判法 |
|------|---------|------|
| 7 段落 header 齐、无空段 | "7 个段落全部存在无空段" | 查固定 header |
| 测试环境约定段非空 | "测试环境约定段落存在完整" | 段内非空（"完整"留人） |
| 每张表块含字段定义 | （表块结构） | `### 表：` 块非空 |
| 每接口块含 路径/方法/响应/错误码 | （接口块结构） | 槽位齐 |

### 3.3 交叉一致性规则（候选 C，跨文件）

| 规则 | 来源判据 | 判法 |
|------|---------|------|
| **PRD 每个 `涉及实体` 在 TRD 有 `### 表：{名}`** | "PRD 每个数据实体有对应表" | 两边抽 header/标签，求差集，缺则 FAIL |

### 3.4 明确留人的语义残量（linter 不碰）

场景还原 5 要素齐全 / 三角评估 / "测试环境约定**完整**" / "AC 是否是用户真要的" / 用户故事覆盖度——这些是语义判断，留 Gate 现场人签（子计划 3 定语义残量的签字形态）。

## 4. linter 工程机制（推荐，待挑刺）

| 项 | 推荐 | 理由 |
|----|------|------|
| 语言 | **Node（JS）** | 对齐待议 check-status.js + 项目栈（NestJS/Vue），避免 python 跨平台脆弱 |
| 位置 | hact-method `templates/scripts/check-docs.js`，由 **init-project 铺进项目仓** | 对齐 status.yml/check-status.js 既定模式（linter 跟项目走，不留方法论仓） |
| 与 check-status.js 关系 | **暂分开**（check-status 验 YAML schema，check-docs 解析 markdown，输入不同）；后续可合一个 CLI 多子命令 | 输入异构，强合无收益 |
| 调用 | 手动 `node scripts/check-docs.js iterations/vN/prd.md`（+ trd.md 做交叉检查） | Gate/hook 接入是子计划 3 |
| 输出 | 逐条 pass/fail + 位置（`prd.md:L42 功能"X" 缺 入口槽`）；有 FAIL 退出码非零 | 人可读 + 机器可判 |
| 解析策略 | 容错行扫描（按固定 header / 槽标签正则切块），非完整 markdown AST | 规整 header 下够用，轻 |

## 6. 净收缩账（诚实）

地基**本身删散文有限**——它建的是"能力"，删除多在后续兑现：
- 地基落地即可删：散文里"6 段落手数""槽位人肉核"这类自检指导语（linter 接管）。
- **大头延后**：Gate 冷核协议 §7 的 ①结构完备 + ②交叉一致那两类活，要等**子计划 3** 把 linter 接进签字、确认可信后才连同冷核散文一起删。
- 这是地基作为"地基"的应有形态：它的净收缩由它解锁的后续子计划兑现，不在本子计划内全部体现。父设计「成功判据 = spec 净收缩」对**整个方向**成立，不要求每个子计划单独达成。

## 7. 开放点（实施前可不决，实施中定）

- PRD `涉及实体` 与 TRD 表名的命名归一（大小写 / 单复数 / 中英）——交叉对账要先约定可比规则，否则 false FAIL。倾向：模板注明"实体名与表名同名同形"，linter 大小写不敏感比对。
- 模板对存量项目（hact-app 等）不追溯，只对新迭代生效；存量散文 PRD/TRD 不强迁。
