## 二、案例对比的关键发现

### 1. 视觉与交互精度的差距

| 维度 | hact-output | Claude Design |
|------|-------------|---------------|
| 圆角 / 阴影 / 动效 | 几乎无 | 完整 |
| 比例数字 | 13px 普通文本 | 22px 粗体 |
| 分摊可视化 | 无 | 卡片底部彩色比例条 + 斜线纹固定段 |
| 类型区分 | 单色蓝标签 | 发放蓝 / 成本紫双色系统 |
| 控件 | radio | 胶囊 Segmented Control |
| 表单架构 | 全页跳转（独立页面） | **右侧 Drawer 滑入** |

### 2. 信息架构差异（最关键）

- hact：新增/编辑 = 8 个独立全页（与 Brief 的 D3/D4 一致）
- Claude Design：所有表单 = 一个右侧 Drawer（未在 Brief 中授权，是 Claude 自主决策）

这个差异远大于其它视觉细节差异——Drawer 在这个场景下其实更优（减少导航深度、上下文不丢失），但 hact 会话从未把它当成"可探的设计选项"。

### 3. 场景覆盖完整性

hact-output 覆盖更全：
- S06（新增后 ✓ 标记）：hact 有，Claude Design 无
- 面包屑三级导航：hact 有，Claude Design 用单返回按钮代替

Claude Design 单独使用做不到 27 个场景的完整覆盖——它的视觉精度依赖于上游已经做完的 hact 思考。

### 4. 结构性不对等

两种方法不是公平竞争：claude-design-input.md 本身就是 hact 会话的蒸馏物。Claude Design 用的是 hact 已经完成的 D1–D7 决策作为输入。

**结论**：Claude Design 不是独立方法，是 hact 的下游工具。但 hact 现在的产出（ux-flows.md + prototype.html）不能直接喂给 Claude Design——需要手动提炼 Brief，这一步现在不在规范里。

## 四、本轮达成的方向性共识

### A. 方法结构应该分三层逐层探选

用户认同的层次划分：

| 层 | 决策内容 | 选项示例 |
|----|---------|---------|
| **第一层：导航架构** | 操作的结果以什么模式承载？用户在哪里？ | 全页跳转 / 侧边 Drawer / 居中弹窗 / 原地内联展开 |
| **第二层：屏幕组成** | 页面由哪些主要区块构成，位置关系是什么？ | 顶部信息卡 + 操作栏 + 内容列表 / 左右分栏 / Tab / ... |
| **第三层：组件细节** | 按钮位置、固定行置顶/置底、表格列宽 | 通常有标准答案，探选收益最低 |

**关键洞察**：当前 Step 2.5 主要发生在第三层和部分第二层，**第一层完全缺席**。第一层的决策影响所有下游画面，必须最先锁定。

### B. 改法方向（未细化）

在识别"非平凡画面"之前，先做一轮"导航架构扫描"：
- 对流程图里每个**操作跳转**（不是每个画面）问"这个操作的结果用什么模式承载？"
- 标准的（列表点行进详情 = 全页跳转）跳过
- 有真实选择的（新增 / 编辑 / 复杂查看）做对比探选

待决定：
- 这一层放在 Step 2.5 之前作为新 Step，还是作为 Step 2.5 的第一阶段
- 第一层的产物形式（仅文字命名 / 文字 + 流程图标注 / 其他）

### C. 交互形式问题（本轮未深入）

明确了 ASCII 线框对人无效，但具体改法没讨论。可能的方向（未确认）：

- Step 2.5 探选时即输出 mini HTML 渲染样品供选择
- ux-flows.md 的角色重新定位（明确为 CC 的工作上下文，不是人的评审产物）
- 在 Step 2.5 之前先生成一个"超粗原型"供用户视觉对照
