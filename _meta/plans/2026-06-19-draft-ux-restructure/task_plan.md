## 重构目标

把当前 draft-ux 规范从「让用户做交互工程师的助手」（审 36 条场景 / 流程图 / 线框图）改为「**CC 当交互工程师，用户当客户**」——客户只参与上游业务诉求与下游设计稿反馈，中间过程内部消化、不外露。

---

## 已达成定调

### 1. 角色与主链路

| 维度 | 定调 |
|------|------|
| 角色姿态 | CC = 交互工程师；用户 = 客户 |
| 入口 / 触发 | 不变（PRD 标记需要 UX → 加载 draft-ux） |
| 主链路 | 业务沟通（多轮文字）→ CC 内部消化 → 出 HTML 原型 → 反馈调整 |

### 2. 交流形态规则

- **业务沟通 = 文字对话**：自然对话，澄清功能边界、用户角色、使用场景、业务约束
- **决策对答 = 直接掏中间产物**：跳过结构化文字方案描述（"方案 A...方案 B..."的列表也属于"让人做文字→画面转换"，故禁用）

### 3. 中间产物触发条件与形态

- **触发条件**：有多种合理走法 **且** 该选择影响下游多个画面（关键决策）
- **默认载体**：**mini HTML 片段**（CC 渲染成本最低、用户直接看到结构）
- **高一档**：**可点击小原型**（决策牵涉路径感、不点不出感觉时）

### 4. CC 内部消化的 5 步清单

| # | 内部动作 | 是否外露 |
|---|---------|---------|
| 1 | 业务理解（多轮对话沉淀） | 外露（即"业务沟通"） |
| 2 | 场景拆解（"用户从 X → 操作 Y → 到 Z"内部清单） | 不外露 |
| 3 | 流程穿线（连成路径，识别分叉/空态/错误） | 不外露 |
| 4 | 画面构思 + 关键决策识别 | 中间产物外露，构思过程不外露 |
| 5 | 生成 HTML 原型 + 用户走查 + 反馈调整 | 外露（终端交付） |

**过渡时机**：对话式过渡——CC 觉得业务够清晰了，主动提议"我准备出第一稿了"；用户认同就出，否则继续聊。**不设固定轮次。**

### 5. 落盘规则

| 产物 | 落盘 | 内容 |
|------|:----:|------|
| `prototype.html` | ✅ | HTML 原型（最终交付） |
| `ux-flows.md`（精简） | ✅ | 仅保留：场景命名表 + mermaid 流程图（下游 TRD/测试用） |
| 原 `ux-flows.md`「交互决策」「交互质量走查记录」段 | ❌ | 审查产物，新姿态不再需要 |
| 内部消化痕迹（步骤 2/3/4） | ❌ | 不落盘 |
| 中间产物本身（HTML 片段 / 小原型） | ❌ | 对话临时辅助 |
| 关键决策结论 | 分层 | 跨迭代影响 → 项目级 `decisions.md`；单期影响 → 不落盘 |

### 6. 视觉定位（B 议题大部分）

- 当前规范「不追求视觉精美」**改**——良好视觉对体验把握有帮助
- **视觉规范单一来源：项目级 `design.md`**
- 原型必须落实 design.md（字体/字号/色彩/间距/控件样式）
- 视觉服从 design.md，**不在原型阶段做视觉创新**（防 CC 调圆角抢戏、防迭代漂移）
- 视觉颗粒度：

| 项 | 必做 | 可做 | 不做 |
|---|:---:|:---:|:---:|
| 颜色 / 字号 / 间距 / 控件样式（来自 design.md） | ✅ | | |
| hover / focus / disabled / 空态等状态可见性 | ✅ | | |
| 动效（Drawer 滑入、淡入等） | | ✅ | |
| 真实数据接入 | | | ❌（占位即可） |

- **第一次做 UX 时 design.md 处置（选 a）**：draft-ux 启动时若 design.md 是空模板，CC 在业务沟通末尾顺手和用户对一下视觉风格基调（深色/浅色、品牌主色、字体系），生成 design.md 初稿后再进入内部消化

### 7. C 议题处置

**不引入 claude design**——理由：没有专职交互工程师，引入会打破方法论顺畅性。

#### Step 1 已定细节

**涵盖范围（参考清单，CC 自判按需）**：
功能边界 / 用户角色 / 典型场景 / 业务约束 / 入口情况 / 数据状态 / 异常处理

**子流程**：

1. CC 多轮自然对话，按需覆盖参考清单方面
2. CC 觉得问够 → 输出**业务理解总结**（结构化清单，按方面分段，**不落盘**）
3. 用户审业务理解总结：
   - OK → 转视觉对接
   - 改 → 按修改继续聊
   - 主动加方面 → 加上继续
4. **视觉对接**：
   - 若 `design.md` 已存在且填充充分 → 跳过本子步
   - 否则 CC 问 3–5 个视觉基调问题（深色/浅色、品牌主色、字体偏向、圆角风格、控件密度）
   - 用户回答 → CC 写 `design.md` 初稿（**落盘**，落盘规则特例：design.md 是项目级跨迭代文件，不在 draft-ux 落盘表管辖）
   - 用户审 design.md 初稿 OK → 转 Step 2

#### Step 2 已定细节

**必走清单**（红线保留，写为内部约束）：
1. 场景拆解（"用户从 X → 操作 Y → 到 Z"内部清单）
2. 流程穿线（连成路径，识别分叉/空态/错误）
3. 画面构思（**信息架构层为主**：承载方式如 Drawer/全页/内联、区块组成如顶部信息卡+操作栏+列表）

**画面构思颗粒度**：信息架构层。**组件细节（按钮位置、列宽等）留到 Step 4 HTML 原型里直接落**——符合工程师实际工作方式，不在脑里先把每个按钮位置想清。

**全程不外露**：内部消化痕迹不展示给用户、不落盘。

**结束出口（两种）**：

| 出口 | 触发 | CC 动作 | 转向 |
|------|------|---------|------|
| **X** | 识别到关键决策点（多种合理走法 + 影响下游多画面） | 先告知用户「我识别到几个关键决策需要先对一下」 | 转 Step 3 |
| **Y** | 未识别到关键决策点 | 告知用户「业务理解和画面构思已就绪，我准备出第一稿原型，可以吗？」 | 用户认同 → 转 Step 4 |

#### Step 3 已定细节

**触发**：仅当 Step 2 出口 X 时进入；否则跳过本步。

**典型决策示例**（写入规范，帮 CC 识别 + 防漏识别）：

| 典型决策 | 选项 |
|---------|------|
| 表单承载方式 | Drawer / 全页跳转 / 居中弹窗 / 原地内联展开 |
| 列表组织粒度 | 一行一员工 / 一行一记录 / 分组折叠 |
| 多操作摆放 | 页面级 / 行级 / 工具栏 |
| 复杂数据呈现 | 卡片 / 表格 / 时间线 / 看板 |
| 多步流程编排 | 单页分区 / 分步向导 / Tab |

**中间产物形态约束**：

- **mini HTML 片段**（默认）：
  - **必须用 design.md 视觉变量**——避免中间产物丑陋让用户分心、误以为视觉就是这样
  - **单画面级**（一个区块/一个表单），对答聚焦
- **可点击小原型**（升级档）：决策本身关于路径感（如"全页跳转 vs Drawer 哪个返回更顺"）、不点不出感觉时升级

**对答进行方式**：

- **一次一对一答**——保持对话感，避免一口气堆 5 个决策让用户消化
- CC 给 2-3 个方案，用户可改选 / 改方案 / 提第三方案，反复直到定
- **决策结论记录**：跨迭代影响 → 写入项目级 `decisions.md`；单期影响 → 不落盘
- **全部决策对完** → CC 告知用户「关键决策已对完，准备出第一稿原型」→ 用户认同 → 转 Step 4

#### Step 4 已定细节

**原型规模与组织**：单 HTML 文件、CSS/JS 内联、自包含；多画面用 vanilla JS 的"切换 div 显示/隐藏"机制实现。

**生成时的覆盖要求（红线性质）**：

| # | 要求 |
|---|------|
| 1 | 流程图中每条路径都能在原型中走通，无死锚点 |
| 2 | 每个画面的信息架构落实（承载方式 / 区块组成） |
| 3 | Step 3 关键决策结论已落实 |
| 4 | 视觉规范落实（design.md 变量，不硬编码颜色/字号/间距） |
| 5 | 状态可见性落实（hover / focus / disabled / 空态 / 错误态） |
| 6 | 占位数据符合业务场景（"张三 / 工号 10086 / 财务部"，不是"xxx / yyy"） |

**CC 自检（写完原型后逻辑核查）**：

- 锚点连接性：每个 `href="#xxx"` 都能找到目标
- 路径覆盖：流程图每条路径都有对应 HTML 节点
- 状态可见性：每个画面的 hover/disabled/空态有 CSS 类
- 视觉规范遵守：grep 一遍 `style=` 看有没有硬编码颜色/字号
- **不假装"浏览器打开"**——CC 不能真打开浏览器，只能做逻辑核查

**生成后转向**：Step 5（用户走查）。

#### Step 5 已定细节

**用户走查方式**：CC 交付原型时给提示性清单（不强制按清单走）：

- 业务路径是否符合预期
- 信息架构是否清晰
- 关键决策结论用起来是否顺
- 视觉是否符合 design.md 基调
- 状态可见性（空态/错误/禁用）是否够用

**subagent 陌生视角冷审**：**去除**（旧 Step 3.5）

理由：新姿态下用户直接看原型（不是看 36 条文字）→ **用户走查 = 真陌生视角**，比 subagent 模拟更有效；旧规范 subagent 冷审是补"用户被迫做文字→画面转换"的累赘，新姿态不再必要；CC 自检（Step 4 清单）+ 用户走查双重防线足够。

**反馈调整循环**：

- 用户提反馈 → CC 逐条判（**改原型** / **记待办** / **认为属过度**）→ 改后再让用户走查
- **待办项落到项目级 `backlog.md`**（已有架构）
- 反复直到用户满意

**走查结束标志**：**用户主动说"OK 可以了"** → 转 Step 6。不设 CC 主动判定——是否结束由客户说了算。

#### Step 6 已定细节

**落盘清单**：
