## 一、一句话诊断

**一段文字被当成「已验证」,靠的是它所在的位置和格式,而不是它背后有证据。** 写进承重墙那一栏、写进豁免登记、打上 AC tag、写成 sprint 依赖——这个「动作」本身赋予了文本一种它从没挣得的权威。

**根因:失效集中在 handoff 边界。** foundation → sprint → develop → review,每次交接把状态**序列化成文字**,下游信这段文字。但这是一次**有损、未验证的序列化**:上游脑子里「大概是这样」,落成一句斩钉截铁的「X 由 Y 承接」,下游当既成事实用。**文本是流程里唯一没有类型检查的接口。**

## 二、映射到六模式报告(证明这不是现造)

本盘不引入新病症,只给报告已发现的模式命名共同原理:

| 报告模式 | 本盘视角 | 归属 |
|---|---|---|
| 模式 2 · 声明的门 ≠ 实际的门 | 文本位置赋予验证地位的**核心样本** | 本盘主攻 |
| 模式 4 · 执行方自评不可信 | 自评是「写方给自己发验证章」,举证责任错位 | 本盘主攻 |
| 模式 6 · 已入账文本本身写错 | 入账 = 获得「已评估」地位而无复验 | 本盘攻「地位」半,scope-vacuum A1 已攻「出口」半 |
| 模式 1 · 归属真空(包与包之间) | 承接声明无双向对账 → 无人认领 | 本盘第一层触及 |

## 三、核心处方:举证责任反转

**重心从审方挪到写方。** 文本默认不可信,证据由**写的人**就地交出;审的人只做轻活——**证据指针在不在?不在,红。**

这不是「拾遗补漏」。拾遗补漏是下游的、事后的、再读一遍去找漏的——而「末尾再读一遍」正是 V5 出血的那个动作本身(审查读了觉得通顺就放过)。

| | 拾遗补漏(错误 handle) | 举证责任反转(实际) |
|---|---|---|
| 在哪 | 末尾 | 关口/准入 |
| 时态 | 事后 | 事前(改默认态) |
| 动作 | 审方努力去找漏 | 写方交证据,审方只查指针 |
| 风险 | 把盲区请回来 | 坏文本从根上挣不到「已验证」 |

## 四、三层机制(按成本铺开,非三选一)

### 第三层 · 给「已验证」地位设门槛(先上,几乎零成本)

约定:**任何声称「已验证/已评估/已承接」的文本,必须就地引用证据**——一个测试 id、一条可跑探针命令、或一段「从条款原文重推」的推导。**没有证据指针的,状态一律降级为「已断言」,对抗审查必须把「已断言」当阻断项对待。**

- 改的是 plan-sprint / develop / adversarial-review(structural develop / task-package-review)三处的**准入措辞**,零代码。
- 作用对象:**已经存在的声明**。sound but incomplete——它检不了一个从没被写出来的声明(见第二层)。

### 第二层 · 灭恒真式度量(紧跟,成本在上游)

覆盖/计数类的病灶是**循环**:分母(该覆盖啥)和分子(覆盖了啥)出自同一支笔,只能回答「我覆盖了我列的吗」,永远回答不了「我列的是不是就是全部该覆盖的」。

要求:**任何覆盖率/计数,分母必须来自覆盖方不能控制的独立枚举源。** 条款落点由条款文本枚举,任务包只负责覆盖,交叉比对 `{write,read,migration}` vs `{write}` → 1/3 → 红。

- **防的是第三层看不见的那半张脸:静默缺项(omission)。** 补漏的前提是知道漏在哪;第二层是「开灯」,先让洞可见。
- 分母独立后,「linter 查不了」被反转成**可机检**:只要条款把落点显式列出,一个 linter 就能 diff 枚举集 vs 覆盖集。
- **真正成本在上游**:逼 standards / 承重墙**枚举自己的落点**。没有权威枚举 → 无独立分母 → 退化回第三层。
- **边界**:只对「该覆盖集能被独立枚举」的东西有效(条款落点、AC 清单、承接对是硬防线;设计意图这类枚举不了)。

### 第一层 · 声明探针化(按需,不铺开)

**不是独立全覆盖工程,是第三层证据在「行为类声明」子集上必然坍缩成的形态。** 证据长什么样取决于声明断言什么:

| 声明类型 | 第三层给的证据 | 成本 |
|---|---|---|
| 条款/意图 | 一段回读原文的重推 | ≈ 免费 |
| 文档事实 | 引用指针 | 免费 |
| 行为类 · 已有测试覆盖 | 填现成 test id | 免费 |
| **行为类 · 静默 · 无覆盖** | **新造探针** | 贵——但就该贵在这 |

筛子(决定哪条真要新探针):对声明问「**它要是假的,进生产前有没有任何东西会自己变红?**」——会红 = 系统已在探它,别浪费;不会红、静默拖到返工/联调才炸 = 探针该花钱的地方。

- V5 出血全是第二类。探针大多**不用新写**(现成集成测试跑过 Y,指针填 test id 即可),只有「行为类 × 静默 × 无覆盖」交集才新造。
- **唯一预先钉死的**:承接声明必做探针化(经验上最烫,四载体全出过事),双向对账 + 探针实测。其余按筛子触发。

## 五、与既有机制的关系(冻结调和,须验证轮裁决)

本盘三层里,多数是**既有机制的实例被命名**,而非净新增:

- 第三层 ≈ 把决策#29「risk 自报不单点」+ foundation 证据化探针 + 「独审须实跑证伪 / 回读条款原文判无条件」这些**已存在的姿态**,升成一条跨阶段的统一准入规则。
- 第二层的「独立枚举」思想,在 A3(机械级条款→落地手段对照)与 foundation-review 探针里已有雏形,只是**未覆盖 post-V0 / 未泛化到 standards 落点**。
- 第一层的探针,skeleton/foundation 已在用,本盘只是明确「行为类声明」这个触发类。

**待裁决**:若判为「统一命名 + 补缺口」→ 与冻结相容;若判为「新增第 N 套机制」→ 受冻结约束,需论证杠杆。倾向前者,但让验证轮回本仓核实,别自己给自己发通行证(本盘也守它自己的规则)。

## 六、待验证开放问题(专门 tee 给下一轮)

这些是本轮点到但**没定**的,是验证轮的输入:

1. **spec 措辞如何自证可重推**——准入规则本身最好别犯它要防的病:三份 spec 的措辞得能被「从原文重推」验证,不能又是一句「已优化」的自报。怎么写?
2. **第二层的独立枚举源在 hact-method 里具体挂哪**——需要回本仓盘现成可枚举源:①条款落点(谁来列、列在哪个文件)②PRD 的 AC 清单 ③承接声明的双向对。哪些已有权威枚举、哪些要新建?
3. **「证据指针」的载体形式**——在 sprint.md / gates.md / progress.md / 任务包里怎么记录才能被机检(check-sprint.js 一类)?指针格式?
4. **承接探针的具体格式与 linter 支持**——双向对账怎么表达、探针 test id 怎么挂、check 脚本怎么校验「承接声明→存在对应探针」。
5. **枚举不了的声明怎么处理**——设计意图这类第二层帮不上,只能靠人。别假装能机检;这部分的诚实兜底是什么?
6. **迁移 / 存量**——存量 specs 与 V5 遗留是否回溯,还是只对 V6+ 生效?(参照决策#29「存量需重铺 check-sprint.js 才获第③层」的先例)
7. **与机制冻结的最终裁决**(见第五节)。
