## 一、本轮的核心问题（为什么要改）

今天治的是**同一个总问题——前端产出物的 UX 质量不达标**，拆成上下游两半：

### 上半 · 保真：能不能照着前置设计做出来

跨 hact-app、org-krm-v2 收集到 **29 条**"实现偏离前置设计"实证，确认是**系统性、跨迭代复发**：

- **视觉规格**：org-krm-v2 至少 6 处硬编码颜色/间距横跨 v3→v5（`$space-xxs:2px` 变量已定义却仍写 `gap:2px`）——**不是缺规范，是规范没被强制加载到开发者眼前**。
- **交互偏离**：Tab 结构与 AC 不符、缺标签、分支遗漏——**全拖到联调/验收才暴露**。

病因三处结构断点：① design.md 是"涉及视觉时"条件加载，靠自判 → 字号字体无人负责；② prototype.html 全程失联；③ develop/pr-review 只对照 standards，唯一保真对账落在 manual-test（太晚）。

### 下半 · 设计质量：设计本身好不好

draft-ux 现在只保证**流程完整**（不漏分支、不死路），不保证**交互质量**。病因不是"不懂 UX 原则"，是两个失效模式：① **回归平均**（无目标时输出训练分布里最通用的平庸解）；② **自评宽松**（同上下文自我 review 被锚定、一路盖章）。抽象原则清单对此无效。

### 两半合起来

> 保真网把"代码别掉到设计稿**以下**"焊住；质量网把"设计稿本身别**平庸**"提上去。先有好设计，再忠实实现，缺一不可。

## 三、对用户使用过程的实质性影响（重点）

按你实际会跑到的 task 顺序说明。**带 ⚠️ 的是会改变操作节奏或需要你额外确认的地方。**

### 1. 跑交互原型时（draft-ux）—— 改动最大（来自②质量轮）

- ⚠️ **新增 Step 2.5「交互方案探选」**：流程图确认后、生成原型前，CC 会对**非平凡画面**（列表如何组织筛选、操作如何摆放、多步如何编排等）先给 **2-3 个交互方案 + 取舍 + 选型理由**，等你确认。纯标准增删改查画面跳过。
  - **你会感受到**：多一道确认环节；你可以改选或提第三方案。
  - **价值**：逼 CC 在设计空间里走一圈，而不是默认交"第一个想到的平庸解"。
- ⚠️ **新增 Step 3.5「交互质量冷审」**：原型生成后，CC 会**额外派一个全新 sub-agent** 做陌生视角冷审——只喂它 prototype.html + ux-checklist + 场景列表，**不喂**设计理由和生成对话，让它不被既有选择锚定，逐条查空态/错态/反馈/回退/任务连贯，再当场修订原型。
  - **你会感受到**：draft-ux 会话多一个环节、多花点时间和 token；你最后审的是**已自批修订过**的原型。
  - **价值**：把"自己对抗自己"里真正有害的锚定拿掉，让自我批判扛得起"可检查的遗漏"这部分。
- **产物变化**：`ux-flows.md` 现在含四段——场景列表 / 流程图 / **交互决策** / **交互质量走查记录**。

### 2. 写 TRD 时（draft-tech-design，来自①保真 fix3）

- **必读清单加 `prototype.html`**（如存在）。
- **接口设计逐画面对照**：原型存在时，CC 会逐画面确认每个接口的请求/响应字段能满足该画面所需数据，避免"接口返回结构对不上画面"。选址在 develop 之前、原型最新鲜时。

### 3. 写代码时（develop，来自①保真 fix1）

- ⚠️ **design.md 升为前端无条件必读全文**：不再凭"涉不涉及视觉"自判。字号/颜色/间距/圆角一律用 design.md 的 SCSS 变量，**禁硬编码**；仅 design.md 与 standards 均未覆盖时才暂停问你。
- **prototype.html 作交互基准**（若存在）：对应交互路径以原型为准。
- **自检清单加「十一、设计保真」**：字号一致 / 用变量无硬编码 / 控件尺寸 / 原型交互分支不遗漏 / 未覆盖视觉先暂停。

### 4. 审查时（pr-review，来自①保真 fix2）

- ⚠️ **新增设计保真维度，双口径**：
  - **design.md 视觉**（字号/变量/控件尺寸）→ 对照**全部 frontend PR**（视觉规格跨迭代稳定）。
  - **prototype.html 交互**（分支/入口）→ 仅对照 **`source=sprint` 的 PR**（联调/人工/B 类派生的修复 PR 原型已旧，再卡=误打回）。
- 快速通道允许"硬编码→既有变量"直修，禁交互改动。

### 5. 联调时（generate-integration-tests，来自①保真 fix3）

- 脚本生成读取集合加 prototype.html；前端场景用原型**软核对覆盖齐全**——每条原型交互分支对应一条场景或显式豁免，**不设硬闸口**，超 15 条仍按上限降级 backlog。

## 四、本轮没做的 / 已识别待议（避免误解）

### ① 保真轮明确不做

| 不做项                         | 理由                   |
| --------------------------- | -------------------- |
| manual-test 加原型对照           | 已进人工阶段，测试人自知怎么测      |
| plan-sprint 加原型锚点           | 与 ux-flows.md 行号硬卡重复 |
| 引入活规格 / 漂移维护制度              | 按阶段收口后漂移问题已消解        |
| fix1（develop 读 prototype）收口 | 软参照非闸口，读到旧原型风险低      |

### ② 质量轮 parked（等冷审跑出经验再评估）

- **同模型共享盲区**：subagent 是同一模型，上下文隔离能去掉"锚定"，去不掉"整类模型都不认识的坏模式会一起漏"——只能靠外部标准补（① 清单内容质量 + ④ 参考样例库）。
- **④ 跨项目 UX 参考样例库**：按 UI 原型分类存"照着学的好例子"，挂 harvest-notes `[UX]` 标签上提，draft-ux 优先复用。复利最高但要人工策展。

### 新识别 · 设计→最终生成之间的损耗（今天讨论产出，留作下轮输入）

本轮提升的是**设计稿（spec）质量**，但从设计到 develop 真正生成代码之间，现有流程只有**防漂移（保真）**闸口，没有**防平庸（质量）**闸口——②③ 只活在 draft-ux 一个点上。损耗集中在"**低分辨率原型 → 真实组件**的上采样"过程，已识别六条来源：

1. **理由不随载体走**：交互决策/走查记录按画面组织，存在 ux-flows.md，而 develop 只读"对应功能段"，很可能读不到——拿到结果拿不到"为什么"，遇缺口回退通用解。
2. **原型轻量 vs 实现丰富度落差**：冷审补的状态是骨架，翻成真组件的上千个微决策原型欠定义，每个都是回归平均入口。
3. **媒介转换**：HTML 原型 → Vue + Element Plus，交互未必 1:1 映射，易接受 El 默认行为。
4. **闸口单点，生成处不复闸**：质量闸只在 draft-ux；develop/联调产生的新设计不过冷审。
5. **触发式覆盖**：draft-ux 可选、ux-flows"若存在"才读，跳过 draft-ux 的画面这套机器一行不跑。
6. **人在 🚫 的注意力衰减**：判断/品味靠人兜底，若回车放行则分层防御塌回自己对抗自己。

下轮方向（未决）：对称性——把 ②/③ 精神下放到生成处（develop 自检对照交互决策、对真实 UI 轻量冷审），或提高原型分辨率。**先等 subagent 冷审跑出实际经验，看损耗落在哪几条，再决定堵哪个。**

---

## 五、一句话总结

> 今天给前端 UX 质量装了**两道互补的网**：保真网（design.md 必读 + prototype 接入 + pr-review 双口径，防代码掉到设计**以下**）+ 质量网（draft-ux 造前探选 + subagent 冷审 + 行为化清单，防设计本身**平庸**）；代价是 draft-ux / develop / pr-review / TRD / 联调各多一道动作。已识别但本轮未堵的，是"设计→最终生成"之间那段**上采样损耗**——留作下轮，等冷审经验积累后再治。
