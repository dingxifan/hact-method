# 补充 · 一次随聊沉淀（2026-06-19，retrospective 之后）

> 起点：用户朴素观感——"PRD/TRD 这些 spec 行数还是好多，动不动两三百行"。顺着聊出一张比 loop 第二层更大的"瘦身机制地图"。loop 第二层只是其中一个成员，且未必是最高 ROI 的那个。**这几条是本阶段真正的指南针，A/B/C 入口决策应放进这张地图里再选。**

## 六、为什么 spec 还是胖：行数花在哪了

把 draft-tech-design（283 行）脑内拆账：

| 成分 | 量级 | 性质 |
|------|------|------|
| **真·设计知识**（疑点清单分类、接口标 AC 回链、AC 操作化…） | **~30–60 行** | 不可压，是知识 |
| **交互仪式**（会话启动前置检查、选项菜单、🚫 停点、逐步汇报格式、签字三件套[gates.md+status.yml+commit]、standards 双源规则、subagent 失败处理、断点续做、红线） | **~200 行** | 大头 |

**关键认识**：spec 长**不是因为知识多，是因为每份 spec 都把整套交互仪式从头抄一遍**；而这套仪式在 ~14 份 spec 里**几乎每份重复**。结构性审查那一整轮打的是"验正确性"那一小块，200 行的仪式大头被 design §10 划进"不可测、留 prose、不动"——**等于绕开了真正占行数的那块**。这就是为什么净收缩只有 −14 行。

## 七、真正能改变 CC 行为的只有三种机制（不是"再写一条规范"）

写更多"禁止跳过 X"本身就是 error B 的退化回路（规则进 spec=进 context=越长越失真；活证据 5cfdedb / hact-app v4 缺字段而规则当时在生效）。真正起作用的只有：

1. **更小的 context** —— CC 只看该看的那一片就没得漂移。= loop 第二层 / sub7 薄壳 / 精确加载。
2. **确定性验证器** —— 检查器查产物，不管 CC"感觉"有没有照做。= loop 第一层（已做 sub1-7）。
3. **结构性强制（forcing function）** —— 让对的事成为**唯一出路**：空槽不填就刺眼；hook 在检查器红时**直接拦 commit**。不求配合，让不配合**做不到**。

**这一轮只动了第 2 种。第 1 种（loop 第二层）parked，第 3 种（hook）被反复定成"不做、软版"。** → 散文删不动的根因。

## 八、判官 + 门卫：唯一能"删散文"的组合

- **linter = 判官**：知道结构对不对、对不对得上账。
- **hook = 门卫**：判官说红就不放过（拦 commit）。

> 验证器只能**新增**能力、删不掉散文——因为"记得跑 check-docs.js、退出码 0 才签字"**本身还是一条散文规则**。
> 真正能**删散文**的是 hook：hook 自动跑、红了就拦，那句"记得跑+退出码0才签字"就能**整段删掉**——强制它的不再是文字，是闸门。

**我们只造了判官、没派门卫**，所以判官一个人站着显得没用武之地，散文也删不下去。**hook 是本方向缺的关键拼图。**

## 九、两坨不同的肥肉，两把不同的刀（别混）

| 肥肉 | 刀 |
|------|----|
| "请 CC 照做"的**可验规则**（对账、签字前置、禁止跳过 X） | **linter + hook**（§八） |
| 每份 spec 都抄一遍的**仪式重复**（启动协议、签字提交、status.yml 更新、断点续做） | **DRY**——抽成一份共享段让各 spec 引用（= sub7 给 develop 干的"共享核心+薄壳"，推广到整个 spec 语料） |

draft-tech-design 那 200 行的大头其实是**第二坨**。两把刀瘦的是不同地方，都得用。

## 十、linter 的价值（大白话定格，防再次"觉得它虚"）

- **它是 PRD/TRD 的拼写检查器**：不查内容好不好，查"有没有漏填的格子"+"第1页跟第5页对不对得上"。你们 check-docs 就两件事：① 空槽填没填 ② 对账（PRD 涉及实体↔TRD 表；PRD AC↔TRD 回链，逐条正反向）。
- **价值是累积的不是单点的**：凑近看每条都 trivial，但"全部·每次·永远·不烦"地查 47 处交叉引用——而人/长会话 CC 最不擅长的恰是这种无聊重复核对（"印象执行"按老样子填、新字段没看见；hact-app v4 缺字段 1 秒可逮）。
- **确定性是它区别于人审/subagent 冷核的根**：只吐 0/1，不累、不被说服、不盖橡皮章；另一个 AI 冷核会幻觉出 pass。**正因如此才敢把 subagent 冷核整段删**（拿不会骗人的换可能骗人的）。
- **硬边界（别吹过头）**：只查**形式 + 对账**，永远查不了**意思**（这条 AC 是不是用户真要的 / 载体是不是真承接 AC 而非仅 id 在场）。意思上的判断永远是人的。linter 的活是**把又笨又机械的核对从人桌上清走**，好让人的注意力全花在"这东西到底对不对"。

## 十一、"越往后加载越多" 可以改——是漏交接的症状，不是自然规律

**现象**：PRD→TRD→sprint→develop，越往后载得越多（develop 要背 PRD+TRD+standards+design+原型+代码）。负载 ≈ O(流水线长度)。

**反框**：增长是**症状**——每多读一份上游文档，都是**上一棒没把它要的东西交到手里、只给了个"回去自己翻"的指针**。

**改法（还是"小 context"，顺着流水线方向用）**：每次交接做成**蒸馏过的、自包含的完整规格**——下游读「交接物」不读「历史」。develop 只读它那一个任务包（AC/契约/相关 standards 已嚼碎放进去），不回头读 PRD/TRD。负载从 O(流水线长度) → **O(单个任务)，与阶段数脱钩**。

**已造了一大半**：sub2 把 AC 操作化成 Given/When/Then **写进任务包**（develop 看 AC 不回 PRD）；任务包有 `api-contract` 字段；draft-ux 早就在做"CC 内部消化 → 只落盘精简 ux-flows 2 段"——**"内部消化→紧交接"模式已存在，只是没系统铺到整条 PRD→TRD→sprint→develop 链。**

**一个真矛盾（撞墙前要知道）**：
- **回链/reference**（为 linter 对账）要的是**指针**，指回源头好交叉核对。
- **carry-forward**（为 develop 小 context 干活）要的是**内容**，别让它顺指针回读整份上游。

两者**拉向相反方向**。任务包现是**混血**：AC 带过来了（好），但 `reference: trd.md L123`、`relevant-standards` 还是**指针**——正是 develop 今天仍要回读 TRD/standards 的**漏点**。压平负载 = 把这几个指针那头的内容蒸馏一份带进任务包。

**一条压不下去的底线（别和上面混）**：develop 要改的**代码文件**随**代码库**长、不随阶段长——是 orthogonal 轴，得用另一把刀（精确加载只读相关段 / 拆小模块），别指望"蒸馏交接"解决它。

## 十二、合并视图：这些其实是一个家族

| 杠杆 | 方向 | 机制类 | 状态 |
|------|------|--------|------|
| loop 第二层（per-API 小循环） | **横切**（按模块/接口切小 context） | §七-1 | parked，本阶段拟重启 |
| 蒸馏交接（读交接不读历史） | **顺切**（按流水线切小 context） | §七-1 | 已造一半，未系统化 |
| hook 门卫 | 强制结果、删"请照做"散文 | §七-3 | 反复定"不做"，**缺的关键拼图** |
| DRY 仪式 | 去重复制的交互仪式 | 工程去重 | 未动 |

**地基✓（结构化模板）+ 判官✓（linter）已就位；缺的是门卫（hook）+ 蒸馏交接 + DRY + loop 第二层。** "删散文的真正回报，要等门卫踩上地基那一刻才到账。"

## 十三、不可删的本体（守住，别为省行数倒洗澡水）

🚫 **人类检查点**（等用户确认/掉头的那一下）+ **真设计知识**——不是肥肉，是方法的身体。它们**没有可验结果**（价值在实时交互那一瞬，事后验不了），forcing function 也强制不了。瘦身瘦的是"只能祈祷 CC 配合"的那些"禁止 X"，**不是**人能介入的那几个点。

## 十四、流水线形状之疑：从「末端验证」到「贯穿脊柱」（本阶段真正的纲）

> 起点：用户追问——"越往后加载越多，蒸馏能缓解但蒸馏本身有信息遗失；那我们这种从前到后分步骤的做法，本身是不是就有问题？" 这一问已**超出 loop 第二层，触到方法论总形状**，可能比 §五/§十二 的 A/B/C/D 入口更该是下一步的纲。

### 14.1 蒸馏不是干净的赢（先认账）

上游信息分两种：下游"用得上的" / "用不上的"。砍掉用不上的是降噪（蒸馏本意），但**无法事先 100% 知道哪条以后用得上**。develop 撞到 AC 没预料的边界、要回推"当初为什么这么定"，而"为什么"被蒸馏掉了——真损失。"背全部历史" vs "蒸馏"是一根光谱两头，**两头都有病**：一头 context 膨胀+失真，一头有损+对意外需求脆。

### 14.2 病灶定性：瀑布，反馈环太长

现形状 PRD(整张)→TRD(整张)→sprint(整批)→develop，**质量是末端一道闸**（联调/人工验收才真验输出）。PRD 埋的错（需求本身不对）拖到很多阶段后、修复最贵处才第一次被证伪。**这就是结构性审查自己写的全局错误 A**，只不过原来在**单阶段内部**看，现在在**整条流水线**尺度看同一个病。

**且两个担忧是同一个形状**：蒸馏有损 = 交接**单向·向前·一次冻结**；瀑布累积 = 验证**单向·向前·末端集中**。根都是 **forward-only + 真相确立得太晚**。

### 14.3 一招同治：把「可执行测试」做成贯穿全程的脊柱

在**最前面**就立起可执行验收测试，一路当**不变量**带下去，任何阶段随时可跑：

- **治蒸馏的损**：**永不蒸馏测试**——它可执行、原样带下、无损。被蒸馏的只是软叙述（理由/探索），丢了也安全，**因为行为被测试钉死**。最该保住的那条信息（正确行为长什么样）恰是那条**不被蒸馏**的，以"可执行真相"全程在场。
- **治瀑布的形**：测试从第 1 阶段就在，每阶段能跑，"对不对"变**连续可答**，反馈环从"横跨流水线"塌成"当场"。

**这是你们自己"AC→可运行测试"的放大版**——但当前建成了**末端操作化**（压 TRD 阶段才把 AC 变例子）+ 一道**验证步骤**；该改成**拉到最前、当组织全局的脊柱**。它在最前面后，每一棒交接"必须无损带过去的核心"就有了机器盯得住的明确对象——蒸馏不再凭感觉砍。

### 14.4 三条边界（别以为推翻流水线就万事大吉）

1. **顺序不消失**：仍需先需求→再接口→再代码（逻辑依赖，非瀑布之错）。要改的是**切片方向**——别切"整张 PRD/TRD"这种**横的满宽片**，改切**竖的、单功能端到端薄片**（一个功能从 PRD 一路打到测试绿），反馈环就短。= 垂直切片，不是取消阶段。
2. **测试治不了"需求对不对"**：只验"实现做对了 AC 说的事"，验不了"这条 AC 是不是用户真要的"。后者永远人判——所以 🚫 人类检查点照留，且本就在**前面**（好事）。脊柱治"实现正确"，非"需求正确"（呼应 §十三 + design §10 PRD 不可测）。
3. **共享地基 vs 薄切片打架**：findings §二硬障——共享数据模型（User/Department/Task）必须先整体自洽才谈得上并行/切片，要**前期成批**；功能逻辑要**薄竖片**。故非"纯一次一片"，而是经典 **"先立一具能走路的骨架（共享类型脊柱）+ 让功能竖片穿过它"**。**shared-type-first（loop 第二层前置）就是这具走路骨架**——两件事在此接上。

### 14.5 结论

"分步骤本身有没有问题"的准确答案：**分步骤（有顺序）不是 bug**；bug 是 ① 切的是**满宽横片**→反馈环横跨整条流水线；② 质量是**末端向前的一道闸**，而非**最前面立起、全程带着的可执行不变量**。改掉这两条，流水线就不再是"有损的瀑布"。

**对地图（§十二）的影响**：这一节是**更高一层的纲**。loop 第二层 / 蒸馏交接 / hook / DRY 都是在"既定流水线形状内"做优化；本节质疑的是**形状本身**。下一步选杠杆前，先决定：是**在现形状内打补丁**（A/B/C/D），还是**先重定形状**（垂直切片 + 测试脊柱前置）——后者可能让前几个杠杆的优先级重排。**待用户定。**
