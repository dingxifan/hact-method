## 总体判断

这是一套成熟度远超一般"AI 协作流程文档"的方法论——已完成从"给 AI 写规矩"到"给 AI 建质量管道"的跃迁，且带有自己的演进回路和成本模型。最大隐患不在设计错误，而在**复杂度增长速度超过收敛速度**，以及几个各自合理的决策叠加出的治理盲区。

## 一、全局层面

### 好的地方

1. **任务驱动替代角色扮演，是对 LLM 工作方式的正确建模。** task.type 路由键 / discipline 只做知识聚类与准入 / 权限走 user-discipline 关联——LLM 的"身份"本来就是它加载的上下文。Gate 退为任务集合聚合视图（决策#13）同理。
2. **分层纪律执行得很好。** skeleton（是什么）→ specs-structural（schema 契约）→ specs-execution（怎么做）→ templates（物料），每份文档有"本文回答/不回答"边界声明；单一真相源意识强（18 字段只在 structural/develop、审查维度只在 brief、§7 判据核对只在 06-gates）。
3. **质量模型四层分工是最精彩的部分。** 确定性 linter（判官）→ pre-commit hook（门卫）→ 独立对抗审查 subagent（隔离、自读权威原文、不收自评）→ 显式留人的语义残量清单。自我纠错记录尤其难得：把"派 subagent 冷核盖章"识别为"用 AI 治 AI 的规范膨胀退化回路"并整段退场。
4. **测试脊柱是全链路可追溯的实例。** PRD 逼出 Given/When/Then（写不出=AC 模糊，在最便宜处暴露）→ TRD 只精化不创造 → 任务包携带回链 id → develop 1:1 物化为可运行测试，每一跳有机械对账。
5. **成本作为一等约束（决策#26）。** 按任务性质降档模型、活文档归档阈值、上下文密度声明、compact 时机写进规范。
6. **方法论自身有演进机制。** feedback → notes → harvest-notes → 待议 → 调整会话的 pull 模型；_meta/plans 保留完整决策痕迹（含 sub7 拆了又撤的反向记录）；BRIEF 决策带"不要绕回"与落地修正注。

### 需要改进的地方

1. **【全-1】两个各自合理的决策叠加出无机械拦截的合并链条**（最值得警惕）：决策#24 接受 master 无第二人工门，安全兜底靠任务包 `risk: sensitive` 触发人工裁决；决策#26 把 `risk: standard` 的审查 subagent 降档 haiku；而 `risk` 由 plan-sprint 填写、check-sprint 明确不机械校验。漏标 sensitive 的任务包 → haiku 审查 → 自动合并进 master，全链条无机械闸。待议里"B 类改共享契约绕过 G2/G3 无检测"是同族问题。建议：check-sprint 加关键词/路径启发式 warning（files/AC 涉 auth/权限/删除/迁移/金额而 risk=standard 时报出留人确认），或 develop 末端安全预检不信任务包自报、对 diff 路径独立扫描。
2. **【全-2】复杂度在膨胀，响应模式是"每次踩坑加一层机制"。** 视觉地基包 / foundation.md / V0 走骨架 / 双源规范 / 地基跟进包 / 框架值二分……单看都有理由，但条件分支已多（新/存量、走没走 V0、有没有 linter、有没有门卫的兜底分叉遍布），兜底逻辑在多份 spec 重复。致密化压的是散文长度，没压分支数量。建议下轮结构性审查把目标从"行数"换成"一个新项目从 init 到 G5 要走的决策分支数"。
3. **【全-3】单人验证偏置。** 软锁冲突 / 共享资产并发依赖 / 多人拉取摩擦全部标注"团队期再说"（YAGNI 本身合理），但规范文风高度依赖历史语境，第五阶段真实开发者进入成本会远超预期。guide/ 是补偿层但在 linter 覆盖之外、已漂移：guide/00 标题"13 个任务类型"、表列 12 个（漏 draft-ux、draft-foundation），catalog 实际 14。
4. **【全-4】技术栈假设渗进骨架层。**（✅ 已处理，决策#27）disciplines 03 直写 Vue/NestJS、视觉地基绑 EP 变量名。修正：栈子模板层 + 播种三源 + skeleton/specs 去栈措辞。
5. **【全-5】status.yml 处于"只写没人读"状态。** hact-app sync 仍解析 markdown；双份状态无消费者、无写入校验、无对账，每个 exec spec 承担"记得同步更新"义务，漂移是时间问题。越早让看板切读 status.yml + 铺写入校验越便宜（待议 #6/#7 已记，建议提优先级）。

## 二、具体执行方法层面

### 好的地方

1. **三层渐进 + 检查排序的经济学。** 疑点前置、骨架先行、"最便宜的检查放在用户注意力之前"（linter → 陌生视角 subagent → 用户确认）。
2. **任务包 18 字段是"给 LLM 的任务说明书"的工程化范本。** files 精确到行号、reference 拒收全文、do-not、escalate-if 必含"上下文不足"、known-risks 须来自 TRD、api-contract 上游推导下游只读。
3. **develop 执行模型干净。** 主线只编排、per-task 下沉执行 subagent、审查 subagent 全新隔离自读权威原文、loop 有界、重置协议"以工作区实际文件为准"。develop-review brief 的"用户输入去向追踪"逐 DTO 字段穷举 + 覆盖率自证 + 噪声纪律是反盲区审查设计范本——"抽象散文里盲区活着，写出具体结局它就死了"值得推广到其他 brief。
4. **降级路径显式。** 测试基建缺失返回 blocked 不静默、subagent 失败主线接管记录原因、存量项目退人工并提示补铺。

### 需要改进的地方

1. **【执-1】🚫 人工阻断点过密且无分级。**（✅ 已处理，决策#28）一期主线 20+ 次确认，混着"人必须拍板"与"可推导"。修正：⚖️ 默认判定档、协议去"继续？"、Step 2.5 并入 Step 2、develop 层自动判定、PRD 继承批量确认、选项列表开场明确即跳过。
2. **【执-2】exec spec 受众混杂，运行时噪声成本高。**（🔄 处理中）正文大量内联历史注解（日期、决策号、撤销记录、"与 XX 同款地基"、"守 2026-06-16"、"sub7 拆了又撤的格"、"v8 主色全错根因"）——写给方法论维护者的记忆钩子，但 exec spec 是 CC 运行时逐字消费的文本，按决策#26 的成本逻辑每次会话都在烧 token 且稀释指令密度。建议"受众分离"：exec 只留"做什么"，"为什么/演进史"移出（canonical 记录多已在 BRIEF/plans/git）。与致密化方向一致，但致密化压的是表达、没分受众。
3. **【执-3】develop 单 spec 承载六种 source 的问题未随撤销拆分消失。** source=foundation 的"三处替换"是运行时补丁式路由，靠 CC 在 327 行里正确跳转。foundation 与其他 source 差异最大（无任务包、全栈、必触发 architecture 门），即使守决策#25②"develop 一味"，也可把 foundation 进料块抽成独立文件由 develop 引用。
4. **【执-4】输出验证侧仍薄于输入侧。** 2026-06-19 待议的全局方向判断至今成立：输入侧 linter+门卫+独审三层，输出侧只有 integration-tests 跑一轮 + manual-test 人工 + 视觉冒烟。下一个大投入放输出可测试性的回报可能高于继续加固输入侧。

### 收尾判断

这套方法论的设计质量在于**对失效模式的诚实**——每个机制都能说出它防的哪次真实踩坑，砍掉的机制留有尸检报告。当前最需要的不是新机制，而是收敛：堵 risk 自报+haiku 降档叠加盲区、做面向"分支数"的复杂度收敛、把输出可测试性从待议兑现为主线投入。
