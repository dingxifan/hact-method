# 公共件 / 复用资产模型 — 讨论沉淀（2026-06-30）

> 状态：**纯概念讨论，先不进实施**（用户拍板）。本文记录把"公用类/公用组件"这个朴素开发概念，对到 hact-method 一致性体系上的完整模型。下次接续从这里读起。
> 起点：用户连日做"质量/一致性"研究，问"开发者说的'把模块做成公用、被引用/继承'是什么意思，对我们方法的开发一致性有什么帮助"。

---

## 〇、概念底座：「公用」的本质 + 三种机制

- **本质**：同一段逻辑/同一个东西**只写一份、多处用它**，而非各抄一遍。
- **三种"用它"的机制**：
  - **引用/调用（组合）**：A 需要时去**叫**那份公用代码干活 —— 现代主力。
  - **继承**：B「是一种」A，白拿 A 的全部能力，只补特殊部分 —— 耦合死，用得越来越少（"优先组合而非继承"）。
  - **组合**：B 内部**装**一个 A 当零件。
- **对一致性的核心价值**：**单一真相源 → 改一处，所有引用方同时变 → 想不一致都做不到。** 把一致性从"靠纪律记得遵守"升成"靠构造保证"。直接对到 BRIEF #25 的**强制边三档（构造级 > 机械级 > 人审级）**——"把它做成公用"= 把一致性的强制力往最强档推。
  - 活证据：org-krm-v2 硬编码颜色横跨 v3→v5 —— 颜色"定义"了一份但各处抄字面值、没去**引用**那一份 = 没真正公用 = 漂移。

## 一、foundation.md 覆盖了五层里的哪些（验证 foundation 没跑偏）

把"公用件"按粒度分五层，对 `templates/foundation.md` 逐层核：

| 五层 | foundation 覆盖？ | 命中 |
|---|---|---|
| 5. 公用基础设施（reset/主题/错误信封/鉴权中间件，跨切面） | ✅ 完全（存在理由） | 视觉地基/错误信封/鉴权/请求管道/入参校验 |
| 4. 公用基类/服务（BaseController/requestClient 单例） | ✅ 充分（"穿过它=单例瓶颈"） | HTTP单例/作用域 base repo/全局卫士 |
| 3. 公用类型/接口（interface Task，契约） | 🟡 部分（只覆盖**跨切面的**类型） | 序列化共享类型/分页信封/错误词汇 + §一领域地图核心实体 |
| 2. 公用组件（Button/Modal/DataTable，UI） | ❌ 不覆盖（有意） | — |
| 1. 公用函数/工具（formatMoney/validateEmail，纯逻辑） | ❌ 不覆盖（有意） | — |

**结论：foundation 精准只拿"上面三层半"，有意把第 1、2 层让出去。** 切割线 = 它自己那句**「只立承重墙、不装修」** + 准入门槛「已证明跨切面 + 稳定」。

- 第 5、4 层 = **承重墙**：不遵守就**失守**（漏一行泄数据），价值是"一致性由构造保证"→ 必须 init 前置立 bar。
- 第 1、2 层 = **装修**：价值只是**省事（DRY）**，不是一致性闸门；且最易踩"错的抽象比重复更糟"→ 懒提取，归 `reusables.md`。
- **判一个件进哪边的一句话**：它是「不遵守就失守/漂移」的**闸门**（→foundation），还是「不复用只是浪费」的**便利**（→reusables）？

## 二、两根轴 → 公共件定位坐标系

讨论中被例子逼出两根轴：

### 轴 A：作用域（项目内 / 跨项目）
### 轴 B：失败模式 ⭐（讨论核心发现）

| | **失守型（承重墙）** | **重造型（工具/装修）** |
|---|---|---|
| 偷懒的人会怎样 | **顺手重写**（敲 `#3370ff` 比找 token 易）→ 偏离 | **本就懒得重写**（从零写摄像头解码要几小时）→ 自然复用 |
| 偏离代价 | 高（越权/泄数据/不一致） | 低（换了个库、风格不齐） |
| 真正的失败 | 偷懒导致**发散** | 不知道**已经有了**，又造一个 |
| 需要的机制 | **锁**（构造级强制） | **可发现**（找得到就行，不用锁） |

> **命门（图省事的人顺手写、合规概率）对两型方向相反**：失守型命门偏向偏离→必须锁；重造型命门已偏向复用→只需让人找得到。

### 两轴交叉 = 2×2 定位法

| | **项目内** | **跨项目** |
|---|---|---|
| **承重墙** | 项目 `shared/`，plan-sprint 预见则 V0 种 | **foundation 技术内生 + 团队 starter**，init/V0 拉，锁构造级 |
| **装修** | 项目 `shared/` 库，lint 焊死（强强制） | **`templates/shared-modules/` copy 目录**，harvest 填（弱强制） |

**关键反直觉**：项目内·装修 ≠ 跨项目·装修的"降级"，而是**镜像翻转**——
- 跨项目 = **弱强制（跨 repo 没法 lint-lock）+ 重发现（要 catalog）**
- 项目内 = **强强制（同 repo 能 lint 焊死到构造级）+ 零发现（grep 自己的 shared/）**

（用户原话"项目内照搬跨项目、无非降级"**只对承重墙行成立**；装修行翻转。）

## 三、登录例子的教训（为什么它是坏例子）

登录 = **承重墙（auth：token/守卫/拦截器/401→踢回/session）+ 装修（表单视觉/SSO与否）混合体**，所以含糊。
- 承重墙那半**早已在 foundation.md 定位**（鉴权/HTTP单例/数据隔离三行）；登录页只是这套鉴权地基的 UI 入口。
- 跨项目共享登录 → 承重墙走 A（spec 共享 + V0 按锁死标准重建，因为它*需要*构造级，而构造级跨 repo 只能每项目自建）；装修走脚手架重新皮肤、永不锁。

## 四、跨项目·重造型工具库设计（QR扫码/短信验证为例）—— 已成形，未实施

QR/短信比登录干净：**核心几乎不变、各项目差异趋零**，接近"纯复用"。它们让 C（真共享代码）重新成立——**但仅对重造型**，因为重造型不需要锁、只需可发现，C 的"跨 repo 没法 lint-lock"硬伤在这里不咬人。

**用户拍板：先做 B（可发现 copy 目录），暂不中央化（不立私有包仓 = 不做 C）。**

### 设计骨架（用户已认可）

1. **是什么/放哪**：`templates/shared-modules/`，和 standards/checklists 平级（团队跨项目资产）。每件 = 一文件夹（**真实可 copy 代码** + 接入 readme：依赖/怎么接/已知坑/出处）+ 一份 `catalog.md` 索引（B 的价值全压在它身上）。
2. **三条腿**（缺一条就退回"没人看的 reusables.md"）：
   - **进库 population** = `harvest-notes` 新增 `[复用]` 收割类，管理者批量上提"已证明跨项目复发+稳定"的真实模块。准入门槛照旧。
   - **引用 routing** = `plan-sprint` 切包增「查工具目录」步：任务能力命中目录件 → 任务包写"copy `shared-modules/qr-scan`，按 readme 接" + 注源。
   - **兜底 enforcement** = `develop` 独审 brief 增「重造检测」维：diff 是不是又造了目录已有能力？
3. **诚实天花板**：copy 模型 → 强制边顶到机械级/强约定 + 独审兜底，**到不了构造级**；**无中央修 bug 传播**（已接受）。
4. **仍远胜现状 reusables.md** 三点：① 新项目**开工第一天目录就满**（harvest 预填），reusables.md 新项目是空的；② **真能 copy 的代码**非文字指针；③ consult 是 plan-sprint **接线步骤**非"哪天想起读一下"。
5. **种子**：方法论仓只放结构 + catalog 格式 + 一个样例骨架；**真实 QR/短信代码靠 harvest 从真项目上提，不投机现写**。

### 落点预览（未动手）
新建 `templates/shared-modules/` + catalog；`harvest-notes`(structural+exec) 加 `[复用]` 类；`plan-sprint`(exec) 查目录步 + 引用写法；`templates/review-briefs/develop-review.md` 加重造检测；guide 个人 notes 加 `[复用]` 标签；`foundation.md` 头注 + BRIEF 决策把"foundation vs reusables"分界扩成三层。

## 五、项目内·复用怎么处理（日期控件为例）—— 触发器换对了

日期控件特殊：用户说的是"**选择**哪几类"——它**首先是一条约定（规范），不是写出来的组件**。

- **第一归宿 = `standards-frontend.md`**（约定：用哪几类控件 + 什么格式）；**可能还有组件半身** = `shared/` 的 `<AppDatePicker>`（包装件）。一个日期资产常横跨 standards + shared/ 两处。
- **升级阶梯（同 token 那招）**：standards 写一句"请用 X 格式"= **人审弱边、会漏**（和硬编码颜色一样）→ 包成 `<AppDatePicker>` = 单一可引用件 → **包 + lint 禁止 import 裸 `<el-date-picker>` = 构造级**（想用错都没入口）。
- **项目内整体用现成机器，不建目录**：同 repo 发现 trivial（grep 自己 shared/），建 catalog+harvest 是过度工程；而强制反能更狠（lint 焊死到构造级，跨项目做不到）。落地 = **standards（约定）+ reusables.md/`shared/`（包装件）+ develop lint/独审（强制）**，零新机器。

### ⭐ 触发器修正：不是「第几次」，是「有多确定」

用户关键修正——**完全可预见的件，第一次就该定，甚至 V0，绕过 rule-of-three**。

- rule-of-three（等第三次）存在的唯一理由 = **防错抽象**（不确定两段相似码会否一直相似时，让复发先证明）。
- 日期控件**没有这个不确定性**（"app 会显示日期且应统一"第一天就 100% 知道）——**可预见性本身消灭了错抽象风险**，再等三次是把"防不确定"的纪律错用到"本就确定"上。

**按置信度分两层（取代按次数）**：

| 置信度 | 例子 | 何时定 |
|---|---|---|
| **高·可预见 commodity** | 日期/金额格式/全 app 通用表单控件/状态徽标 | **第一次就定，甚至 V0**，无 rule-of-three |
| **低·真涌现/不确定** | 两功能碰巧共用的某 helper，以后还共不共用未知 | **rule-of-three** 懒提拔，让复发证明再提取 |

- 日期控件落 V0 的**精确位置**：**不是 foundation 承重墙行**（它是装修件、不笼罩每页，塞进去会稀释那张表）；家是 standards-frontend + `shared/` 包装件；**决定时机可在 V0**，套视觉地基的**「框架(V0)/值(V1)」二分**——V0 标杆切片碰到日期字段就**顺手把 `<AppDatePicker>` 立成标杆**（标杆=漂移主防线，BRIEF #25），格式/locale 等"值"留 V1 填。
- **双向纪律**：只有高置信度 commodity 配"第一次就定"；不确定的件**忍住别在 V0 投机造**——否则反向掉回错抽象陷阱（正是 foundation"只立承重墙不装修"要拦的）。

## 六、最终模型（两列走通）

```
确定 + 跨项目     → 失守型走 foundation/spec（V0 按锁死标准重建）；重造型走 shared-modules copy 目录（harvest 填，弱强制+可发现）
确定 + 项目内     → standards 约定 + shared/ 包装 + lint 焊死（构造级），V0/标杆立起来，第一次就定，绕过 rule-of-three
不确定 + 项目内   → rule-of-three 懒提拔（防错抽象的那条尾巴）
```

公共件体系最终三层、无重叠：
```
foundation.md            ← 承重墙/失守型：锁构造级。V0 种 + 跨项目技术内生
reusables.md             ← 项目内·装修/重造型：项目 shared/，确定的早定、不确定的 rule-of-three 懒提拔
templates/shared-modules/ ← 跨项目·装修工具/重造型：copy 目录，harvest 填 ← 本轮拟新建（未实施）
```
