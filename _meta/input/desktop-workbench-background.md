## 一、一句话定位

**一个常驻桌面、始终在场的个人工作台**：让「已经在硬盘上的摊子」不被忘掉，让「刚发生的事」不被漏掉。

它服务的是**用户一个人**。它**不是**待办系统——事的真相源在 JHH-Nortion，工作台是那个"始终在场、够得着本地"的入口与视图。

## 二、原点

用户的工作面对 **100+ 交易对象**，信息从微信、邮件、飞书、本地文件多渠道涌入，同时要对自己的工作做排期与跟进。核心困境是**事情会消失**，两种消失方式：

| 消失方式 | 成因 | 谁来解决 |
|---|---|---|
| **忘掉** | 项目文件夹太多太深，摊子沉下去就想不起来 | v1 工作区（本项目） |
| **漏掉** | 事发生在微信/邮件里，当下没记，事后忘了 | v1.1 录入口（本项目） |

## 三、两条必须遵守的教训（本项目的立项依据）

这两条来自用户既有系统的真实失败，是本项目所有取舍的根据。**违反其一即失败**。

### 教训 A：汇聚型产品的价值不是线性的

> **覆盖三个信息源里的一个，价值不是 33%，是 0。**

**实证**：mail-ai 已实现「AI 待办提取」（`emails.is_todo`、todos 模块、飞书任务同步均已上线），但在 v8 被**隐藏入口**（`project.md`：「隐藏 AI工作台·待办·关键日期入口（路由保留）」）。用户原话：

> 因为我的信息源有很多，邮件中的 AI 待办没有办法和其他的打通，所以就不想做下去了。

死因不是做得不好，是**它只懂邮件**。既然还得去别处看，这一处就不会来；不来，就死了。

**推论——自动化的推进方向必须反过来**：

| | 做法 | 结果 |
|---|---|---|
| ❌ | 一个渠道一个渠道地做全自动 | 覆盖率永远 < 100%，每一步都死 |
| ✅ | 先建一个什么都能进的池子（全手工，覆盖率 100%），再一个渠道一个渠道地**降低录入成本** | 任何一步停下，系统仍活着 |

手工池天然全渠道——**入口是人的手，手什么都够得着**。"AI 抽待办"省的是录入成本；录入成本高不至死，孤岛才至死。因此 AI 抽取的优先级排在覆盖率之后。

### 教训 B：需要人工保鲜的状态源必然烂掉

用户原话：

> 我还要搞一堆文本去记，时间一长，文本也就忘记了，而文件夹不会，因为一旦产生新文件或变化就会动文件夹。

文本清单需要被喂：开始要记、有进展要改、结束要划掉。任何一步跟不上就与现实脱节；脱节几次就不被信任；不被信任就不再被看。

**文件夹不需要喂**——它是干活的副产品：

- 项目开始 → 本来就要建文件夹（不是额外动作）
- 项目在动 → 文件进出，自动就动了
- 项目结束 → 右键移出工作区

**你不可能忘记更新它，因为你根本不需要更新它。** 「右键加入 / 移出」这两个动作本身就是**开摊子 / 收摊子**的语义，比任何待办状态字段都可靠，因为它绑在本来就要做的事上，而不是绑在自觉上。

> 推论：工作区区块是本系统里**唯一不会烂**的部分。这是它排在 v1 的真正理由。

## 四、与既有系统的关系（边界，不得越界）

| 系统 | 形态 | 在本项目中的角色 |
|---|---|---|
| **JHH-Nortion** | Web（Next.js + Supabase） | **事的唯一真相源**。用户天天在用。工作台读它、写它，**自己不存事** |
| **mail-ai** | Web（Vue + NestJS） | 邮件渠道来源。其待办功能已因教训 A 停用，**不复活、不对接待办**，未来只作为录入来源之一 |
| **桌面工作台**（本项目） | Windows 桌面常驻 | 三样 Web 结构上做不到的能力（见下） |

**桌面形态的独一份价值**——这三条是本项目存在的全部理由：

1. **始终在场**：不用切标签页、不用"想起来打开"。Web 应用那三秒切换成本足以让人说"算了等会儿再记"，然后就没有等会儿了
2. **够得着本地文件**：工作区、文件变动、拖进拖出
3. **够得着本机微信**：选中即录入

**补充事实**：JHH-Nortion v8 与 mail-ai 的目标用户均已转向**团队**，**个人日常这一层目前无人服务**。本项目填的是这一层。

## 七、关键技术判断（已讨论，供 `draft-foundation` 选型时继承）

### 7.1 用事件日志，不用 git

**结论：非开发文件夹用事件日志；本来就是 git 仓库的（开发项目）顺手读一下即可 —— 识别 git，不引入 git。**

理由：

- **要的是「活动的历史」，不是「内容的历史」**。git 存内容历史（能回到任何版本）；本项目要的是"什么时候、哪个摊子、动了什么"，一张事件表即可，一年几 MB
- **二进制爆盘**：xlsx / docx / pdf / PPT 无法增量存储，改一次存一份全量。30MB 的 PPT 改 20 次 = `.git` 里 600MB，且这些空间买到的能力一次都不会用
- **版本问题在非开发文件夹里本就不存在**：人天然用文件名做版本（`报价单-最终版2.xlsx`），演进已被摊平成并存文件。真被覆盖了是网盘版本历史的活
- **需要人工 commit** = 又一个需人工保鲜的东西，直接违反教训 B
- 其余：`.git` 混进工作目录；出错需懂 git 才能救（个人工具不应有需专业知识维护的零件）

**事件日志反而补上了 git 也补不了的洞**：删除和改名不留任何痕迹——"我记得有个文件，怎么没了"目前无从回答。

**顺带解决"太深"**：事件表是扁平的、按时间排的，路径只是一个字段。埋在第六层的文件昨天动过，照样浮在最上面。扫描告诉你"有什么"，事件流告诉你"发生了什么"——要的是后者。

### 7.2 事件日志：两条腿 + 归并窗口

```
┌─ 实时监听 ─────────────┐
│ ReadDirectoryChangesW   │──┐
│ （chokidar 等已封装）    │  │
└────────────────────────┘  │   ┌──────────────┐   ┌────────┐
                            ├─→ │ 归并窗口 2~3s │─→ │ 事件表 │
┌─ 对账扫描 ─────────────┐  │   └──────────────┘   └────────┘
│ 启动时 + 定期            │──┘          ↑
│ 与快照 diff 补漏         │      ┌──────────┐
└────────────────────────┘      │ 快照表   │ 路径→mtime,size
                                 └──────────┘
```

**实时监听负责快和细（能分辨改名），对账扫描负责全和可靠。** 两者写入同一张事件表。

**为什么必须有第二条腿**——实时监听有三个洞，每一个都会让"多久没动"说谎：

1. **程序没开时变动全丢**（关机、崩溃、系统更新重启）—— 最常发生
2. **内核缓冲区会溢出**（解压几千文件的包），中间事件全丢，只得到一个"溢出"通知。调大缓冲区（上限 64KB）只是推高阈值
3. **监听会掉**（外接盘拔插、目录改名导致句柄失效）

**已知降级（须写入设计，勿当 bug 查）**：对账扫描补不出「改名」——只看到 A 没了、B 出现了，会记成一删一增。程序运行期间的改名是准确的。

**归并窗口是必需品，不是优化**：Office 存盘的实际动作是「建临时文件 → 删原文件 → 临时文件改名为原名」三个事件。不归并的话，改一次 Excel 在事件表里像发生了三件事，还带一条"删除"。规则：攒 2~3 秒，窗口结束按最终状态归约。

**噪音过滤**：`~$*.docx` / `*.tmp` / `Thumbs.db` / `desktop.ini`。扫描时它们只是多几行，事件流里会持续刷屏。

**表形态（草案）**：

```
events    ts · workspace · kind(新增/修改/删除/改名) · path · old_path · is_dir
snapshot  workspace · path · mtime · size          ← 仅供对账
```

- 「多久没动」= 该工作区 `events` 最后一条的 `ts`（一次索引查询）
- 「最近发生了什么」= 该工作区最后 N 条

### 7.3 文件夹 mtime 不冒泡（实现约束）

Windows 上文件夹的修改时间**只在直接子项增删改名时更新**。在 `A项目/合同/正式版.docx` 里改内容存盘，`A项目` 这一层时间戳**不会动**。因此"多久没动"不能直接读顶层时间戳——这也正是采用事件流（监听文件事件）而非时间戳轮询的原因之一。

对账扫描需设**排除规则与深度上限**（快照只存路径/时间/大小，几万文件在 SSD 上是秒级）。

### 7.4 本地文件夹 only

**用户已定**：本期只做本地文件夹，不考虑网盘。

砍掉：占位符属性判断、"下载到本地"的假修改事件、冲突副本文件名过滤、网络卷断连导致的监听失效。

**保留不变**：两条腿 + 归并窗口（程序没开会漏、Office 三连，均与网盘无关）。

> ⚠️ **范围决定须有执行动作**：加入工作区时检查路径，落在同步盘下（读 `%OneDrive%` / `%OneDriveCommercial%` 等环境变量）则**提示但不硬禁**——"该目录在 OneDrive 下，事件记录可能不准，仍要添加吗？"。否则某天顺手加进一个网盘目录，系统只会安静地吐噪音，而用户只会觉得"这功能好像不太准"。约半小时的活，是「范围决定」与「纸上写写」的区别。

- **核心实体**：工作区（workspace）· 文件事件（event）· 快照（snapshot）· 软件入口（app）· 〔v1.1〕收集条目（capture，**不落本地库，直发 JHH-Nortion**）
- **贯穿全局的作用域**：**无多租户 / 无组织 / 无多用户**——单人单机，数据全部本地。这是本项目最重要的简化，须在地基蓝图中显式声明，以免下游按常规套上鉴权与隔离
- **关键不变式**：
  1. **工作台不持有"事"的真相**——事的真相在 JHH-Nortion；工作台侧任何待办状态都是缓存，冲突时以 JHH-Nortion 为准
  2. **事件表只追加，不修改**
  3. 状态变更须带**来源**字段（手工 / 采集 / 外部系统回填）——为将来"团队过程管理软件把结果送回来"留的唯一接口预留，除此之外不为团队场景做任何提前设计
