# hact-method 方法论演进说明

> 本文对照旧版基线（master 分支，截至 2026-06-21）与新版（method-lab 分支），
> 系统整理新方法论做了哪些调整、为什么做、带来什么效果，以及未来还能往哪里走。
> 受众：已了解 hact-method 基本框架的团队成员。

---

## 一、演进背景：旧方法走到了什么边界

### 正反馈退化回路

旧版质量控制的核心假设是：把规则写进规范，AI 遵照执行，输出就是对的。
这个假设在实践中形成了一个退化循环：

> 规范越写越长 → context 越来越重 → 执行失真概率越来越高 → 发现新问题 → 规范再写长

**活体证据**：看板应用 v4 的 PRD 缺少"入口"和"draft-ux"两个字段，
而这两行判据从 2026-06-03 就已经写进规范——并非没有同步，
而是上下文中"这类产物大概长这样"的印象覆盖了新增的两行。

### 质量验证时机错误

旧版只在管线末端验输出正确性（integration-tests + manual-test）。
在最便宜的地方（PRD 阶段、设计阶段）只验格式，在最贵的地方（联调）才暴露内容问题。

### 人工审查门过多，节奏慢

develop 阶段有 6 个 🚫 等人确认门。每个任务都需要人在场，
批量任务尤其被拉长。pr-review 是另一个独立等待节点。

### 方向调整的一句话总结

> 不再把"规范写清楚"当成质量保证，而是把"输出可机械验证"作为质量保证。
> 检查器跑一万次结果一致，不受 context 失真影响。

## 二、质量体系转型：从规范遵循到输出可测试性

### 核心方向

每条"为了让 AI 写对而下的散文规则"，凡其目的可由确定性检查达成的，转成确定性检查并从正文中删除。成功判据是 **spec 净收缩**，而非"加了多少检查器"。

### 五项机制

**① 结构化模板（产物半结构化）**

PRD、TRD、任务包、sprint 的格式规则从 spec 正文移进模板文件的 HTML 注释。
作者往已摆好槽位的骨架里填，字段没法忘——空着就刺眼。

新增模板：`templates/prd.md` / `templates/trd.md` / `templates/sprint.md` / `templates/queue/task-package.md`

**② 检查器群落**

| 检查器 | 覆盖范围 | 覆盖 Gate |
|--------|---------|---------|
| `check-docs.js` | PRD/TRD 结构完备 + 交叉一致性（实体对账、AC-nn 对账） | G1 / G2 |
| `check-sprint.js` | 任务包 17 字段完备 + AC 回链 + queue/sprint/status 三方一致 | G3 |
| `check-gate.js` | G4 manual-test 任务全 merged + 验收报告通过；G5 feedback 清空 | G4 / G5 |
| `check-ux.js` | draft-ux 产物结构（ux-flows / prototype-map / prototype.html 存在） | — |

**③ 门卫 hook（pre-commit-hook.sh）**

签字 commit 时按 staged 文件路由到对应检查器，红则拦 commit。
"记得跑 linter、退出码 0 才签"从散文变成机制——绕不过去，不再靠记性。

**④ AC 链路机械化**

PRD 每条 AC 分配全局唯一稳定 id（`AC-nn`，append-only，允许空号）。
链路：`PRD AC-nn` → `TRD "满足 AC：AC-nn"` → `任务包 "(源：AC-nn)"` → 测试代码 → check-sprint 逐条正反向对账。
机械可检查的范围：覆盖存在性、无悬空引用、全覆盖。语义忠实性留人。

**⑤ 末端审查 brief 外置**

5 份审查 brief 独立存放于 `templates/review-briefs/`，spec 正文只留一句派发指令。

| brief | 被审产物 | 派发时机 |
|-------|---------|---------|
| `prd-review.md` | prd.md | draft-prd Step 7.5 |
| `trd-review.md` | trd.md | draft-tech-design Step 5 |
| `task-package-review.md` | queue/*.md | plan-sprint Step 3.5 |
| `prototype-review.md` | prototype.html | draft-ux Step 5 |
| `develop-review.md` | git diff + 测试 | develop 每个 task 后 |

Brief 自包含：subagent 自读输入，不靠主线转手，无失真。

### 诚实账

当前"及格但不漂亮"：建检查器和模板是"搬运"而非净删除，真正的大块散文要等 G3/G4/G5 的检查器全部站稳后才能整段拔。删 AI/人眼步骤是主要的净收缩，散文大头是后续空间。

## 三、对抗式审查贯穿管线：自动化 loop 的引入

### 核心范式

旧版用 subagent 做冷核，但指令是"请逐条核对"——倾向给出"基本符合"的软结论，实质是概率系统评估概率系统，互相盖章。

新版的**隔离冷核范式**做了三件事：

1. **隔离上下文**：全新 subagent，自读磁盘最新原文，不受主会话锚定
2. **自读权威输入**：任务包 / git diff / standards 章节 / 测试代码，不收执行体的自评或摘要
3. **对抗化指令**：默认假设实现有问题，存疑即判阻断；找不到证据不放行

### 管线分布

| 阶段 | 审查形式 | 是否形成 loop |
|------|---------|-------------|
| draft-prd Step 7.5 | 独立 subagent 审内容有效性（一次） | 否 |
| draft-tech-design Step 5 | 独立 subagent 审 TRD 内容有效性（一次） | 否 |
| plan-sprint Step 3.5 | 独立 subagent 审任务包（一次） | 否 |
| draft-ux Step 5 | 独立 subagent 对抗审查原型（一次） | 否 |
| **develop 每个 task** | 独立审查 subagent，最多 3 轮，超界升级 | **是** |
| adversarial-review skill | B 类任务通用对抗审查入口 | 是 |

### 为什么这是自动化提升的关键

检查器解决的是格式和结构问题（确定性）；对抗式审查解决的是语义和质量问题（概率提升）。两者合力才能让人工门从 6 个压到 3 个——否则移掉人工门就是裸奔。

develop 的版本最重：审查 subagent 收到 findings → 执行 subagent 整改 → 重审，闭合 loop，不需要人在场。同任务 3 轮未过才升级给用户。

## 四、develop 执行模型翻转与 pr-review 砍除

### 旧模型 vs 新模型

**旧版**：主线逐 step 执行，每个关键判断等人确认（6 个 🚫 门），末端交 pr-review 做内容审查后人工合并。

**新版**：主线只编排（5 件事），实际写代码和审查都下沉到隔离的 subagent。

```
会话定标
    ↓
[仅 frontend] 前端设计门（一次性确认 design.md/prototype 覆盖）
    ↓
per-task loop：
    执行 subagent（自读任务包 → 写 → 自绿）
        ↓
    独立审查 subagent（对抗审查，最多 3 轮）
        ↓ 通过
    下一个 task
    ↓ 全部完成
末端全量验证（build/lint/test）
    ↓
[安全敏感预检] 权限/认证/不可逆操作 → 人工裁决
    ↓ 通过
commit → PR → 自合并到 master → 状态更新
```

人工门压缩到 3 处：前端设计到位确认、escape-hatch（审查 3 轮未过）、安全敏感预检。

### develop spec 减肥

471 行 → 305 行正文 + 49 行 develop-review.md brief = 354 行（-25%）

删掉的主要是：两种会话模式的分支描述（统一为"任务集"）、inline 的审查 prompt（外置 brief）、Fast Mode 定义（全自动下无意义）。

### pr-review 砍除

develop 内置独立审查后，pr-review 的内容复审全部冗余：

| pr-review 原有职责 | 新去向 |
|------------------|--------|
| standards 合规 | develop-review brief 第 3 类 |
| 测试保真 | develop-review brief 第 4 类 |
| AC 忠实性 | develop-review brief 第 1 类 |
| 设计保真比对 | develop-review brief 第 6 类（新增） |
| CR 留痕 | develop 末端 `code_reviews[]` |

**治理代价明确接受**：master 无第二人工门。安全敏感改动（权限/认证/数据隔离）保留 escape-hatch，触发 architecture discipline 人工裁决。

### develop-review.md 的 7 类审查

| 类 | 名称 | 要点 |
|----|------|------|
| 1 | AC 忠实性 | Given/When/Then 例子 1:1 物化成测试断言 |
| 2 | do-not 越界 | 禁止边界、凭据、超出 files 范围 |
| 3 | 标准合规 | relevant-standards 强制约定 |
| 4 | 测试品类空缺 | 鉴权/边界/错误/契约/安全注入等 |
| 5 | 留人判项 | N+1 / 日志隐私 / 竞态等明显漏洞 |
| 6 | 设计保真（frontend）| design.md 变量 + prototype.html 交互路径 |
| 7 | 用户输入去向追踪（backend）| DTO 每字段端到端穷举表 |

## 五、管线各站具体变化

### 上游质量前置：PRD 与 draft-ux 的系统强化

**核心目标**：在后端开发启动之前，把需求和交互中的隐含假设逐一显式化。
隐含假设是后端开发中最隐蔽的成本来源——开发者不得不自己猜或者临时决定，
猜错了要返工，猜对了也没有记录可循。

#### PRD 阶段的强化

**① 验收标准写成行为例子（AC 行为例子化）**

旧版 AC 写法：`用户可以删除订单`——可以验收，但不能告诉开发者"删除后系统应该做什么"。

新版 AC 写法（AC 下紧跟一行行为例子，格式固定）：
```
- AC-03：用户可以删除订单
  - 例：Given 用户在订单列表页、订单状态为"已完成" / When 点击"删除"按钮 / Then 弹出二次确认框；用户确认后订单从列表消失；后台记录软删除标记
```

这个例子由 CC 起草、产品负责人验证。意义在于：AC 变成了可以 1:1 转化成测试代码的规格，
从"告诉人"升级为"告诉机器"。

**② 功能类型识别 + 语义默认值补问**

在写每个功能时，新版 PRD 会主动识别功能类型，并就该类型的常见默认行为提问：

| 识别到的功能类型 | 必须有 AC 的隐含维度 |
|----------------|-------------------|
| 含数据列表 | 默认排序字段 + 方向；空态行为（纯提示 / 有引导 CTA） |
| 含搜索 | 搜索字段范围（哪些字段被检索） |
| 含不可逆操作（删除/清空） | 数据是否可恢复（软删保留 / 硬删彻底清除） |
| 含跨会话持久化状态 | 持久化范围（session 内 / 账号级跨设备） |

这些决策如果不在 PRD 阶段明确，开发者会在写代码时自己决定，
而这个决定往往不会被记录、也不会被验收。

**③ 新增必填字段**

- `入口`：用户从哪里触发这个功能？（防止开发完成才发现入口没有设计）
- `draft-ux`：是否需要交互原型？（让 PRD 显式触发交互设计阶段）

#### draft-ux 阶段的强化

**① AC 与场景的覆盖映射**

PRD 里每条 AC，在 draft-ux 阶段都会被对应到原型的具体画面。

- 前端可见的 AC：标注在哪个场景（S1/S2/...）的哪个画面里实现
- 纯后端逻辑的 AC：明确标注"排除，前端无画面"

产出 `prototype-map.md`，格式：

```
| AC-01 | 场景 S2（订单详情页） | 原型 HTML #order-delete-btn 段 |
| AC-02 | 排除：后端软删除，无前端画面 | — |
```

这张表让后续任务分配和测试核对都有机器可读的锚点，而非靠记忆。

**② 8 条行为待决扫描（交互决策的系统性穷举）**

在生成原型前，draft-ux 会主动扫描以下 8 类常见交互决策点：

| 序号 | 决策类型 | 典型问题 |
|------|---------|---------|
| 1 | 危险操作摩擦力 | 直接执行 / 弹确认框 / 手输确认词 |
| 2 | 批量选中触发方式 | 勾选框常驻 / hover 出现 / 长按触发 |
| 3 | 表单未保存离开 | 直接离开 / 警告弹窗 / 自动存草稿 |
| 4 | 空态引导形式 | 纯文案 / 带操作按钮的引导区 |
| 5 | 权限受限的 UI 表现 | 隐藏 / 禁用加提示 / 操作后报错 |
| 6 | 操作成功后的跳转 | 停留原页 / 跳回列表 / 刷新当前 |
| 7 | 数据加载失败处理 | 重试按钮 / 静默降级 / 整页错误态 |
| 8 | 列表行点击行为 | 跳到详情页 / 侧边抽屉 / 行内展开 |

这些问题在旧版里没有专门的环节提出，通常要等开发者写到这里才自己决定，
或者在验收时才发现和预期不符。

**③ 独立对抗审查原型**

原型生成后，由一个全新的、不知道前面设计过程的 AI 来走查原型，
检查是否有遗漏场景、死路、或隐含假设，输出问题清单。

#### 两个阶段强化的合力效果

```
PRD（行为例子化 + 语义默认值）
    ↓ 每条 AC 有具体例子
draft-ux（AC 覆盖映射 + 行为扫描 + 原型）
    ↓ 每条前端 AC 有画面锚点；每个交互决策已明确
draft-tech-design（TRD）
    ↓ 接口设计对照原型，字段满足画面需求，隐含假设已消除
develop（开发）
    ↓ 任务包里的 AC 有具体行为例子 → 测试代码 1:1 落地
    ↓ 开发时"不知道这里应该怎么做"的情况大幅减少
```

开发阶段最常见的隐藏成本——"没想到这里还有个决策"——在上游两个阶段就被系统性地清空。

### 前端视觉地基三件套（跨切面一致性首落地）

**触发**：看板应用 v8 一批前端开发包全部 `[merged]`、单元测试全绿、联调 35 场景全绿——但人工验收一打开界面，立刻发现 15 条系统性视觉偏离：主色全错（用了 Element Plus 默认的 `#409eff`，设计稿是 `#3370ff`）、16px 视口外溢、侧栏宽 180px（设计 208px）、脚栏带整块没做。所有自动门都是绿的，问题却是肉眼一看就满屏。

**病根：四个缺口**

| 缺口 | 含义 |
|------|------|
| R1 | token 定义了但没接线（变量声明在，全局没引用） |
| R2 | 没有全局基线层（reset / UI 库主题覆盖无人铺） |
| R3 | 跨组件的地基活无人认领 |
| R4 | 像素层面无机械门禁 |

**核心洞察：真正的新增量是 R2/R3——「跨切面地基」的结构盲区**

R1/R4 早在 2026-06-22 的「前端规范一致性框架」里就识别过（见 §六），并非新发现。这次真正补上的格子是 R2/R3：旧框架是「**逐组件复用**（reusables.md）+ **逐规则 lint**（单文件违规）」的视角，隐含假设每个视觉违规都挂在某个业务包里。但 **Element Plus 主题覆盖、全局 reset、body margin、脚栏带这类跨切面公共件不属于任何业务页面**——plan-sprint 按页 / 按组件切任务包时，它们天然落在所有包的缝隙里。这是 reusables（管现成组件）与 lint（管单文件）**两道防线之间的结构缝**。整条流水线里 manual-test 是视觉问题的**唯一捕捉网，而它在最后一环**——这些错不是"开发时引入的"，是"一直存在、到验收才第一次被人眼看到"。修法两手：在源头建一个专门的地基层，再把捕捉网从末端往前移。

**三件落地**

**① 视觉地基包**（治 R2/R3，真新增 ADD）：plan-sprint 新增骨架规则——含前端的迭代若项目尚无视觉地基（全局 reset + UI 库主题覆盖 + design.md token 全局接线），地基包就是前端首包，其余前端任务 `depends_on` 它，标记 `baseline: visual`；地基一旦建成（通常 v1）后续迭代不重建，只在 design.md 变更时触发跟进包。配套 Step 3.5 审查 brief 增第 ⑤ 维度「视觉地基完备性」+ `check-sprint.js` 硬核（v1 含前端却无 `baseline:visual` 包 → FAIL，vN+1 退人工确认）+ task-package 模板标记说明。

**② token 落地门禁**（治 R1）：`standards/frontend.md` 补两条强制——单一全局样式入口 + UI 库主题覆盖（禁用库默认主色）；`frontend-checklist.md` 段一加两条机械项（全局入口存在 / 主题被覆盖，地基包 PR 必核）；`draft-tech-design.md` 增「视觉地基约定」owner 块（与「测试基建约定」并列）。

**③ 视觉冒烟断言**（治 R4，前移捕捉网）：`generate-integration-tests.md` 涉视觉基线迭代时**必跑**（不再问"要不要做"），固化 3 条机械断言——实测渲染的 `--el-color-primary` == 设计主色 / `scrollWidth − innerWidth ≤ 0`（无横向外溢）/ 关键容器尺寸 == token 值；取数源是 design.md 新增的「〇、视觉冒烟锚点」段。

**两处类别纠正（落对层，本轮最易被误解的判断）**

- **token 落地不能写进 check-sprint / check-gate**：这两个检查器核的是 markdown 产物，而 **G3 签字时根本还没有代码**（代码在 develop 才写）。"裸 hex grep、主题是否被覆盖、全局入口是否存在"都是**代码级**检查，必须落 develop 的 stylelint + lint 层。三段保证各归其位：计划保证（地基包在 sprint 里）→ check-sprint；代码保证（无裸 hex / 主题被覆盖 / 全局入口在）→ develop lint；运行保证（实测 CSS 变量 == 设计）→ 视觉冒烟。
- **具体 stylelint 规则是技术栈层，不进 hact-method 通用模板**：哪个 UI 库、哪些文件路径是项目特定的，由 draft-tech-design 在项目仓播种 stylelint 配置；hact-method 只留"结构 + 机制"，**不新建通用 `check-visual-tokens.js`**。

**明确拒绝的 over-engineering**：像素快照 / visual regression CI、design-tokens.json 导出工具链、给所有任务包加 `visual-tokens-required` 字段、check-gate 加视觉核、通用 check-visual-tokens.js——冒烟断言（几条确定值比对）已覆盖 80%，ROI 远高于重基建。

### 规范致密化（全管线）

四件工具 + 一把语气刀的分工：

| 内容类型 | 旧版处理 | 新版处理 |
|---------|---------|---------|
| 格式/字段规则 | 写进 spec 正文 | 搬进 template 注释 |
| "记得跑 linter" | 散文强调 | 门卫 hook 机械强制 |
| 审查维度清单 | 写进 spec 正文 | 外置 brief，派发时指针 |
| 过程判断、红线 | 保留（不可动） | 保留（不可动） |
| 教学体措辞 | 大量 | 改指令体（最大减肥刀） |

各站减幅：draft-prd -42%、plan-sprint -33%、generate-integration-tests -35%、manual-test -7%、draft-tech-design +16%（机制补全优先于减肥）。

### draft-ux 整体重构

**旧版问题**：CC 把场景枚举、流程图、ASCII 线框图逐步外露给用户审查，用户被迫做"文字→画面"的脑内转换，体验像在做"交互工程师的助手"。

**新版角色**：CC = 交互工程师；用户 = 客户。中间设计过程内部消化，用户只参与上游业务沟通和下游原型走查。

新版关键新增：
- **Step 2 内部清单**：5 项必走（场景拆解 / AC→Sx 覆盖映射 / 流程穿线 / 画面构思 / 行为待决扫描），全程不外露
- **prototype-map.md**：前端 AC 与 HTML 锚点的机器可读映射（`AC-nn | 场景 | #{id}`），为后续对账建基础
- **Step 3.5 路径 B**：Claude Design 路径，生成 design-brief.md 供外部设计工具使用
- **Step 5 独立对抗审查**：替代旧版"自我走查"，隔离上下文冷审原型

### dispatch-new（B 流程质控升级）

| 维度 | 旧版 | 新版 |
|------|------|------|
| 信息收集 | 混用一张清单 | bug / optimization 分化清单，frontend 额外要视觉参照 |
| 进入门槛 | "继续追问" | **禁止带模糊信息进下一步**（硬线） |
| 中间对齐 | 无 | Step 3.5 行为契约草稿（AC + do-not + files 初估） |
| AC 格式 | 自由叙述 | 强制 Given/When/Then 格式 |
| schema 变更 | 独立 `schema-change` 字段 | 融入 AC + known-risks（消除幽灵字段） |

### standards 归位

`standards-{shared,frontend,backend}.md` 从 `iterations/vN/` 移到项目根。

旧版问题：每迭代"从上期副本重生"产生副本链，多个并行迭代各持一份副本，约定漂移。

新版：v1 播种，vN+1 在项目根原地增补，单一真相源，历史基线靠 git。所有消费者（plan-sprint / develop / manual-test / revise-doc）改读项目根。

## 六、架构治理调整与未来方向

### 骨架层变化

| 维度 | 旧版 | 新版 | 原因 |
|------|------|------|------|
| discipline 数量 | 9 个（含 review） | 8 个 | 代码审查内嵌 develop，不再是独立学科 |
| task type 数量 | 13 个（含 pr-review） | 12 个 | pr-review 砍除，职责内化进 develop |
| develop 完成判据 | 代码完成 + pr-review 通过 + merged | 代码完成 + per-task 对抗审查通过 + 全量绿 + merged | 自审自合并 |

### 进行中的三个方向（未全面落地）

**行为规格管线**：PRD Step 4 新增语义默认值识别（默认排序/搜索范围/软硬删/持久化）；draft-ux Step 2 新增 8 条行为待决扫描清单（危险操作摩擦力/批量选中/未保存离开/空态 CTA 等），在上游把"没说清楚"的交互决策显式化。

**隐性假设防线**：develop-review 第 7 类"用户输入去向穷举表"——对每个 DTO 字段逐条追问去向（service 在哪消费 / 是否被系统值覆盖 / 结论）。无声明→建议；TRD 已声明 user-owned 但 service 忽略→阻断。adversarial-review skill 同步。

**前端规范一致性框架（视觉地基部分已落地）**：三维度（视觉规则 / 组件复用 / 交互模式）× 四站点（TRD / plan-sprint / develop / wrap-up）的系统框架。其中**视觉地基**（R2/R3 跨切面公共件 + R1 token 接线 + R4 像素冒烟）已于 2026-06-28 落地为「视觉地基三件套」（见 §五）。**仍待议**：组件复用维度的全量机械化——`check-reusables.js` 防同一组件多处重复实现 / 禁本地重声明、自动核对该复用处是否复用。

### 待议清单中的最高优先级

以下条目已识别、尚未动手，是未来演进的主要着力点：

1. **develop 拆分为多 task type**：source=sprint/bug/optimization 三条路径上下文加载和反馈去向不同，合在一份 304 行规范里仍有冗余。拆分后每个 type 的规范可进一步收缩，同时消除"运行时按属性分支"的解析风险。

2. **B 类升级触发检测**：B 类任务如果实际修改了 TRD/standards 等共享契约，当前无任何机制检测，会静默绕过 G2/G3 保护。在 dispatch-new 或 develop 入口增加"是否改动共享契约"自检。

3. **TRD shared-type-first**：TRD 按 API 模块并行生成的前提——先跑"共享类型定义"subagent 产出 schema.md，所有后续 API 模块 subagent 引用它。解锁 TRD 并行化、降低 draft-tech-design 的 context 压力。

4. **status.yml 校验落地**：目前 status.yml 是"只写没人读"——看板应用仍读 markdown。等看板应用切读 status.yml 时同步落 check-status.js + 入门卫，消除双轨并行。
